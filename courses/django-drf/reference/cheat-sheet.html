Cheat-Sheet

The maps for the whole course on one page: the request lifecycle, the three-rung verb mapping, the view ladder, and the decisions (which serializer hook, which relation prefetch, which status code). The glossary defines the terms; this sheet shows how they fit. Built to print.

The request lifecycle, end to end

  HTTP request
     │
  ┌──────────────── MIDDLEWARE (onion, top-down) ───────────────┐   L14
  │ Security → Session → Common → Csrf → Auth → ...             │
  │   │                                                          │
  │  URLconf  path() matches the PATH only (never the verb)      │   L2
  │   │                                                          │
  │  view callable = as_view()  →  dispatch() reads the verb     │   L3
  │   │                          →  get()/post()/...  (or 405)   │
  │   │                                                          │
  │  [ DRF APIView ]  auth → permission → throttle  (the gate)   │   L11
  │   │               request.data (parsed) ; Response (negotiated)  L5
  │   │               serializer  ⇄  queryset (lazy, cached)     │  L8/L9
  │   ▼                                                          │
  │  action / handler runs, returns Response                     │
  └──────────────── response back out, BOTTOM-UP ───────────────┘
     │
  HTTP response

Middleware wraps everything. Routing picks the view by path; the verb is resolved inside it. DRF swaps the request/response objects and runs the gate before your handler.

The three-rung verb mapping

Rung 1  FBV        if request.method == "GET": ...   (you branch)     L3
Rung 2  CBV View   def get(self, ...)   dispatch routes  (Django)     L3
Rung 3  ViewSet    as_view({"get": "list"})  + router   (as data)     L6

DRF's APIView subclasses Django's View: it inherits rung 2, it did not invent it. Rung 3 is the only routing DRF adds on top.

The view abstraction ladder

APIView                  you write get()/post() + logic          L5
  + queryset, serializer_class
GenericAPIView           knows objects + serializer              L10
  + mixins (list/create/retrieve/update/destroy)
GenericAPIView + mixins  behavior exists; wire get()→list()      L10
  pre-combined
concrete generics        ListCreateAPIView, etc.; set 2 attrs    L10
  as a viewset
ModelViewSet + router    all six actions, routed                 L6/L10

Each rung removes code. Drop down a level the moment the packaging stops fitting.

Relations in a loop = N+1. See next box.

select_related vs prefetch_related

select_relatedprefetch_related
RelationFK, OneToOne (one-side)M2M, reverse FK (many-side)

Put them in get_queryset(), not on self.queryset (that is cached across requests). This is the N+1 fix for API list endpoints.

Serializer: both directions

OUT:  Serializer(obj).data           → native → JSON
      Serializer(qs, many=True).data
IN:   Serializer(data=request.data)
      .is_valid() → .validated_data → .save()

Serializer validation ladder

1  field type/format checks   (built in)
2  validate_<field>()         (one field)
3  validate(self, data)       (across fields)

One field: validate_<field>. Two fields: validate. ModelSerializer infers fields + validators + create/update. Nested writes need an explicit create()/update().

Migrations: two commands

edit model
  → makemigrations  write numbered file (no DB hit)
  → sqlmigrate app N  preview SQL (optional)
  → migrate  apply unapplied files to the DB
  → commit the file  version control for schema

Reverse: migrate app 0002 unapplies everything after 0002.
