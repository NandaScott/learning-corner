Django & DRF · Reference

Glossary

The shared vocabulary for this course, in plain language, no Django background assumed. Every lesson uses these terms exactly as defined here. Print it; keep it next to you.

Django: the framework and its shape

TermDefinition
Framework (batteries included)A bundle of decided answers to the problems every database-backed site shares, built to work together: models, URL routing, templates, forms, auth, an admin. Django's slogan: "for perfectionists with deadlines." (Lesson 1)
ModelA Python class describing a database table's shape. Django reads it to run queries for you (the ORM), so you write Python, not SQL. One model definition is the single source for that data's structure. (Lesson 1)
ORMObject-relational mapper: the layer that turns model classes and Python method calls into SQL and back. (Lesson 1)
TemplateThe HTML presentation, kept separate from the logic that fetches data. In MTV naming, this is what classic MVC calls the "view." (Lesson 1)
AdminAn add/change/delete interface Django generates by reading a registered model's metadata. An internal tool for trusted staff, not a public front end. (Lesson 1)
MTVModel-Template-View, Django's naming of the MVC pattern. MVC's controller → Django's view; MVC's view → Django's template. (Lesson 1)
DRY"Don't repeat yourself." Every distinct concept or piece of data lives in one place; Django deduces the rest from minimal input. (Lesson 1)
Loose couplingThe layers (templates, database, views) stay independent and don't need to know about each other. Django's stated design goal, alongside tight cohesion within a layer. (Lesson 1)

Django: the request cycle

TermDefinition
ViewThe request-answering logic. Precisely: a callable that takes an HttpRequest and returns an HttpResponse. Not the HTML (that's the template). The word carries the whole course. (Lesson 2)
HttpRequestThe object Django builds for each incoming request, holding its metadata (path, method, headers, body). Passed into the view. (Lesson 2)
HttpResponseWhat a view must return: the bytes (and status/headers) sent back to the client. A plain one sends whatever you put in it, with no content negotiation. (Lesson 2)
URLconfA list of path() entries mapping URL routes to views. Matches on the path only; the HTTP method is not used for routing. (Lesson 2)
path()One URLconf entry: a route string → a view, with optional <converter:name> segments that capture and type-cast parts of the URL, passed to the view as keyword arguments. (Lesson 2)
HTTP verb / methodGET, POST, PUT, PATCH, DELETE, etc. A field on the request. Because routing ignores it, all verbs for one URL reach the same view. (Lesson 2)

The verb-to-view mapping (the three rungs)

TermDefinition
Function-based view (FBV)A view written as a plain function. To serve multiple verbs on one URL it branches: if request.method == "GET". Rung 1, the "jank." (Lesson 3)
Class-based view (CBV) / ViewA view written as a class subclassing django.views.View. Each verb is a like-named method (get, post, ...); no request.method branching in your code. Rung 2. (Lesson 3)
as_view()Class method that bridges the URLconf and a CBV. Returns a callable that, per request, instantiates the class, runs setup(), then calls dispatch(). On a viewset it also accepts a verb→action map. (Lessons 3, 6)
dispatch()The method that reads request.method once and routes to the like-named handler. This is where the verb check relocated to (it didn't disappear). (Lesson 3)
http_method_namesThe verbs a View will route, default ["get","post","put","patch","delete","head","options","trace"]. (Lesson 3)
http_method_not_allowed() / 405Called by dispatch() when a known verb has no matching handler; returns HttpResponseNotAllowed (HTTP 405) listing supported methods. Free correct rejection. (Lesson 3)

DRF: what it adds on top

TermDefinition
DRFDjango REST Framework: a toolkit for building Web APIs on Django. It does not replace Django's request handling; it enriches it and (with viewsets/routers) abstracts routing. (Lesson 4)
Content negotiationChoosing the response's content type from what the client asked for (e.g. the Accept header). DRF's Response does it; plain HttpResponse does not. (Lesson 4)
Request (DRF)Extends HttpRequest with flexible parsing. (Lesson 5)
request.dataThe parsed request body: file and non-file input, across POST/PUT/PATCH, for JSON and other media types. The API-fit replacement for request.POST. (Lessons 4, 5)
Response (DRF)Takes unrendered Python data, runs content negotiation, and renders to the chosen type. Default renderers: JSON and the browsable API. (Lesson 5)
Browsable APIThe default HTML rendering of a DRF endpoint, letting a developer explore the API in a browser. One of the two default renderers. (Lesson 5)
SerializerConverts both directions: model instance/queryset → native Python (.data) → JSON, and incoming data → validate (is_valid()) → validated_data → save(). (Lesson 5)
@api_view / APIViewDRF's two view wrappers (function / class). Both deliver a DRF Request, add Response negotiation context, and auto-handle 405 and ParseError. APIView subclasses Django's View, inheriting the verb dispatch. (Lesson 5)

DRF: routing as data (rung 3)

TermDefinition
ViewSetOne class grouping a resource's behaviors as named actions rather than HTTP-verb methods. (Lesson 6)
ActionA named behavior on a viewset. The standard six: list (GET collection), create (POST collection), retrieve (GET member), update (PUT member), partial_update (PATCH member), destroy (DELETE member). (Lesson 6)
Verb→action mapThe dict passed to as_view({"get": "list", "post": "create"}) tying HTTP verbs to actions. Routing expressed as readable data. (Lesson 6)
RouterRegisters a viewset and generates its URLconf: the collection and member URL patterns and their verb→action maps, so you don't hand-write them. (Lesson 6)
@actionDecorator marking a viewset method as an extra routed action beyond the standard six, declaring its methods and whether it's detail (member) or collection. (Lesson 6)
Collection vs member URLCollection = the resource list (/snippets/); member = one item (/snippets/42/). The same verb (GET) means different actions on each (list vs retrieve). (Lesson 6)

The ORM and the QuerySet

TermDefinition
Manager (.objects)The query entry point on a model. Model.objects.filter(...) returns a QuerySet. (Lesson 8)
QuerySetA description of a database query, not its results. Lazy: building and chaining it runs nothing. (Lesson 8)
Lazy / evaluationA QuerySet hits the database only when evaluated: iterated, passed to list()/len(), truth-tested, or printed. Chained filters resolve to a single query at that point. (Lesson 8)
QuerySet cacheAfter full evaluation, results are stored on the QuerySet and reused. Reuse one saved variable rather than re-calling .all(). Slicing/indexing an unevaluated set can re-query. (Lesson 8)
N+1 problem1 query for a list plus 1 more per row to follow a relation, because related-object access is itself a query. Scales with row count. (Lesson 8)
select_relatedPulls ForeignKey / OneToOne relations in the first query via a SQL join, so later attribute access does not re-query. The one-side fix for N+1. (Lesson 8)
prefetch_relatedPulls ManyToMany / reverse relations in a separate query, joined in Python. The many-side fix for N+1. (Lesson 8)

Serializers in depth

TermDefinition
ModelSerializerA serializer that reads a model (via inner Meta.model + Meta.fields) and generates matching fields, model-derived validators (e.g. unique_together), and default create()/update(). (Lesson 9)
Field-level validationA validate_<field>() method: a rule about one field, returning the value or raising ValidationError. Sees only that field. (Lesson 9)
Object-level validationA validate(self, data) method: a rule across fields, receiving the whole data dict. The place for cross-field checks. (Lesson 9)
Writable nested serializerA serializer embedded in another (Child(many=True)). Reads automatically; writing requires overriding create()/update() to save the nested objects. (Lesson 9)

Generic views (the abstraction ladder)

TermDefinition
GenericAPIViewA subclass of APIView that adds queryset and serializer_class attributes and getters (get_queryset(), get_serializer_class(), get_object()). Has no verb handlers on its own. (Lesson 10)
MixinA class supplying one action method: ListModelMixin.list, CreateModelMixin.create, RetrieveModelMixin.retrieve, UpdateModelMixin.update, DestroyModelMixin.destroy. Combined with GenericAPIView. (Lesson 10)
Concrete generic viewA pre-combined class needing only queryset + serializer_class: e.g. ListCreateAPIView (GET, POST), RetrieveUpdateDestroyAPIView (GET, PUT, PATCH, DELETE). (Lesson 10)
get_queryset()The method to override for a per-request queryset (e.g. per-user filtering) and for adding select_related/prefetch_related. Use it rather than self.queryset, which is evaluated once and cached across requests. (Lesson 10)
ModelViewSetThe concrete generics gathered into one viewset: given queryset + serializer_class, it implements all six actions and is routed by a router. Top of the ladder. (Lessons 6, 10)

Authentication and permissions (the gate)

TermDefinition
AuthenticationDecides who the request is. Runs first, before permission and throttling; sets request.user and request.auth. Set via authentication_classes. (Lesson 11)
Permission (authorization)Decides whether the identified request may proceed. An all-must-pass list of classes checked before the view runs. Set via permission_classes. (Lesson 11)
ThrottlingCaps how often a client may call. Runs after permission. UserRateThrottle keys on user id (IP for anonymous) with a rate like "60/min". (Lesson 11)
has_permission vs has_object_permissionRequest-level check (may this user reach the view) vs object-level check (may they act on this row). Per-owner rules live in has_object_permission. (Lesson 11)
SAFE_METHODSThe read-only verbs GET, HEAD, OPTIONS. Used in permissions to allow reads while restricting writes. (Lesson 11)
401 vs 403401 Unauthorized: no or failed identity. 403 Forbidden: identity known, action refused. Falls out of the auth-then-permission order. (Lesson 11)
TokenAuthenticationA scheme where the client sends Authorization: Token <key>; on success request.user is a User and request.auth is a Token. (Lesson 11)

Migrations (the schema write side)

TermDefinition
MigrationA numbered, dependency-ordered file describing a schema change (its operations). Version control for the database. (Lesson 13)
makemigrationsDiffs the current models against the last migration and writes a new migration file. Records the change; does not touch the database. (Lesson 13)
migrateApplies unapplied migration files to the database, in dependency order. Tracks what is already applied. Naming an earlier migration rolls back to it. (Lesson 13)
sqlmigratePrints the SQL a given migration would run, without executing it. (Lesson 13)

Middleware (the request pipeline)

TermDefinition
MiddlewareA framework of hooks into request/response processing: a plugin system for globally altering input or output, running around every view. (Lesson 14)
MIDDLEWAREThe ordered setting listing the middleware stack. Order matters: session-dependent layers after SessionMiddleware, security near the top. (Lesson 14)
The onionEach middleware wraps the next. Request phase runs top-down through the list; response phase runs bottom-up (reverse); the view is the center. (Lesson 14)
get_responseThe next step in the chain (next middleware, or the view). A middleware calls it to descend a layer; work before the call is the request phase, work after is the response phase. (Lesson 14)
Short-circuitA middleware returning a response without calling get_response. Inner layers and the view never run; only already-run outer layers process the response. (Lesson 14)

Testing DRF

TermDefinition
APITestCaseA test class like Django's TestCase but with self.client set to an APIClient. Base class for endpoint tests. (Lesson 15)
APIClientA test client that sends real requests to your URLs (.get()/.post()/...), with a format argument (e.g. format="json"), and returns the response. (Lesson 15)
format="json"Tells the test client to send a JSON body (the API path). Omit it and the client sends multipart form data, a different code path. (Lesson 15)
force_authenticateSets request.user directly, bypassing the token/session mechanics, so a test exercises permission logic rather than authentication. On the client or on a factory-built request. (Lesson 15)
APIRequestFactoryBuilds a request object passed straight to View.as_view(), with no URL resolution or middleware. For testing one view in isolation. (Lesson 15)
