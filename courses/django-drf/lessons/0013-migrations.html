Migrations

Lesson 8 was the read side of the ORM: querying rows that already exist. This lesson is the write side of the schema itself. A model describes the shape you want a table to have, but changing a Python class does not change a database. Migrations are how Django turns a model edit into an actual schema change, and keeps every environment's schema in step.

The concept

Two schemas exist at once: the one your models describe in Python, and the one the database actually has. When you edit a model (add a field, drop a field, add a table) those two drift apart. Migrations close the gap. The docs call them Django's mechanism for propagating model changes into the database schema, and describe them as a version control system for the database: changes are packaged into migration files, then applied.1

Two commands do the work, and keeping them straight is most of this lesson: makemigrations writes the change down as a file, and migrate applies that file to the database.

The steps

  1. edit a model            add/remove a field on the Python class
        │
  2. makemigrations          Django diffs models vs the last migration,
        │                    writes a new migration file (e.g. 0002_...)
        │
  3. sqlmigrate  (optional)  see the SQL that file would run
        │
  4. migrate                 run the file's operations against the database
        │
  5. commit the file         the migration is checked into version control

Step 2 records the intent as a file; step 4 executes it. The two are separate on purpose.

Step 2 - makemigrations writes the change down

After editing a model, makemigrations compares the current models to the state captured by the previous migrations and writes a new migration file describing the difference:2

$ python manage.py makemigrations polls
  Migrations for 'polls':
    polls/migrations/0002_question_pub_date.py
      + Add field pub_date to question

The result is a file, not a schema change. Nothing has touched the database yet.2

Migration files are numbered per app (0001_initial, 0002_...), and each declares the operations it performs and its dependencies on earlier migrations. That ordering is what lets Django replay the same sequence of changes on any database and arrive at the same schema.1

Step 3 - sqlmigrate shows the SQL (optional)

A migration is not SQL; it is a description Django can turn into SQL for whatever database you use. To see exactly what it would run, ask:2

$ python manage.py sqlmigrate polls 0001

Useful for review, and for seeing that one migration can become several SQL statements. It only prints; it changes nothing.2

Step 4 - migrate applies it

migrate runs the unapplied migration files against the database, in dependency order, across every app:2

$ python manage.py migrate
  Operations to perform:
    Apply all migrations: admin, auth, contenttypes, sessions, polls
  Running migrations:
    Applying polls.0002_question_pub_date... OK

Django tracks which migrations are already applied, so migrate only runs the new ones. Run it once per environment (dev, staging, production).2

Migrations run backward too

Because the files are an ordered history, you can move to an earlier point. Naming a target migration unapplies everything after it:3

$ python manage.py migrate books 0002
  Unapplying books.0003_auto... OK

Rolling books back to 0002 reverses 0003. The history is navigable in both directions.3

Why this matters

The split between makemigrations and migrate is the whole idea. One records a schema change as a versioned file; the other applies recorded files to a database. Because the files are committed to source control and applied in order, every developer's laptop, the CI server, staging, and production all run the same sequence and end up with the same schema. That is what "version control for the database" means in practice: the model is the source of truth for shape (the DRY principle from Lesson 1), and migrations are the audited trail that carries that shape into every real database.

Key line "Editing a model does not change the database. makemigrations writes the change as a numbered, dependency-ordered file; migrate applies unapplied files to the database. The committed files are version control for the schema, keeping every environment in step."
The trap Thinking makemigrations changes the database. It only writes a file; the database is untouched until migrate. The mirror mistake is editing a model and running the app without makemigrations: the model and the schema now disagree, and queries against the missing column fail. Two commands, two distinct effects: record, then apply.

Recall, answer out loud before peeking:

① You add a field to a model. Which command records the change, which applies it, and what does the first one produce?

show answer

makemigrations records it, producing a numbered migration file (e.g. 0002_...) describing the operations. migrate applies unapplied files to the database. The database is unchanged until migrate runs.

② Why are migration files numbered and committed to version control?

show answer

They form an ordered history with dependencies, so replaying the same sequence on any database yields the same schema. Committing them keeps every environment (dev, CI, staging, production) in step. They are version control for the schema.

③ How do you see the SQL a migration will run, and how do you roll one back?

show answer

sqlmigrate <app> <number> prints the SQL without running it. migrate <app> <earlier-number> unapplies everything after that target.
