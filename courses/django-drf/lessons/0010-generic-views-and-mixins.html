Generic views and mixins

Lesson 5 wrote a full APIView by hand; Lesson 6 collapsed a resource into a viewset. This lesson fills the rung between them. Most API views do the same five things (list, create, retrieve, update, delete) against a queryset and a serializer, so DRF factors that repetition into mixins and pre-built generic views. It also shows what a ModelViewSet was made of all along.

The concept

Start from GenericAPIView, a subclass of the APIView from Lesson 5. It adds two attributes that name the pieces a CRUD view needs: queryset (the objects, Lesson 8) and serializer_class (the object-to-JSON boundary, Lesson 9). It also adds helper methods that read those attributes: get_queryset(), get_serializer_class(), and get_object(), which looks up a single row using lookup_field (default pk).1 On its own GenericAPIView still has no get() or post(). The behavior comes from mixins.

The steps: climbing the abstraction ladder

  APIView                         you write get()/post() and all the logic      (L5)
     │  + queryset, serializer_class, get_object()
  GenericAPIView                  knows the objects + the serializer
     │  + mixins (list/create/retrieve/update/destroy)
  GenericAPIView + mixins         behavior exists; you wire get()→list()
     │  pre-combined
  concrete generics               e.g. ListCreateAPIView; set 2 attributes
     │  as a viewset
  ModelViewSet + router           all six actions, routed as data           (L6)

Each rung removes code. Same machinery underneath: the verb dispatch from Lesson 3, carrying the DRF objects from Lesson 5.

Rung A - mixins supply the actions

Each mixin provides one action method: ListModelMixin.list, CreateModelMixin.create, RetrieveModelMixin.retrieve, UpdateModelMixin.update, DestroyModelMixin.destroy. You combine the mixins you want with GenericAPIView and connect each HTTP verb to the mixin's action:2

class SnippetList(mixins.ListModelMixin,
                  mixins.CreateModelMixin,
                  generics.GenericAPIView):
    queryset = Snippet.objects.all()
    serializer_class = SnippetSerializer

    def get(self, request, *args, **kwargs):
        return self.list(request, *args, **kwargs)
    def post(self, request, *args, **kwargs):
        return self.create(request, *args, **kwargs)

The mixins give you list() and create(); you still map get→list and post→create by hand. Note the verb dispatch is the same get()/post() from Lesson 3.2

Rung B - concrete generics pre-combine the mixins

The common mixin combinations are already packaged as concrete view classes, so you set only the two attributes:3

class SnippetList(generics.ListCreateAPIView):
    queryset = Snippet.objects.all()
    serializer_class = SnippetSerializer

class SnippetDetail(generics.RetrieveUpdateDestroyAPIView):
    queryset = Snippet.objects.all()
    serializer_class = SnippetSerializer

The whole hand-wiring above collapses to a class name. The pre-built set covers the combinations:3

  ListAPIView                 GET (collection)
  CreateAPIView               POST
  RetrieveAPIView             GET (member)
  UpdateAPIView               PUT, PATCH
  DestroyAPIView              DELETE
  ListCreateAPIView           GET, POST
  RetrieveUpdateAPIView       GET, PUT, PATCH
  RetrieveDestroyAPIView      GET, DELETE
  RetrieveUpdateDestroyAPIView GET, PUT, PATCH, DELETE

Pick the class whose verbs match the endpoint. Each still just needs a queryset and a serializer_class.3

Rung C - override the getters for dynamic behavior

Setting the queryset attribute is the static case. Override get_queryset() when the set depends on the request, for example per-user filtering. The docs are explicit that you should use get_queryset() rather than reading self.queryset directly, because self.queryset is evaluated only once and cached across all requests:4

def get_queryset(self):
    user = self.request.user
    return user.accounts.all()

Per-request querysets go here. This is also where the Lesson 8 fix lives:4

def get_queryset(self):
    return Order.objects.select_related("customer") \
                        .prefetch_related("items__product")

When the serializer follows relations, add select_related/prefetch_related to get_queryset() so a list endpoint does not become N+1.4

Rung D - ModelViewSet is the whole ladder as a viewset

Lesson 6's ModelViewSet is what you get when the concrete generics are gathered into one viewset. Give it a queryset and a serializer_class and it implements all six actions, ready for a router:5

class AccountViewSet(viewsets.ModelViewSet):
    queryset = Account.objects.all()
    serializer_class = AccountSerializer

Two attributes, full CRUD, routed by a router (Lesson 6). This is the top of the ladder.5

Why this matters

The ladder is one idea repeated: name the queryset and the serializer once, and let DRF supply the behavior. APIView gives you the dispatch and nothing else; GenericAPIView plus mixins supplies the five actions; concrete generics pre-mix the common cases; ModelViewSet plus a router is the fully abstracted end. Knowing the rungs means you can drop down a level the moment the packaging does not fit, and you know exactly which method (get_queryset, get_serializer_class, get_object) to override instead of abandoning the generics.

Key line "GenericAPIView adds queryset + serializer_class to APIView; mixins add the five action methods; concrete generics pre-combine them; ModelViewSet is the lot as a viewset. Override get_queryset() (not self.queryset) for per-request sets and to add select_related/prefetch_related."
The trap Reaching for self.queryset inside a method, or filtering it in place. self.queryset is evaluated once and cached across every request, so per-request logic there leaks between users. Override get_queryset() instead. And remember concrete generics did not replace the verb dispatch: a ListCreateAPIView still answers via the same get()/post() methods from Lesson 3, now filled in by the mixins.

Recall, answer out loud before peeking:

① What two attributes does GenericAPIView add over APIView, and what do mixins add on top?

show answer

queryset and serializer_class (plus getters like get_object()). Mixins add the action methods: list, create, retrieve, update, destroy.

② You need a read-write collection endpoint (GET list, POST create) with no custom logic. Which concrete generic, and what must you set?

show answer

ListCreateAPIView. Set queryset and serializer_class; nothing else is required.

③ Why override get_queryset() instead of setting self.queryset, and what Lesson 8 tool belongs there?

show answer

self.queryset is evaluated once and cached across all requests, so per-request logic (like per-user filtering) must go in get_queryset(). It is also where you add select_related/prefetch_related to avoid N+1.

④ What is a ModelViewSet, in terms of this ladder?

show answer

The concrete generics gathered into a single viewset: given a queryset and serializer_class, it implements all six actions and is routed by a router (Lesson 6).
