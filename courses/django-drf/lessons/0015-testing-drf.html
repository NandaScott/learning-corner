Testing DRF

Everything the course built runs behind an HTTP boundary: a request comes in, a view answers, a status code and a payload go out. That boundary is exactly what a test should exercise. DRF ships test helpers that let you send a request to an endpoint and assert on the response, so the whole stack (routing, the verb dispatch, the serializer, the auth gate) is checked end to end.

The concept

DRF extends Django's testing tools with API-aware versions. The two you reach for most are APITestCase (a test class that behaves like Django's TestCase but gives you an API client) and APIClient (a client that sends real requests to your URLs and hands back the response).1 A test builds a request, sends it through the actual view, and asserts on the status code and the returned data. No mocking of the framework; you test what a real caller would see.

Arrange a request, act by sending it, assert on what came back. The same shape as any test, at the HTTP boundary.

1-4. A full endpoint test

The canonical create test builds the URL by name, posts JSON, and checks both the status code and that the object landed:1

from django.urls import reverse
from rest_framework import status
from rest_framework.test import APITestCase
from myproject.apps.core.models import Account

class AccountTests(APITestCase):
    def test_create_account(self):
        url = reverse("account-list")
        data = {"name": "DabApps"}
        response = self.client.post(url, data, format="json")
        self.assertEqual(response.status_code, status.HTTP_201_CREATED)
        self.assertEqual(Account.objects.count(), 1)
        self.assertEqual(Account.objects.get().name, "DabApps")

Three things worth naming: format="json" sends a JSON body (the API case from Lesson 5), status.HTTP_201_CREATED is the readable status constant, and the assertions check both the response and the database.1

The APIClient supports every verb (.get(), .post(), .put(), .patch(), .delete()), so one test class can drive the whole verb dispatch from Lesson 3 and check that each method returns the right status:2

from rest_framework.test import APIClient

client = APIClient()
client.post("/notes/", {"title": "new idea"}, format="json")

A GET on a missing member should be 404, a POST with bad data should be 400 (the serializer validation from Lesson 9), a wrong verb should be 405. Each is one short test.2

Testing behind the auth gate

Lesson 11 put an authentication and permission gate in front of every view. To test the logic behind the gate without building real credentials, force_authenticate makes the client act as a given user:3

user = User.objects.get(username="lauren")
client = APIClient()
client.force_authenticate(user=user)

Every request from this client now counts as that user. It sets request.user directly, skipping the token or session path, so the test exercises your permission rules, not the authentication mechanics.3

This is what lets you test the object-level rules from Lesson 11 cleanly: authenticate as the owner and assert a 200 on edit, authenticate as someone else and assert a 403, send no authentication and assert a 401. Three users, three status codes, the permission logic pinned down.

Testing a view in isolation: APIRequestFactory

When you want to test one view without routing through URLs, APIRequestFactory builds a request object you pass straight to the view. The standalone force_authenticate helper works on that request:4

from rest_framework.test import APIRequestFactory, force_authenticate

factory = APIRequestFactory()
view = AccountDetail.as_view()

request = factory.get("/accounts/django-superstars/")
force_authenticate(request, user=user)
response = view(request)

Lower level than APIClient: no URL resolution, no middleware, just the view called with a request. Use it for focused unit tests of a single view's logic.4

Why this matters

The API boundary is the right place to test, because it is where behavior is defined: a caller sends a request and expects a status and a payload. APITestCase plus APIClient test at exactly that boundary, driving the real routing, verb dispatch, serializer, and auth gate in one pass, which makes them the natural fit for a red-green loop on an endpoint. Drop to APIRequestFactory when you want a single view under a microscope. And force_authenticate is the tool that keeps auth from getting in the way: it separates "does the permission logic work" from "does the token machinery work," so each can be tested for what it is.

Key line "Test at the HTTP boundary: APITestCase gives you an APIClient; send a real request with format=\"json\" and assert on response.status_code and response.data. force_authenticate(user=...) sets request.user directly so you test permission logic, not the token path; APIRequestFactory tests one view in isolation."
The trap Two easy mistakes. Forgetting format="json": the client then sends multipart form data, which is not the API path you meant to test and can pass or fail for the wrong reason. And reading force_authenticate as testing login: it deliberately bypasses the authentication mechanics and just sets request.user, so it validates permission rules, not whether a real token or session would authenticate. Test the token path separately if you need to.

Recall, answer out loud before peeking:

① What two helpers do you use to send a request to an endpoint and assert on the response, and what do you assert on?

show answer

APITestCase (the test class, giving you self.client, an APIClient). You assert on response.status_code (via status.HTTP_* constants) and on response.data and/or the database state.

② Why pass format="json", and what happens if you forget it?

show answer

It sends a JSON body, the actual API request shape. Without it the client sends multipart form data, so you are testing a different code path than the one your API clients use.

③ You want to test that a non-owner gets 403 on edit. Which helper, and what does it actually do?

show answer

force_authenticate(user=...) on the client. It sets request.user directly, bypassing the token/session mechanics, so the test exercises the permission rules (Lesson 11), not the authentication path.

④ When would you use APIRequestFactory instead of APIClient?

show answer

To test a single view in isolation: it builds a request you pass straight to View.as_view(), with no URL resolution or middleware. Lower level, for focused unit tests.
