Django & DRF · Lesson 9

Serializers in depth

Lesson 5 introduced the serializer as the object-to-JSON boundary with validation. This lesson goes inside it: the ModelSerializer shortcut that infers fields from a model, the two layers of custom validation, and what it takes to write a nested serializer that can save. This is the layer where "is this input acceptable" is actually decided.

The concept

A plain Serializer makes you declare every field by hand. Most of the time a serializer mirrors a model, so DRF provides ModelSerializer: it reads the model and generates matching fields for you, adds model-derived validators (such as a unique_together constraint), and supplies default create() and update() implementations.1 You describe what you want in an inner Meta class:

class AccountSerializer(serializers.ModelSerializer):
    class Meta:
        model = Account
        fields = ["id", "account_name", "users", "created"]

Meta.model says which model; Meta.fields lists what to expose. Fields, validators, and create/update come for free from the model.1

The steps: the validation ladder

When you call is_valid() (Lesson 5), DRF runs validation in layers, from narrow to wide. Two of those layers are yours to customize.

  incoming request.data
        │
  1. per-field type/format checks   (built in: is this an int? a valid date?)
        │
  2. validate_<field>()             (your rule for ONE field)
        │
  3. validate()                     (your rule ACROSS fields)
        │
  validated_data  →  create() / update()  →  saved object

Field checks first, then your field-level rules, then your object-level rule. Only data that clears all three reaches validated_data.

Layer 2 - field-level validation

Add a validate_<field_name>() method for a rule about one field. It receives that field's value and must return the validated value or raise serializers.ValidationError. If the field is optional (required=False), the method only runs when the field is present:2

class BlogPostSerializer(serializers.Serializer):
    title = serializers.CharField()

    def validate_title(self, value):
        if "django" not in value.lower():
            raise serializers.ValidationError("Blog post is not about Django")
        return value

One field, one method. Return the value on success; raise ValidationError to reject.2

Layer 3 - object-level validation

When a rule spans more than one field, put it in validate(). It receives a dictionary of all the field values and must return that dictionary or raise ValidationError:3

    def validate(self, data):
        if data["start"] > data["finish"]:
            raise serializers.ValidationError("finish must be after start")
        return data

This is the layer for cross-field rules, the ones no single validate_<field> can see.3

Writable nested serializers

A serializer can embed another. Reading is automatic: nest a serializer with many=True and the output includes the related objects. Writing is not automatic. Because a default create() does not know how to build the nested objects, you override create() (and update() if needed) to say how the nested data is saved:4

class AlbumSerializer(serializers.ModelSerializer):
    tracks = TrackSerializer(many=True)

    class Meta:
        model = Album
        fields = ["album_name", "artist", "tracks"]

    def create(self, validated_data):
        tracks_data = validated_data.pop("tracks")
        album = Album.objects.create(**validated_data)
        for track_data in tracks_data:
            Track.objects.create(album=album, **track_data)
        return album

Pull the nested data out of validated_data, create the parent, then create each child pointing at it. Explicit, because DRF will not guess your write semantics.4

Why this matters

ModelSerializer is the DRY payoff from Lesson 1 applied to the API boundary: describe the model once, and the serializer's fields, validators, and default save logic follow. The two validation hooks give you a clear place for every rule: one field goes in validate_<field>, many fields go in validate. And the nested-write rule is the one place DRF deliberately steps back: automatic reading, but explicit create()/update() for writing, because only you know how the related rows should be built.

Key line "ModelSerializer infers fields, validators, and create/update from the model. Validation runs field checks, then your validate_<field>(), then your cross-field validate(). Nested serializers read automatically but need an explicit create()/update() to write."
The trap Putting a cross-field rule in a validate_<field>() method. A field-level method only sees its own value, so it cannot compare two fields; that belongs in object-level validate(self, data). The second trap: expecting a nested serializer to save on its own. Reading nested data is automatic; writing it is not, until you override create()/update().

Recall, answer out loud before peeking:

① What three things does ModelSerializer generate for you from the model?

show answer

Serializer fields matching the model fields, validators derived from the model (e.g. unique_together), and default create() and update() implementations.

② A rule needs to check that end_date is after start_date. Which method, and why not the other?

show answer

Object-level validate(self, data), because it receives all field values and can compare them. A validate_<field>() method only sees its own field's value, so it cannot see the other date.

③ You nest TrackSerializer(many=True) inside an album serializer. Reading works; posting an album with tracks fails to save the tracks. Why, and what fixes it?

show answer

Nested writing is not automatic. Override create() (and update()) to pop the nested data out of validated_data and create the related objects explicitly.
