Django & DRF · Lesson 4

Where plain Django fights an API

Django was built to serve HTML pages to browsers, and it's good at that. Point it at building a JSON API for other programs instead and several of its defaults work against you. This lesson names those friction points, because each one is a problem DRF exists to solve. This is the "what problem does DRF solve" question, stated as a list.

The concept

A web page and an API are different jobs. A page sends HTML to a human's browser, driven by GET and POST from forms. An API sends and receives structured data (usually JSON) to and from other code, across the full set of verbs (GET, POST, PUT, PATCH, DELETE). Django's request and response objects, and its form machinery, are shaped for the first job. Use them for the second and you end up writing the same glue by hand in every view. DRF's own tutorial frames itself as closing exactly this gap.1

The friction points

1. request.POST doesn't understand JSON, PUT, or PATCH

Django's request.POST is built for HTML form submissions: it parses form-encoded bodies, and effectively only for POST requests. An API client sends a JSON body, and often on PUT or PATCH. DRF introduces request.data precisely because it is more useful for Web APIs than request.POST: it parses arbitrary content (JSON and other media types) and works for POST, PUT, and PATCH alike.2 Without that, a plain Django view has to read and parse the raw request body itself.

2. HttpResponse doesn't negotiate content types

A plain HttpResponse sends back whatever bytes you put in it. An API often needs to answer the same endpoint as JSON for a program and as something browsable for a human developer, chosen by the client's Accept header. That choice is content negotiation, and plain Django doesn't do it. DRF's Response takes unrendered data and uses content negotiation to decide the correct content type to return, then renders accordingly.3

3. Serialization is hand-rolled

Model instances and querysets are Python objects; JSON is text. Something has to convert between them, in both directions, and validate incoming data before it touches the database. In plain Django you write that conversion and validation yourself for every model. DRF provides serializers to turn model instances and querysets into native Python datatypes (then JSON) and to validate and deserialize incoming data back into objects.4 Lesson 5 covers them.

4. Status codes and API errors are manual

Correct APIs return meaningful HTTP status codes: 201 on create, 204 on delete, 400 on invalid input, 405 on the wrong verb, and a clean error when a body fails to parse. In plain Django you set and remember each of these by hand. DRF's view wrappers add handling for cases like 405 Method Not Allowed and ParseError automatically.5

None of this is hard once. It's that you rewrite it in every view, for every model, forever. That repetition is what a framework layer is supposed to remove.

Notice what is not on this list: verb-to-view mapping. Lesson 3 already solved that in core Django with the class-based View. The friction that remains is specifically about being an API (data in and out, negotiated, validated, with correct status), not about routing verbs. That's the precise seam DRF fills, and why it calls itself a toolkit for building Web APIs rather than a replacement for Django's request handling.

Key line "Django's defaults are shaped for HTML pages: request.POST can't read a JSON PUT body, HttpResponse doesn't negotiate content, serialization and status codes are hand-rolled. DRF exists to remove that per-view, per-model repetition, not to fix verb routing, which core Django already handled."
The trap Lumping the verb-mapping fix in with "what DRF solves." It isn't DRF's problem to solve; class-based View handled it (Lesson 3). DRF's contributions are the API concerns: parsing arbitrary bodies (request.data), content negotiation (Response), serialization, and automatic API errors. Keep the two piles separate or you'll credit DRF for Django's work.

Recall, answer out loud before peeking:

① Why is request.POST a poor fit for an API, and what does DRF offer instead?

show answer

request.POST parses form-encoded bodies and effectively only for POST. APIs send JSON, often on PUT/PATCH. DRF's request.data parses arbitrary media types across POST/PUT/PATCH.

② What does "content negotiation" mean, and which object performs it in DRF?

show answer

Choosing the response's content type based on what the client asked for (e.g. the Accept header). DRF's Response does it, taking unrendered data and rendering to the negotiated type. Plain HttpResponse doesn't negotiate.

③ Name one friction point that is not DRF's job, and say why.

show answer

Verb-to-view mapping. Core Django's class-based View/dispatch() already solved it (Lesson 3); DRF inherits that and adds the API-specific layer.
