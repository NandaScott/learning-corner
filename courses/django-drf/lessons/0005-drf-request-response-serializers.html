Django & DRF · Lesson 5

DRF's request, response, and serializer layer

Lesson 4 listed what plain Django makes you hand-roll for an API. This lesson is DRF's answer to each item: a richer Request, a negotiated Response, and serializers for the object↔JSON boundary, all delivered through two wrappers, @api_view and APIView, that sit on top of the verb dispatch from Lesson 3.

The concept

DRF gives you two ways to write an API view, matching Django's two view styles. For a function, the @api_view decorator; for a class, subclass APIView. Both wrappers do the same job: they make sure your code receives DRF's Request instead of Django's plain HttpRequest, they add the context a Response needs for content negotiation, and they handle API errors like 405 Method Not Allowed and ParseError for you.1 Inside that wrapper, you work with three upgraded objects.

The three upgrades

1. Request — parsing that fits an API

DRF's Request extends the regular HttpRequest with flexible parsing. Its core is request.data: the parsed request body, covering file and non-file input, working for POST, PUT, and PATCH, and handling JSON or other media types the same way you'd handle form data.2 This is the direct fix for friction point 1 from Lesson 4.

2. Response — one object, many rendered forms

DRF's Response is given unrendered data (plain Python) and defers the rendering. It runs content negotiation to pick the right content type for the client, then renders. By default the renderers are JSON and the browsable API, so the same endpoint answers a program with JSON and a developer's browser with an explorable HTML page.3

REST_FRAMEWORK default renderers:
    'rest_framework.renderers.JSONRenderer',
    'rest_framework.renderers.BrowsableAPIRenderer',

You return data once; the negotiated renderer decides the wire format. The browsable API is why you can click through a DRF endpoint in a browser.3

3. Serializers — the object/JSON boundary, with validation

A serializer converts both directions. Outbound, it turns a model instance (or a queryset, with many=True) into native Python datatypes that a renderer can emit as JSON:4

serializer = SnippetSerializer(snippet)          # one instance
serializer.data                                   # → native Python (then JSON)

serializer = SnippetSerializer(Snippet.objects.all(), many=True)   # a queryset
serializer.data

Outbound: object → .data → JSON.

Inbound, it takes incoming data, validates it, and exposes the clean result, which you can then save:5

serializer = CommentSerializer(data=request.data)
serializer.is_valid()             # validate
serializer.validated_data         # the clean, typed values
serializer.save()                 # persist (create/update the object)

Inbound: request.data → validate → validated_data → save. This replaces the hand-written parsing and validation from Lesson 4.

Putting it together

A function-based API view for a single object shows all three at once, and note the verb handling: it's still the request.method branch, because a function view branches. DRF's contribution here is the objects, not the routing:6

@api_view(["GET", "PUT", "DELETE"])
def snippet_detail(request, pk):
    try:
        snippet = Snippet.objects.get(pk=pk)
    except Snippet.DoesNotExist:
        return Response(status=status.HTTP_404_NOT_FOUND)

    if request.method == "GET":
        serializer = SnippetSerializer(snippet)
        return Response(serializer.data)

    elif request.method == "PUT":
        serializer = SnippetSerializer(snippet, data=request.data)
        if serializer.is_valid():
            serializer.save()
            return Response(serializer.data)
        return Response(serializer.errors, status=status.HTTP_400_BAD_REQUEST)

    elif request.method == "DELETE":
        snippet.delete()
        return Response(status=status.HTTP_204_NO_CONTENT)

@api_view also enforces the method list: a verb not in ["GET", "PUT", "DELETE"] gets an automatic 405. By default a bare @api_view accepts only GET.6

Write the same thing as a class and the branch disappears again, exactly as in Lesson 3, because APIView subclasses Django's View:

class SnippetDetail(APIView):
    def get(self, request, pk, format=None):
        ...
        return Response(serializer.data)
    def put(self, request, pk, format=None):
        ...
    def delete(self, request, pk, format=None):
        ...

Same get()/put()/delete() dispatch as core Django, now carrying DRF's Request and Response.

Why this is the whole DRF value, minus routing

Line the three upgrades against Lesson 4's list and they cancel it: request.data kills the manual body parsing, Response kills the manual content negotiation, serializers kill the hand-written conversion and validation, and the wrappers kill the manual 405/parse-error handling. What DRF did not touch is the verb-to-method dispatch, because APIView inherits it from Django's View untouched. DRF is the API layer bolted onto Django's existing view machinery, not a rewrite of it. The one routing improvement DRF does add, turning verbs into named actions and generating the URLconf, is Lesson 6.

Key line "DRF wraps your view (@api_view for functions, APIView for classes) so it gets a parsing Request (request.data), a negotiated Response, and serializers for object↔JSON with validation, plus automatic 405/parse errors. The verb dispatch it just inherits from Django's View."
The trap Thinking DRF replaced Django's verb dispatch with something new. The function example still branches on request.method, and the class example still uses get()/put()/delete(): the same mechanism from Lesson 3. DRF changed what flows through the view (Request, Response, serializers, auto-errors), not how the verb is routed. The routing change comes later, with viewsets and routers.

Recall, answer out loud before peeking:

① What three things does an @api_view/APIView wrapper guarantee your code, per the docs?

show answer

A DRF Request instance (not plain HttpRequest), the context a Response needs for content negotiation, and automatic handling of API errors such as 405 and ParseError.

② Trace a serializer both directions in one line each.

show answer

Outbound: Serializer(instance).data → native Python → JSON. Inbound: Serializer(data=request.data) → is_valid() → validated_data → save().

③ In the function-based snippet_detail, how are the verbs told apart, and how in the APIView version?

show answer

Function version: if request.method == branching (a function branches). Class version: get()/put()/delete() methods dispatched by the inherited Django dispatch().

④ Which Lesson-4 friction point does DRF not address, and why not?

show answer

Verb routing. It was never DRF's to fix; APIView subclasses Django's View and inherits dispatch(). DRF adds the API layer (data/response/serializer/errors) on top.
