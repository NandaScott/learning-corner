The ORM and the QuerySet

Lesson 1 named the ORM as one of Django's bundled parts and moved on. This lesson opens it up, because the object you query with, the QuerySet, has behavior that surprises people: it is lazy, it caches, and it will quietly fire one database query per row if you are not watching. Understanding when a QuerySet touches the database is the difference between a fast endpoint and a slow one.

The concept

A model class maps to a database table, and each model has a manager, reached as Model.objects, that is the entry point for queries. Calling something like Entry.objects.filter(...) gives you back a QuerySet: a description of a query, not its results. The results do not exist until the QuerySet is evaluated. That one property, laziness, drives everything else in this lesson.1

The steps

  1. build a QuerySet      Entry.objects.filter(...)   → no DB query yet
  2. refine it (chain)     .filter(...).exclude(...)   → still no query
  3. evaluate it           iterate / list() / print    → ONE query runs
  4. reuse the same var    results are cached           → no new query
  5. touch a related row   entry.blog                   → a NEW query, per row

Steps 1 and 2 are free. Step 3 is the database hit. Step 5 is where the surprise cost hides.

Steps 1-2 - building and chaining are free

Creating or refining a QuerySet triggers no database activity. You can stack filters, and Django folds them into a single query that runs only at evaluation:1

q = Entry.objects.filter(headline__startswith="What")   # no query
q = q.filter(pub_date__lte=datetime.date.today())        # no query
q = q.exclude(body_text__icontains="food")               # no query
print(q)   # NOW one query runs, with all three conditions

Three refinements, one database hit. The chain is composed in Python and sent to the database once.1

Step 3 - evaluation is the database hit

The database is queried only when the QuerySet is evaluated: iterating over it, calling list() on it, taking its len(), testing it for truth, or printing it.1 Until one of those happens, the query has not run.

Step 4 - a QuerySet caches its results

Once a QuerySet is fully evaluated, it stores the results in an internal cache, and later uses of the same QuerySet object reuse that cache instead of re-querying.2 The practical rule: assign a QuerySet to a variable and reuse the variable. Calling Model.objects.all() twice is two separate QuerySets and two queries; iterating one saved variable twice is one query.2

One sharp edge: slicing or indexing a QuerySet that has not been fully evaluated queries the database each time, because a partial fetch is not cached the way a full evaluation is.2

Step 5 - related objects are lazy too, and that is the trap

Accessing a related object across a foreign key is itself a query. Fetch one Entry, then read entry.blog, and that attribute access hits the database a second time to load the blog:3

e = Entry.objects.get(id=5)   # query 1
b = e.blog                     # query 2 (loads the related Blog)

Fine for one object. Now put it in a loop.

for e in Entry.objects.all():   # 1 query for the entries
    print(e.blog.name)          # + 1 query PER entry for its blog

  100 entries → 1 + 100 = 101 queries.   This is the N+1 problem.

One query to get the list, then N more, one per row, to follow the relation. The count scales with your data.

The fix: fetch the relations up front

Two methods pull related data in advance. select_related follows foreign-key and one-to-one links by adding a SQL join, so the related rows arrive in the same query and later attribute access does not re-query:3

e = Entry.objects.select_related("blog").get(id=5)   # one query, with a join
b = e.blog   # no query; already loaded

select_related: for the "one" side (ForeignKey, OneToOne). One query, joined.3

prefetch_related handles many-to-many and reverse relations, where a join would not fit. It runs a separate query for the related set and joins the two in Python:3

Restaurant.objects.select_related("best_pizza") \
                  .prefetch_related("best_pizza__toppings")

prefetch_related: for the "many" side (ManyToMany, reverse FK). A second query, joined in Python. The two combine, and __ traverses deeper.3

Why this matters

The QuerySet's laziness is what lets you build queries up in pieces without paying for each step, and its caching rewards reusing one variable. But the same laziness means every unfollowed relation is a query waiting to fire, and in a loop that becomes N+1. The tools to defeat it, select_related for the one-side and prefetch_related for the many-side, are the two names worth memorizing from this lesson. They decide query count, and query count decides latency.

Key line "A QuerySet is a lazy description of a query: chaining is free, evaluation (iterate, list, len, print) is the one database hit, and results are cached per variable. Following a relation is another query, so relations in a loop are N+1, fixed by select_related (one-side) and prefetch_related (many-side)."
The trap Assuming a query runs where you wrote the filter(). It runs where you evaluate, which may be much later, or twice if you call .all() in two places instead of reusing a variable. And the query you can see (filter) is rarely the expensive one; the hidden queries are the per-row relation lookups a serializer or template triggers while iterating.

Recall, answer out loud before peeking:

① You write three chained .filter()/.exclude() calls and never iterate the result. How many queries ran?

show answer

Zero. Building and refining a QuerySet is lazy; nothing hits the database until the QuerySet is evaluated (iterated, list(), len(), truth-tested, or printed).

② A loop over 50 objects reads a foreign-key relation on each. How many queries, and how do you cut it down?

show answer

1 + 50 = 51 (the N+1 problem). Add select_related("<fk>") to the queryset so the related rows come back in the first query via a join, cutting it to 1.

③ When do you reach for prefetch_related instead of select_related?

show answer

For many-to-many and reverse foreign-key relations, where a SQL join does not fit. prefetch_related runs a second query for the related set and joins it in Python. select_related is for ForeignKey/OneToOne (the one-side), done as a join.
