Middleware and the request pipeline

Lesson 2 drew the request cycle as URL to view to response. That skipped a layer. Before a request reaches any view, it passes through a stack of middleware, and the response passes back out through the same stack in reverse. This lesson is that outer layer: what middleware is, the order it runs in, and how it wraps everything you have built so far.

The concept

Middleware is a framework of hooks into Django's request and response processing: a light, low-level plugin system for globally altering Django's input or output.1 It is the code that runs for every request, around the view, regardless of which view. Session loading, authentication, CSRF protection, and security headers are all middleware. The view from Lesson 2 sits at the center; middleware is the wrapping.

The steps

1. The stack is an onion

Middleware is listed in the MIDDLEWARE setting, and Django applies it top-down during the request phase and in reverse during the response phase. Each layer wraps the view like an onion. A request travels inward through every layer to the view; the response travels back outward through the same layers in reverse:2

flowchart LR
  subgraph REQ["request phase: top-down through MIDDLEWARE"]
    direction TB
    r0["request"] --> r1["Security"] --> r2["Session"] --> r3["Auth"] --> r4["Csrf"] --> rv["[ VIEW ]"]
  end
  subgraph RESP["response phase: bottom-up (reverse)"]
    direction TB
    pv["[ VIEW ]"] --> p4["Csrf"] --> p3["Auth"] --> p2["Session"] --> p1["Security"] --> p0["response"]
  end
  rv --> pv

In through the list, out through it backward. The view is the innermost point.2

2. A middleware is a callable that wraps the next one

The shape is small. A middleware factory takes get_response (the next step in the chain, either the next middleware or the view) and returns a callable that runs per request: do work before, call get_response(request), do work after, return the response:3

def simple_middleware(get_response):
    # one-time setup, at server start

    def middleware(request):
        # BEFORE: runs on the way in, before the view
        response = get_response(request)   # hand off to the next layer / view
        # AFTER: runs on the way out, after the view
        return response

    return middleware

get_response is the rest of the onion. Calling it descends one layer; everything before the call is the request phase, everything after is the response phase.3

The factory runs once, at server startup (the setup line); the inner function runs once per request.3

3. A layer can short-circuit

A middleware does not have to call get_response. If a layer returns a response on its own, without calling the next step, the request never reaches the inner layers or the view, and only the layers that already ran on the way in will run on the way out:2

flowchart LR
  r["request"] --> s["Security"] --> a["Auth"]
  a --> x["✗ returns 403 here
view and inner layers never run,
response goes back out through Security only"]

This is how a middleware blocks a request early: return a response instead of calling get_response.2

4. Order is significant

Because each layer wraps the next, the order in MIDDLEWARE matters. The default stack encodes real dependencies:4

MIDDLEWARE = [
    "django.middleware.security.SecurityMiddleware",
    "django.contrib.sessions.middleware.SessionMiddleware",
    "django.middleware.common.CommonMiddleware",
    "django.middleware.csrf.CsrfViewMiddleware",
    "django.contrib.auth.middleware.AuthenticationMiddleware",
    "django.contrib.messages.middleware.MessageMiddleware",
    "django.middleware.clickjacking.XFrameOptionsMiddleware",
]

Session-dependent middleware (auth, messages) must come after SessionMiddleware so the session is loaded first; security sits near the top so it runs early. Reorder carelessly and things break.4

5. Optional per-stage hooks

Beyond the before/after wrapping, a middleware class may define extra hooks: process_view (just before the view runs), process_exception (when a view raises), and process_template_response (when the response has a render() method). process_exception runs only for exceptions raised in the view, in reverse order, and if one returns a response the layers above it are skipped.5

Why this matters, and how it meets the rest of the course

Middleware is the outermost ring of the request lifecycle. Lesson 2's URL-to-view-to-response happens inside it: routing and the view run only after the request has passed inward through every middleware layer. That placement explains a detail from Lesson 11. Django's own AuthenticationMiddleware sets request.user during the request phase, from the session, for the whole site. DRF's per-view authentication (Lesson 11) runs later, inside the view, and can set a different request.user, for example from a token. Two auth layers at two depths: the middleware ring on the way in, the view's own gate at the center. Seeing the onion is what makes that ordering make sense.

Key line "Middleware is the onion around the view: the request goes top-down through the MIDDLEWARE stack, the view runs at the center, the response comes back bottom-up. Each layer wraps the next via get_response, and a layer that returns a response without calling it short-circuits the rest."
The trap Picturing middleware as a flat list that runs once before the view. It runs twice, in opposite orders: top-down on the request, bottom-up on the response, because each layer wraps the next. That is also why order matters and why a short-circuit only unwinds through the layers that had already run inward, not the whole list.

Recall, answer out loud before peeking:

① In what order does middleware run on the request phase versus the response phase, and where is the view?

show answer

Top-down through MIDDLEWARE on the request, bottom-up (reverse) on the response. The view runs at the center, after the request has passed inward through every layer.

② What is get_response, and what happens if a middleware does not call it?

show answer

It is the next step in the chain (the next middleware, or the view). If a middleware returns a response without calling get_response, it short-circuits: inner layers and the view never run, and only the already-run outer layers process the response.

③ Why must AuthenticationMiddleware come after SessionMiddleware in the list?

show answer

Because each layer wraps the next and runs in order; authentication depends on the session being loaded first, so SessionMiddleware must run earlier (be higher in the list).
