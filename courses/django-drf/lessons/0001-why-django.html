Django & DRF · Lesson 1

Why Django

Before any code, the plain question: what is Django a solution to? The answer is that building a database-backed website means solving the same dozen problems every time, and Django ships decided answers to all of them in one box. This lesson is what's in the box, and the principles that shaped it.

The concept

Every content-driven web app needs the same machinery: a way to describe data and talk to a database, a way to turn a URL into code, a way to render pages, a way to handle forms, a login system, and an interface for staff to edit records. Write those from scratch and most of the work is plumbing, not the product. Django is a high-level Python web framework that supplies that plumbing so a small team can move fast: the docs describe it as being for "perfectionists with deadlines," emphasizing rapid development and clean, pragmatic design.1

"Batteries included" is the usual shorthand. Django bundles the common parts rather than leaving you to assemble them, and the parts are built to work together.

What's in the box

The overview page walks the pieces in the order you'd build a site.2 A short tour of the four that matter for this course:

1. Models — data described once, in Python

A model is a Python class that defines a table's shape. Django reads it to talk to the database for you, so you write queries in Python instead of SQL, and the same class definition is the one source for that data's structure.2 This is the object-relational mapper (ORM).

2. URLconf — a URL becomes a function call

A URL configuration maps request paths to the code that answers them, capturing pieces of the path as arguments along the way:2

urlpatterns = [
    path("articles/<int:year>/", views.year_archive),
    path("articles/<int:year>/<int:month>/", views.month_archive),
]

A request for /articles/2026/ calls year_archive(request, year=2026). Lesson 2 is this line in detail.

3. Templates — the HTML, kept out of the Python

Templates describe how a page looks, separately from the code that fetches the data. The template system is deliberately independent of the rest so the presentation layer and the logic layer don't reach into each other.3

4. The admin — a staff interface, generated for free

Register a model and Django reads its metadata to build a working add/change/delete interface for trusted staff, no custom backend screens required.24 One line:

from django.contrib import admin
from . import models

admin.site.register(models.Article)

The admin is an internal management tool for trusted users, not a public front end.4

The principles under it

The pieces feel consistent because a few stated philosophies shaped all of them.3

DRY: don't repeat yourself. Every distinct piece of data or logic should live in exactly one place; Django tries to deduce as much as it can from as little input as possible.3 Describe a model once and the ORM, the admin, and forms all read from that single definition.

Loose coupling, tight cohesion. The layers stay independent: the template system, the database layer, and the view system each work without knowing about the others.3 You can swap or reason about one without dragging the rest along.

Explicit over implicit; less code. Django prefers explicit behavior over "magic," using it only where the convenience is large and stays understandable, and it leans on Python's introspection to cut boilerplate so you write less.3

MTV: the same idea as MVC, renamed

You'll see Django called an "MTV" framework: Model, Template, View. It's close to the classic Model-View-Controller pattern, with two words moved. What MVC calls the controller (the code that decides what happens), Django calls the view. What MVC calls the view (the presentation), Django calls the template.5

  classic MVC          Django (MTV)
  ───────────          ────────────
  Model         →      Model        (the data)
  Controller    →      View         (the logic that answers a request)
  View          →      Template     (the HTML)

Hold onto one word: in Django, a view is the logic that answers a request. That word carries the next five lessons.

Key line "Django is a box of decided answers to the problems every database-backed site shares (models, URL routing, templates, an auto admin), held together by DRY and loose coupling. And in Django, 'view' means the request-answering logic, not the HTML."
The trap Reading "view" as the visual page. In Django a view is the controller-side code that receives a request and returns a response; the visible HTML is the template. Getting this backwards makes every later lesson (and the whole verb-to-view question) read wrong, because the verbs map onto the view, which is logic, not markup.
