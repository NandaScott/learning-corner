Django & DRF · Lesson 2

From URL to response

Lesson 1 established that a Django "view" is the request-answering logic. This lesson is the mechanism around it: how an incoming URL gets matched to a view, what the view receives, and what it must hand back. Nail this cycle and the verb-mapping problem in Lesson 3 becomes obvious.

The concept

Django's request handling is a short contract. When a page is requested, Django builds an HttpRequest object holding the request's metadata and passes it to the right view. Each view is responsible for returning an HttpResponse object.1 Everything else (routing, the view, the template) is machinery in service of that one in-and-out.

So a view, precisely, is a callable that takes an HttpRequest and returns an HttpResponse. Nothing more is required to be a view.

The steps

  1. request arrives:  GET /articles/2026/
        │
  2. URL resolver scans urlpatterns top-to-bottom for a match
        │
  3. match found → Django calls the view, passing the
     HttpRequest plus any captured path pieces as kwargs
        │
  4. view runs its logic (query models, pick a template…)
        │
  5. view returns an HttpResponse; Django sends it to the client

Two objects define the whole cycle: HttpRequest in at step 3, HttpResponse out at step 5.

Step 2 — the URLconf matches the path

A URLconf is a list of path() entries. Each maps a route string to a view, and the route can capture parts of the URL using angle brackets with a converter:2

from django.urls import path
from . import views

urlpatterns = [
    path("index/", views.index, name="main-view"),
    path("articles/<int:year>/", views.year_archive, name="year"),
]

<int:year> captures a segment, converts it to an int, and passes it on as the year keyword argument. The name lets other code refer to this route without hardcoding the URL.2

Step 3 — Django calls the view

On a match, Django invokes the view with an HttpRequest object and any captured route values as keyword arguments.2 The view slot in path() takes a view function directly, or the result of as_view() for a class-based view (Lesson 3), or an include() of another URLconf.2

Step 4–5 — the view runs and returns a response

The simplest possible view skips models and templates entirely and returns a response by hand:1

from django.http import HttpResponse

def year_archive(request, year):
    return HttpResponse(f"Articles from {year}")

A plain function. It takes the request (plus the captured year) and returns an HttpResponse. That is a complete, valid Django view.

Why this cycle matters

Two consequences carry forward. First, the view is the one place the application's logic runs per request, which is why Lesson 1 insisted a "view" is logic, not markup. Second, and this is the setup for the next lesson: notice what the routing matched on. The URL resolver matched on the path (/articles/2026/). It did not look at the HTTP method (GET, POST, PUT, DELETE). The path picks the view; the method is just a field sitting on the HttpRequest the view receives.

That single fact is the root of the verb-mapping question. One path routes to one view, no matter the verb, so if a single URL needs to behave differently for GET versus POST, that difference has to be sorted out inside the view. Lesson 3 is what that looks like, and how Django lets you stop doing it by hand.

Key line "A Django view is a callable that takes an HttpRequest and returns an HttpResponse. The URLconf routes on the path alone, so all HTTP methods for one URL arrive at the same view."
The trap Assuming routing considers the HTTP method. It doesn't. path() matches the URL string; the verb rides in on the request object. That's exactly why a plain view has to branch on request.method to serve the same URL differently per verb, which is the awkwardness Lesson 3 unpacks.
