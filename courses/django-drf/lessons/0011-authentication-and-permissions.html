Django & DRF · Lesson 11

Authentication and permissions

Every view from the last three lessons runs behind a gate. Before your get() or list() executes, DRF answers two questions in order: who is this request (authentication), and are they allowed to do this (permission). This lesson is that gate, its fixed order, and the classes that fill each slot.

The concept

Two different questions, often confused. Authentication identifies the request: it decides who is calling and attaches that identity as request.user. Permission (authorization) decides whether that identity may proceed. DRF runs them in a fixed sequence, and authentication always goes first: it runs at the very start of the view, before the permission and throttling checks, and before any of your code.1

  request
    │
  1. authentication   → sets request.user, request.auth   (who?)
    │
  2. permission       → allowed? if not, raise            (may they?)
    │
  3. throttling       → under the rate limit? if not, raise (how often?)
    │
  4. your view / action runs

A fixed pipeline. Each stage can stop the request before your code runs. Authentication first, because permission needs to know who the user is.1

The steps

1. Authentication sets request.user

You list authentication schemes in authentication_classes on an APIView (or via decorator on a function view). Each scheme tries to identify the request; the first that succeeds sets request.user (the identity) and request.auth (any extra credential, such as a token):2

class ExampleView(APIView):
    authentication_classes = [SessionAuthentication, BasicAuthentication]
    permission_classes = [IsAuthenticated]

    def get(self, request, format=None):
        return Response({"user": str(request.user)})   # the identity

SessionAuthentication reuses Django's login session; BasicAuthentication reads HTTP Basic credentials. Whoever they identify becomes request.user.2

Token authentication is the common choice for non-browser clients. The client sends Authorization: Token <key>; on success request.user is a Django User and request.auth is the Token. A request that fails authentication and is denied gets a 401 Unauthorized with a WWW-Authenticate header:3

Authorization: Token 9944b09199c62bcf9418ad846dd0e4bbdfc6ee4b

Header format for TokenAuthentication. The literal word Token, a space, then the key.3

2. Permission decides allowed or not

Permissions are a list of classes checked in turn before the view's main logic. If any check fails, DRF raises and the view body never runs, returning 403 Forbidden or 401 Unauthorized depending on whether the request was authenticated:4

  authenticated but not allowed   → 403 Forbidden
  not authenticated at all        → 401 Unauthorized (with WWW-Authenticate)

The status code tells the client which problem it is: "I don't know you" (401) versus "I know you, and no" (403).34

The built-in permission classes cover the usual cases:5

  AllowAny                   everyone, authenticated or not
  IsAuthenticated            only signed-in users
  IsAdminUser                only users with is_staff = True
  IsAuthenticatedOrReadOnly  anyone may read (GET/HEAD/OPTIONS); writes need sign-in
  DjangoModelPermissions     ties to Django's add/change/delete model permissions

Set them with permission_classes = [IsAuthenticated]. They compose: all must pass.5

3. Two levels of permission check

A permission class can decide at two granularities. has_permission judges the whole request (may this user reach this view at all). has_object_permission judges a specific object (may this user act on this row). Object-level checks are where per-owner rules live, and they use the object from the queryset in Lesson 10. The classic custom permission reads any request but restricts writes to the owner:6

class IsOwnerOrReadOnly(permissions.BasePermission):
    def has_object_permission(self, request, view, obj):
        if request.method in permissions.SAFE_METHODS:   # GET, HEAD, OPTIONS
            return True
        return obj.owner == request.user

SAFE_METHODS are the read-only verbs. Reads pass for anyone; writes require the requesting user to own the object.6

4. Throttling caps the rate

After permission, throttling limits how often a client may call. UserRateThrottle keys on the user id (falling back to client IP for anonymous requests) and enforces a rate like "60/min", set per-scope in settings.7 It is the last gate before the view runs.

Why this matters

The order is the point. Authentication must run first because permission cannot decide "may this user" without a user, and request.user is precisely what authentication produces. Permissions then compose as an all-must-pass list, at either the request level (has_permission) or the object level (has_object_permission). The 401-versus-403 split falls straight out of the order: no identity yet is 401, known-but-refused is 403. Throttling sits last, capping rate once identity and permission are settled. Set these as class attributes and the same gate protects an APIView, a generic view, or a ModelViewSet alike.

Key line "The gate runs in a fixed order: authentication (sets request.user) then permission (allowed?) then throttling (how often?), before your view. Permissions are an all-pass list, checked at request level (has_permission) or object level (has_object_permission); no identity is 401, known-but-refused is 403."
The trap Conflating authentication with permission, and the two status codes with it. Authentication only answers "who," and it never rejects on its own for being unprivileged; permission answers "may they." A signed-in user hitting a resource they do not own gets 403 (identity known, refused), not 401 (no identity). And object-level rules only fire through has_object_permission on a specific object, not has_permission.

Recall, answer out loud before peeking:

① In what order do authentication, permission, and throttling run, and why must authentication be first?

show answer

Authentication, then permission, then throttling, all before the view. Authentication is first because it sets request.user, and permission needs to know who the user is to decide whether they are allowed.

② A logged-in user tries to edit a record they do not own and is refused. What status code, and which permission method enforced it?

show answer

403 Forbidden (the identity is known, the action is refused). Enforced by has_object_permission, comparing obj.owner to request.user for non-SAFE_METHODS.

③ What do request.user and request.auth hold after successful TokenAuthentication?

show answer

request.user is the Django User instance; request.auth is the Token instance. The client sent Authorization: Token <key>.
