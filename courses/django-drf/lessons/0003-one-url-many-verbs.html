Django & DRF · Lesson 3

One URL, many verbs

This is the lesson the whole course was aimed at. Lesson 2 showed that routing matches the path and ignores the HTTP method, so every verb for one URL lands in the same view. Here is the awkwardness that creates, and the fix Django ships for it, a fix that DRF later builds on rather than replaces.

The concept

A single resource, say one article at /articles/42/, wants to answer several HTTP methods: GET to read it, PUT to replace it, DELETE to remove it. All three are the same URL, so all three route to the same view (Lesson 2). The view has to tell them apart somehow. There are two ways to do that in Django, and the difference between them is the point.

Rung 1 — the function-based view branches on the method

A function-based view receives the request and inspects request.method, branching to the right block:1

from django.http import HttpResponse

def my_view(request):
    if request.method == "GET":
        # ...read logic...
        return HttpResponse("result")
    # and, in a real view, elif for POST / PUT / DELETE …

One function, one big conditional. Add verbs and the function grows a longer if/elif ladder, all sharing one scope.

This works, and for one or two methods it is fine. The awkwardness shows up as it grows: the handlers for unrelated verbs are crammed into one function, sharing local variables and one indentation level; you have to remember to reject unsupported methods yourself; and there is no natural seam to reuse one verb's behavior without dragging the others along. This is the "jank" the framework's own docs implicitly call out by offering the alternative next.

Rung 2 — the class-based view maps each verb to a method

Django's View class lets you respond to different HTTP methods with distinct instance methods instead of branching inside one function. The same behavior as above becomes:1

from django.http import HttpResponse
from django.views import View

class MyView(View):
    def get(self, request):
        # ...read logic...
        return HttpResponse("result")

    def post(self, request):
        # ...create logic...
        return HttpResponse("created")

The HTTP verb is the method name. GET runs get(), POST runs post(). No request.method check anywhere in your code.1

The docs put it plainly: class-based views let you respond to different HTTP request methods using distinct class instance methods, replacing the need for conditional branching within a single function, which keeps the logic for each request type separate.1

How the verb reaches the method: as_view() and dispatch()

The routing side barely changes. In the URLconf you write MyView.as_view() where a function view would go. as_view() is a class method that bridges the URL resolver and the class: it returns a callable that, per request, instantiates the class, initializes it via setup(), and calls dispatch(). dispatch() looks at the request's HTTP method and routes to the handler of the same name.2

The request.method check didn't vanish. It moved out of your view and into the framework's dispatch(), done once, correctly, for everyone.

What happens for a method you didn't write

The base View knows the standard verbs. Its default http_method_names is:3

["get", "post", "put", "patch", "delete", "head", "options", "trace"]

The verbs dispatch() is willing to route.

If a request uses a method in that list but your class has no matching handler (say a PUT arrives and you only defined get), dispatch() calls http_method_not_allowed(), which returns an HttpResponseNotAllowed, an HTTP 405, carrying the list of methods you actually support.3 You get correct method-rejection for free, the thing you had to remember to do by hand in the function-based version.

Why this matters, and where DRF comes in

Two things to carry out of this lesson. First, the class-based View turns "branch on the verb" into "name a method after the verb," and hands the branching, plus 405 handling, to dispatch(). That is Django solving its own verb-mapping awkwardness, in core Django, with no third-party help.

Second, and this is the hinge of the course: DRF does not invent verb-to-method mapping. DRF's APIView is a subclass of this very View, so it inherits as_view(), dispatch(), and the get()/post()/put()/delete() convention unchanged. What DRF changes is what flows through that dispatch (the request and response objects, content negotiation, serialization, error handling) and, later, how routing itself is generated. Lessons 4 through 6 are that story. The verb mapping you just learned is the floor they all stand on.

Key line "Function views branch on request.method; Django's class-based View names a method after each verb and lets dispatch() do the routing, with a free 405 for unsupported verbs. DRF's APIView subclasses that same View: it inherits the fix, it doesn't invent it."
The trap Believing the request.method check disappears with class-based views. It doesn't; it relocates. dispatch() still reads request.method once, then calls the like-named handler. The win isn't that the check is gone, it's that it's written once in the framework instead of by hand in every view. Miss this and you'll misexplain what DRF is doing on top.

Recall, answer out loud before peeking:

① In a function-based view, how do you serve GET and POST differently on the same URL? Name one downside as it scales.

show answer

Branch on request.method with if/elif inside the one function. Downsides: unrelated verb logic shares one scope, you must reject unsupported methods yourself, and there's no clean seam to reuse one verb's behavior.

② In a class-based View, what runs a GET request, and what component routed it there?

show answer

The get() method runs it. dispatch() (reached via as_view()) read request.method and called the like-named handler.

③ A PUT hits a class-based view that only defines get(). What does the client get, and from which method?

show answer

A 405, as an HttpResponseNotAllowed listing the supported methods, produced by http_method_not_allowed() (called by dispatch() because PUT is a known verb with no handler defined).

④ Does DRF invent the verb-to-method mapping? Explain.

show answer

No. DRF's APIView subclasses Django's View and inherits as_view()/dispatch()/get()+post(). DRF adds richer request/response objects and negotiation on top of that inherited dispatch.
