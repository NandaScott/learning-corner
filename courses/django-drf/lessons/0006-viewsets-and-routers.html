ViewSets and routers

This is the one routing improvement DRF adds beyond what Django's class-based views already gave you. It lifts the verb mapping up a level: from "verb → method" to "verb → named action," and then lets a router generate the whole URLconf from a single viewset. It's the payoff of the three-rung story the course has been building.

The concept

Lesson 3 mapped an HTTP verb to a like-named method (get, post). That's fine for one URL. But a typical resource spans two URLs with a predictable set of behaviors: a collection (/snippets/) and a member (/snippets/42/), across list, create, retrieve, update, and delete. Writing that as separate APIView classes means repeating the same wiring for every model. A ViewSet collapses the related behaviors into one class, named by action rather than by HTTP verb, and a router generates the URL patterns for it.1

The steps

1. A ViewSet names actions, not verbs

Instead of get() and post(), a viewset defines the standard CRUD actions. The default routers know this exact set:1

class UserViewSet(viewsets.ViewSet):
    def list(self, request):            ...   # collection: many
    def create(self, request):          ...   # collection: add one
    def retrieve(self, request, pk):    ...   # member: one
    def update(self, request, pk):      ...   # member: replace
    def partial_update(self, request, pk): ... # member: patch
    def destroy(self, request, pk):     ...   # member: delete

These action names (list, create, retrieve, update, partial_update, destroy) are the standard set routers provide routes for.1

2. The verb→action map is data

The link between HTTP verbs and these actions is an explicit dictionary. You can even bind it by hand, which is the clearest way to see what a router automates:2

snippet_list = SnippetViewSet.as_view({
    "get": "list",
    "post": "create",
})
snippet_detail = SnippetViewSet.as_view({
    "get": "retrieve",
    "put": "update",
    "patch": "partial_update",
    "delete": "destroy",
})

Same as_view() from Lesson 3, but now it takes a map. GET on the collection runs list; GET on a member runs retrieve. The routing is a value you can read, not a set of method names.2

  Rung 1 (L3): verb  →  if request.method == "GET"          (you branch)
  Rung 2 (L3): verb  →  get()                               (Django dispatch)
  Rung 3 (L6): verb  →  {"get": "list"}  →  list()          (verb→action map)

The whole course in three lines. Each rung moves the verb-to-code decision further out of your hands and into declarable structure.

3. A router generates the URLconf

You rarely write that map yourself. You register the viewset with a router, and the router produces the URL patterns for all the standard actions across the collection and member URLs:3

from rest_framework.routers import DefaultRouter

router = DefaultRouter()
router.register(r"snippets", SnippetViewSet, basename="snippet")

urlpatterns = router.urls   # /snippets/ and /snippets/<pk>/ , all verbs wired

One register() call replaces the two as_view({...}) blocks above and every path() for them. The router builds the URLconf from the viewset.3

4. Extra actions with @action

For behavior outside the standard six, the @action decorator marks a method as an extra route, and the router picks it up too. You declare the verb(s) and whether it's a detail (member) or collection route:4

from rest_framework.decorators import action

class UserViewSet(ModelViewSet):
    @action(methods=["post"], detail=True)
    def set_password(self, request, pk=None):
        ...            # POST /users/<pk>/set_password/

The verb→action mapping extends cleanly to custom behavior, still as declared data.4

Why this is the top of the ladder

The course's whole arc, in one view: core Django made you branch on the verb, then let you name a method after it (Lesson 3). DRF kept that dispatch and enriched the objects moving through it (Lesson 5). ViewSets take the last step: describe a resource's behaviors as named actions, hand the verb→action map to a router, and let it generate the routes. The verb mapping that started as a hand-written if request.method == ends as a dictionary you often don't even write. That progression, from branch to method to routed action, is the precise answer to "the jankiness in how Django maps verbs to a view, and how DRF cleans it up."

Key line "A ViewSet names a resource's behaviors as actions (list, retrieve, create…); as_view({\"get\": \"list\"}) maps verbs to actions as data; a router generates the URLconf from it. Verb-to-code goes from a hand-written branch to a declared map."
The trap Treating actions as if they were HTTP verbs. retrieve and list are both GET, on different URLs (member vs collection); update is PUT, partial_update is PATCH, destroy is DELETE. The action name describes the behavior; the verb→action map (written by you, or generated by the router) is what ties each to an actual HTTP method and URL.

Recall, answer out loud before peeking:

① List the six standard viewset actions and, for each, the HTTP verb and whether it's collection or member.

show answer

list (GET, collection), create (POST, collection), retrieve (GET, member), update (PUT, member), partial_update (PATCH, member), destroy (DELETE, member).

② What does SnippetViewSet.as_view({"get": "list", "post": "create"}) express, and how does it differ from a plain APIView's as_view()?

show answer

It maps HTTP verbs to viewset actions as data: GET→list, POST→create. A plain APIView.as_view() takes no map; it dispatches straight to like-named get()/post() methods.

③ What does a router do, in one sentence?

show answer

It generates the URL patterns (the URLconf) for a registered viewset's standard actions across its collection and member URLs, so you don't hand-write the verb→action maps or path() entries.

④ Recite the three rungs of verb mapping this course covered.

show answer

(1) Function view branches on request.method. (2) Class-based View names a method per verb, dispatched by dispatch(). (3) ViewSet + router map verbs to named actions as data and generate the routes.
