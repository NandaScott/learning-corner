Correctness and visibility are two axes

Structural enforcement is invisible at the call site: read a task's code and the protection is nowhere on the page. That is a real cost, and it is a discoverability cost, not a correctness one. Design arguments stall on the two being treated as one.

The concept

Lesson 6 moved an invariant from memory into structure using middleware and a task base class. Both enforce correctly. Both are also invisible where the code runs: open the task, read every line, and nothing mentions the search path. The guarantee is real and it is somewhere else.

The objection "I cannot see the protection happening" is legitimate and it is about a different property. Two designs can both correctly enforce an invariant and still reasonably disagree about how visible the enforcement should be. Holding those apart is the single most useful move available in a stalled design discussion.

Step 1 — Two questions, asked separately

The correctness question: can the invariant be violated by code someone writes later? This has a yes or no answer, and Lesson 1's one question is how it gets asked.

The visibility question: can a reader of this code tell that the invariant is being enforced? This is a matter of degree, it trades against other things, and no amount of it changes the answer to the first question.

Both matter. They are not ranked against each other in general, only in specific cases, and mixing them produces the two symmetric mistakes in the next step.

Step 2 — The two symmetric mistakes

Treating invisibility as incorrectness: "the task does not reset the search path, so the task is wrong." The task is not wrong. It is protected by something the reader cannot see, and the complaint is that they cannot see it. Acting on this mistake usually means adding a redundant per-call-site reset, which restores the convention this design existed to remove, and now the codebase has both.

Treating structural correctness as the end of the conversation: "it cannot be violated, so there is nothing to discuss." A guarantee nobody can find is a guarantee people work around. The reader who cannot see why a query is safe will either add their own defensive reset, or refactor in a way that steps outside the chokepoint, because nothing told them a chokepoint existed. Correctness that is undiscoverable erodes, not because the mechanism fails but because people build around it.

Two axes, four quadrants. Most design arguments are two people pointing at different axes.

Step 3 — Name the split out loud

The move: state which axis each side is on. "We agree the invariant must be structurally enforced. We are disagreeing about how visible the enforcement should be at the call site." Naming it that way often unsticks an argument that had been circling, because it converts one unresolvable dispute into two tractable ones, each with a different kind of evidence behind it.

It also stops the worse outcome, which is the correctness question being decided by whoever cares more about visibility. Once separated, the correctness question can be settled first, on its own terms, and visibility becomes a design task on top of a settled guarantee rather than an argument against it.

Step 4 — Buy visibility without giving up structure

Visibility is not all-or-nothing, and it is usually cheap once the axes are separate. Options, roughly in order of cost:

Name the thing loudly. A base class called TenantScopedTask puts the guarantee in the one line every task author does write. This is close to free and it is the option most often skipped.

Make it explicit at the definition, not the call. A decorator on the function is visible where the function is defined, while still being on the path. This costs the app-wide default: something must ensure it is applied, which trades a little correctness for visibility, and that trade should be made knowingly rather than by accident.

Write the invariant test. Lesson 6's step 5, read as documentation: a test named for the rule, entering through each door, is the most discoverable form the rule can take, because it is the artefact a developer finds when they change the behaviour.

Document at the chokepoint, and point to it. One explanation where the enforcement lives, referenced from the base class docstring, so a reader who does ask "how is this safe" finds the answer in one hop rather than a search.

What none of these do is add a redundant check at the call site. That is the one option that pays for visibility with the correctness property that was the point.

Step 5 — Accept the residue: hiding is what modules are for

Some invisibility is not a defect to be fixed. Ousterhout's argument for deep modules is that the best modules offer a lot of functionality through a simple interface, and that a shallow module with a complex interface and little behind it fails precisely because it does not hide much.1 Information hiding means a caller does not see the mechanism, which is the same sentence as "the enforcement is invisible at the call site", said approvingly.

So the goal is not maximum visibility. It is that the reader who needs to know can find out, cheaply, without every reader paying for that access on every line. A chokepoint with a loud name, an invariant test, and one page of explanation is a deep module doing its job. A chokepoint nobody can locate is the same mechanism with the discoverability work skipped.

Why it matters

Conflating the axes is what makes shape arguments feel like personality clashes. One person is answering "can this break" and the other is answering "can I tell what is going on", both are right about their own question, and the discussion has no way to converge because nobody has said which question is being answered. Separating them costs one sentence.

The asymmetry is worth keeping in mind. Correctness is binary and load-bearing: get it wrong and the invariant fails. Visibility is a gradient and it is about the cost of future work: get it wrong and people are slower and eventually route around the mechanism. Settle correctness first, then spend on visibility, and do not trade the first for the second by accident.

Key line "Can this be violated?" and "can a reader see that it cannot?" are different questions with different kinds of answer. Settle correctness first, then buy visibility with loud names, an invariant test, and one page at the chokepoint. Never buy it with a redundant check at the call site.
The common trap The near-miss is answering the visibility objection by adding an explicit reset at each call site "for clarity", keeping the middleware as a safety net. That reads as belt and braces and it reinstates the convention the structure replaced: the call-site reset is now the thing people learn to do, so a path that omits it looks wrong even though it is safe, and a path that includes it looks safe even where the chokepoint was bypassed. The signal inverts. Buy visibility with names, tests, and documentation, and leave the enforcement in exactly one place.

③ Why is maximum visibility not the goal?

show answer

Because hiding mechanism is what modules are for. Ousterhout's deep modules offer a lot of behaviour through a simple interface, and a caller not seeing the mechanism is information hiding working as intended. The goal is that a reader who needs to know can find out cheaply, not that every reader sees everything on every line.

Primary source — read this one Ousterhout, A Philosophy of Software Design, Ch. 4 "Modules Should Be Deep". Read it for the deep-versus-shallow distinction and for the point that interface complexity is what a caller must know. It is the strongest available argument that the invisibility in step 5 is a feature, which is what makes it useful for calibrating how much of step 4 to actually buy.
