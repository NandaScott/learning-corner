The Shape of Code · Arc 1 · Lesson 2

Where shape shows up

"This feels structurally wrong" is not yet a claim anyone can act on. Shape problems land in exactly three places, and naming which one turns a feeling into something a colleague can agree or disagree with.

The concept

Lesson 1 gave the question: what rule is this code guarding, and can new code elsewhere break it. This lesson gives the three places to point the question at. Entities, boundaries, and invariants. Each has a different tell and a different class of fix, and the three are ranked: invariants are the highest-stakes of the three, for a reason worth being precise about.

Three places, three tells. Locating the problem is most of the work of fixing it.

Step 1 — Entities: does the code's cast of characters match the domain's?

Ask whether the things in the code correspond to the real, distinct things in the domain, or whether one bloated object is standing in for two or three different things that got merged, distinguished only by a flag.

The tell is a field whose meaning depends on another field's value. A record with a kind and a set of fields where some are meaningful for one kind and meaningless for another is two entities wearing one costume. Every consumer then has to re-derive which entity it is actually holding, from a flag, at every use site.

The fix is to split the entity so each real thing is its own thing. Entities is the least alarming of the three axes, because a merged entity usually works. It just makes every downstream reader do the disambiguation, forever.

Step 2 — Boundaries and authority: who is allowed to change this?

Ask whether the thing that is allowed to change a piece of state is actually the only thing that can. That word "only" is the whole question. Nominating an owner is easy; the design question is whether anything enforces the nomination.

The tell is a piece of state that five unrelated functions can each mutate independently. Nobody set out to build that. It accumulates: the state was public because it started simple, and each new writer was locally reasonable. What is lost is the ability to answer "how did this value get to be wrong", because the answer is any of five places, or an interleaving of them.

The fix is to narrow the aperture. One owner, and the state is reachable only through it. Domain-driven design calls this an aggregate: a cluster of objects with a single root through which all changes pass, so the root can be the place that checks the rules.1

Concentrating authority is what makes the rule-checking site exist at all.

Step 3 — Invariants: what must be true always?

An invariant is a rule that must hold always, not merely at the moment of a transition. "A tenant must never see another tenant's data." "An email document always has a text path." "An account balance is never negative." These are the highest-stakes shape violations, and the reason is a distinction worth holding onto.

A lifecycle rule constrains a change: an order may move from paid to shipped but not from cancelled to shipped. It is checked at a moment, and the natural home for the check is the code performing the change, which is a place that obviously exists.

An invariant constrains every state the system is ever in. There is no single moment to check it, because it must hold at all moments, including in code written next year by someone who never read the rule. So an invariant has no natural home. If nothing structural gives it one, it ends up in a comment, a wiki page, and the collective memory of whoever was in the room, and it decays at the rate people leave.

Step 4 — Use the three as a checklist, in that order

Entities first, because a merged entity generates fake invariants: rules like "if kind is email then txtPath must be set" are only rules because two things were merged. Split the entity and the rule evaporates rather than needing enforcement. Boundaries second, because concentrating authority creates the one place an invariant check can live. Invariants last, and hardest, because they are what remains once the structural cleanups are done.

Why it matters

The three axes convert a taste claim into a locatable one. "I do not like this design" invites a defence. "This merges two entities behind a flag, so every consumer re-derives which one it has" invites a fix, and can be agreed with or refuted on the merits. That is the difference between a design discussion that converges and one that becomes a preference fight.

The ranking matters as much as the list. Fake invariants are the ones most often argued about, because they are the ones an entity split would have deleted outright. Time spent designing enforcement for a rule that should not exist is worse than wasted: it makes the merged entity permanent by building machinery around it.

Key line Shape problems land in three places: entities (do the code's things match the domain's things), boundaries (is the permitted writer the only possible writer), and invariants (what must be true always, not just at a transition). Invariants are the highest stakes, because a rule has no natural home the way a transition does.
The common trap The near-miss is treating an invariant as a lifecycle rule. A lifecycle rule constrains a change and can be checked by the code making the change, so it has an obvious home. An invariant constrains every state the system ever occupies, including states produced by code not yet written, so no single check site is sufficient. Answering "when do we validate this?" for something that is actually an invariant produces a check that is correct and, structurally, in the wrong category.

② Why are invariants ranked as the highest-stakes of the three?

They are rules, not workflows. A lifecycle rule constrains a transition, so the code performing the transition is an obvious home for the check. An invariant must hold in every state at every moment, including in code written later by someone who never heard the rule, so it has no natural home. Without a structural one it lives in memory and decays.

③ Why work the three axes in the order entities, boundaries, invariants?

A merged entity manufactures fake invariants ("if kind is X then field Y is required") that a split would delete rather than enforce.
