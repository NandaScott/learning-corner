Invariants: convention or structure

"Everyone must remember to do X first" is a rule stored in people's heads. It holds until the next person writes the next code path. Moving it into the structure means enumerating the entry points, because entry points are finite and future call sites are not.

The concept

The highest-stakes axis from Lesson 2. An invariant must hold in every state the system is ever in, which means it has no natural check site the way a transition does. The design question is therefore not "when do we check this" but "what makes it impossible not to."

The worked case, from the original conversation, is tenant isolation on a multi-tenant Postgres schema layout. The invariant: a query must never execute against another tenant's data. Not a lifecycle rule, not a rule about a change. An always-true rule.

The mechanism it rests on is the Postgres search path. An unqualified table name is resolved by walking a list of schemas: "The system determines which table is meant by following a search path, which is a list of schemas to look in. The first matching table in the search path is taken to be the one wanted."1 Point the search path at a tenant's schema with SET search_path TO tenant_x, public; and every unqualified query in that session reads that tenant's tables. Which is exactly why forgetting to set it is not a degraded query. It is a correct query against the wrong tenant.

Step 2 is the move. It replaces an unbounded set of call sites with a bounded set of doors.

Step 1 — State the invariant precisely

Write it as a sentence that is true at all times, with no "when" and no "before". "A query must never execute against another tenant's data" qualifies. "Reset the search path before querying" does not: that is an instruction, and an instruction is already a convention wearing the invariant's clothes. If the sentence contains a verb aimed at a developer, it has not been stated as an invariant yet.

The precision pays off immediately, because the sentence determines what counts as a violation. "Never executes against another tenant's data" makes an unqualified query in a session with the wrong search path a violation even if it returns plausible results, which is the case a looser statement would miss.

Step 2 — Enumerate the entry points, not the call sites

The convention-based design asks every function that runs a query to reset the search path first. That set is unbounded: it includes every function that exists and every function anyone will write. No audit can complete over it, and it grows fastest exactly when the team is busiest.

The set of ways execution enters the system is small, knowable, and changes rarely. On this stack: an HTTP request, a background task, a management command, a shell session, a scheduled job. Five doors, and the list can be written on one line and checked.

The whole fix is trading an unbounded set for a bounded one.

Step 3 — Put enforcement at each entry point

Each door gets a wrapper that establishes the invariant before any application code runs, and the wrapper is on the path rather than beside it.

For HTTP, that is middleware. Django's contract is a callable taking get_response, whose __call__(request) runs once per request with the code before get_response(request) executing "for each request before the view (and later middleware) are called."2 Ordering matters and is documented: on the request phase Django applies MIDDLEWARE top-down, so tenant resolution must sit above anything that queries tenant data.

class TenantSchemaMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        tenant = resolve_tenant(request)
        with tenant_schema(tenant):          # SET search_path, restore on exit
            return self.get_response(request)

No view can run outside the context manager, because the view is called from inside it.

For workers, that is a task base class. Celery documents both the per-task and the app-wide form: @app.task(base=MyTask) sets one task's base class, and Celery('tasks', task_cls='your.module.path:DatabaseTask') sets it for the whole app, with before_start() among the documented lifecycle handlers.3 The app-wide form is the one that matters here: with task_cls, a task written next year gets the enforcement without its author knowing the enforcement exists.

Whether the mechanism is a middleware, a base class, a decorator, or a context manager is not the design decision. The design decision is that it sits on the only path in.

Step 4 — Audit for bypasses

Structural enforcement is only as good as the completeness of the door list, so the audit is part of the design rather than a follow-up. The question for each door: can application code run through it without passing the wrapper?

The failure cases are specific and worth checking by name. A task that does not inherit the base, in a codebase using per-task base= instead of app-wide task_cls. A management command that queries directly. A raw connection or a second database alias that skips the layer the wrapper hooks. A middleware ordered below something that already queried. Each is a real door that was not on the list.

Postgres offers a sharp reminder here that the search path is a trust boundary in its own right. The documentation's own caveat: "adding a schema to search_path effectively trusts all users having CREATE privilege on that schema", because a user able to create like-named objects in a schema on your path "can take control and execute arbitrary SQL functions as though you executed them."1 A design that writes the search path per request should be deliberate about what else is on that path.

Step 5 — Test the invariant, not the implementation

A test asserting that the middleware calls SET search_path tests the implementation, and it stays green when someone adds a sixth door. A test asserting the invariant looks different: enter through each door, run a query that would read the wrong tenant's rows if the invariant were broken, and assert it does not.

Written that way, the test fails when a new entry point appears without enforcement, which is the actual thing being guarded against. That is the difference between a test that documents the mechanism and a test that defends the rule.

Why it matters

The guarantee moves from "everyone remembers" to "structurally cannot happen", and the two are not points on one scale. A convention's reliability decays with team turnover, deadline pressure, and code volume, which are the conditions under which a tenant-isolation failure is worst. Structural enforcement is indifferent to all three, because the new author never had to know.

This is the property the formal-methods tradition calls correctness by construction, and the practical claim attached to it is that prevention is cheaper than detection: Amey's report on a commercial deployment of the approach attributes the savings largely to the elimination of retesting caused by finding and fixing defects.4 The same economics show up here in miniature. A door has a one-time cost. A convention has a recurring cost paid by every future author, plus the cost of the one time it fails.

Key line A convention asks an unbounded set of future call sites to remember. Structure enumerates the finite set of entry points and enforces at each one, so the rule holds for code whose author never heard of it. Name the invariant, list the doors, wrap each door, then audit for the door you forgot.
The common trap The near-miss is a helper that does the right thing, which everyone is supposed to call. It is convention with better ergonomics: the guarantee still depends on remembering, and the unbounded set of future call sites is untouched. The test is whether the enforcement sits on the only path in or beside it as something available to be used. A second trap is declaring victory after wrapping the obvious door. Middleware covers HTTP and covers nothing else, and the paths that skip it (workers, management commands, the shell, a raw connection) are precisely where the rule is least likely to be remembered.

Recall — answer out loud before peeking:

① Why is "enumerate the entry points" the move, rather than "audit the call sites"?

show answer

Call sites are unbounded: every function that queries today plus every one anyone writes later, so no audit over them can complete. Entry points are how execution enters the system (request, task, management command, shell, scheduled job), which is a small list that changes rarely and can be checked. The fix is trading an unbounded set for a bounded one.

② A shared helper resets the search path correctly and every developer is told to call it. Structural or convention?

show answer

Convention, with better ergonomics. The guarantee still depends on remembering, and a new code path that skips the helper is not stopped by anything. Structural means the enforcement is on the only path in, so code cannot run without it. Beside the path is not on it.

③ Middleware now covers every HTTP request. What is still exposed, and what closes it?

show answer

Every non-HTTP door: Celery tasks, management commands, the shell, scheduled jobs, and anything using a raw connection or a different database alias. For workers, an app-wide task base via Celery's task_cls so tasks written later inherit it automatically, rather than per-task base= which each author must remember.
