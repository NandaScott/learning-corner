The Shape of Code · Arc 1 · Lesson 1

Two kinds of correct

Code can pass every test and still be built wrong. "Produces the right output" and "makes the wrong output hard to produce" are different properties, and only one of them shows up in a test run.

The concept

There are two kinds of correct, and conflating them is what lets a structural problem ship.

Functionally correct means the code produces the right output for the inputs it was given. It passes the tests. It does what the ticket asked. This is a claim about behaviour on the inputs someone thought to write down.

Conceptually correct means the code's structure matches the real structure of the problem, so that wrong states, wrong combinations, and rule violations are hard or impossible to create by accident. Not avoided because everyone remembers to avoid them. Not caught by a test that happens to exist. Impossible, or at least loudly difficult, to write in the first place.

The second is a claim about the code that does not exist yet. That is why no test can report on it. A test exercises what was written; conceptual correctness is about what a future colleague, or a future you, will be permitted to write next Tuesday without anything objecting.

Step 1 — Functional correctness is a claim about tested inputs

A green suite says: for these inputs, this output. It is a real and necessary claim, and it is narrower than it feels. The suite cannot fail on a combination nobody constructed, and it cannot fail on a code path nobody has written. Working code is therefore evidence about the present and silence about the future.

Step 2 — Conceptual correctness is a claim about what can be written at all

Shift the question from "what does this code do" to "what does this code permit." A function taking a status string permits every string. A record with an optional field permits the combination where the field is absent and the state requires it. A rule enforced by a comment permits every caller who does not read the comment. In each case the permitted-but-wrong thing has not happened yet, which is exactly why nothing is red.

Step 3 — The tell is the patch test

Functionally correct code that is conceptually wrong has a signature failure mode. It works today, and every new edge case arrives as a surprise. The fix is a bolt-on: another if, another flag, another special case, in another place. What does not happen is the fix falling naturally out of the existing structure.

Ousterhout catalogues this under the symptoms of complexity: change amplification, where a simple change requires edits in many places, and unknown unknowns, where there is something you need to know and no way to discover what it is until a bug appears after your change.1 A wrong shape produces both, and produces them steadily rather than all at once, which is why it is easy to absorb as normal.

right shape                          wrong shape

Where the fix lands is the diagnostic. Falling out means the structure knew about the case. Bolting on means it did not.

Step 4 — The one question

One question does the work, and it is worth memorising verbatim, because it is short enough to ask in a meeting:

What rule is this code trying to guarantee, and could someone violate that rule by writing new code elsewhere, without the compiler or the structure stopping them?

If the answer is yes, that is a shape problem. Notice what the question forces: first name the rule, which is often the harder half. Code that cannot state the rule it guards has no defence against violating it, because nobody knows what they would be violating.

Why it matters

A shape problem is not a style problem, and the two get treated the same because both surface at review time as "this could be nicer." Style is how the code reads. Shape is what the code permits. Renaming a variable, extracting a helper, or tightening a docstring improves how a wrong shape reads while leaving every wrong thing it permits exactly as writable as before. That is why a shape problem survives a review that only checks readability, and survives it looking better than it went in.

The practical payoff is where the correction gets made. A shape problem found at design time is a different sentence in a document. Found after the code is in production and three callers depend on the loose signature, it is a migration. The cost of the fix grows with the number of places that learned to depend on the wrong shape, which is why the question above is worth asking before the first line rather than at review.

Key line Functional correctness is about the inputs you tested. Conceptual correctness is about the code nobody has written yet. Ask: what rule is this guarding, and could new code elsewhere break it without anything stopping them?
The common trap The near-miss is treating clean code as conceptually correct code. Well-named, well-factored, fully tested code can still hand a caller a signature that accepts an impossible combination, or a record that can hold a state its fields contradict. Clean Code is largely about legibility, which is a real axis and a different one. A tidy wrong shape is a wrong shape that reads well.

③ What is the tell that distinguishes a shape problem from an ordinary bug?

show answer

Where the fix lands. A shape problem is fixed by bolting on another if, flag, or special case in another place, and the next edge case feels like a surprise. With the right shape the fix falls out of the existing structure and touches one place. Ousterhout's change amplification and unknown unknowns are the same symptom described from the outside.

Primary source — read this one Ousterhout, A Philosophy of Software Design, Ch. 2 "The Nature of Complexity". Twelve pages, and the most useful twelve in the book for this course. It gives the three symptoms (change amplification, cognitive load, unknown unknowns) and the two root causes (dependencies and obscurity), which is the vocabulary for describing what a wrong shape costs before you can point at a bug.
Go deeper. Ask if the line between a shape problem and a bug is unclear on a specific piece of code. Bring the code. The one question usually settles it in a sentence, and where it does not, the disagreement itself is informative.
