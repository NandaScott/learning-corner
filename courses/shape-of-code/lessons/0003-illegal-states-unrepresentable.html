The Shape of Code · Arc 2 · Lesson 3

Make illegal states unrepresentable

A status field plus a set of optional fields quietly permits every combination of the two, most of which are nonsense. Splitting one type into one case per state removes the nonsense from the language, not from the code review.

The concept

This is the entities axis from Lesson 2, and the phrase to say out loud in a design discussion. Yaron Minsky coined it for OCaml at Jane Street, in his Effective ML guest lectures and the Jane Street writing around them.1 Say "making illegal states unrepresentable" and most senior engineers will know exactly what you mean, which is a large part of why it is worth knowing the phrase and not merely the idea.

The principle: model the data so that values which make no sense in the domain cannot be constructed. Not rejected at runtime. Not caught by a test. Not expressible.

The five steps. Step 2 is the one that turns a hunch into an argument.

Step 1 — Spot the flag-plus-optionals encoding

The wrong shape is one entity, a flag, and scattered trust:

type Order = {
  status: string;                 // "pending" | "paid" | "shipped" | "cancelled"
  trackingNumber?: string;
};

// somewhere, someone has to remember:
if (order.status === 'shipped' && !order.trackingNumber) { /* uh oh */ }

The comment is the specification. That is the problem, not the style.

The TypeScript handbook names this exact failure, using a shape with kind: "circle" | "square" and optional radius and sideLength: "The problem with this encoding of Shape is that the type-checker doesn't have any way to know whether or not radius or sideLength are present based on the kind property."2 Even after checking kind === "circle", reading radius is still an error, because nothing connected the two fields.

Step 2 — Count what the type permits

This is the step that converts taste into arithmetic, and it is the one to do out loud in a review. The Order above has a status: string, so it permits every string, and an independent optional tracking number, so it permits present or absent. The type therefore describes an unbounded set of orders, of which exactly four are legal states, and among those four the tracking number is required in one and meaningless in three.

Every combination the type permits and the domain forbids is a bug someone has to be prevented from writing, by hand, forever. That count is the cost of the encoding, and it is not a rhetorical point: it is the number of "uh oh" comments the codebase will eventually need.

Step 3 — Split into one case per state

Give each state its own case, carrying exactly the fields that state actually has:

type Order =
  | { status: 'pending' }
  | { status: 'paid';      paidAt: Date }
  | { status: 'shipped';   trackingNumber: string }
  | { status: 'cancelled'; reason: string };

Four cases, four legal states. The illegal combinations are no longer values that can be built.

Note what left the type. There is no longer any way to have a shipped order without a tracking number, because trackingNumber does not exist outside the shipped case. There is no longer a cancelled order without a reason. The "uh oh" check has nothing left to check, so it can be deleted rather than maintained.

Step 4 — Narrowing hands each consumer only its own fields

The handbook's definition: "When every type in a union contains a common property with literal types, TypeScript considers that to be a discriminated union, and can narrow out the members of the union."2 Checking order.status === 'shipped' narrows the type to that case, and only inside that branch is trackingNumber reachable. Outside it, reading the field is a compile error rather than undefined at runtime.

The second benefit is exhaustiveness. A consumer that switches on status can be made to fail compilation when a fifth state is added, so the new state surfaces as a list of every place that must decide about it. Compare the flag encoding, where adding a state changes nothing and is discovered in production.

flag encoding                        discriminated union

add status 'refunded'                add case { status:'refunded'; ... }

The union turns "add a state" from a search problem into a worklist.

Step 5 — Keep the transition knowledge, in one place

The union removes illegal states. It does not by itself remove illegal transitions: nothing above prevents building a shipped order directly from a cancelled one. Something still has to know the legal order of states, pending to paid to shipped, and that is fine. It is real domain knowledge and it has to live somewhere.

The design requirement is that it live in one place, a transition function that is the only way orders change state, rather than smeared across every function that happens to touch an order. That is the boundaries axis from Lesson 2 doing its job: concentrating authority is what makes a single legal-transition check possible.

Why it matters

The flag encoding and the union encoding are equally functionally correct on the day they are written. They diverge on everything after that day. Under the flag, each new consumer must independently rediscover which field combinations are real, and each new state is invisible to the compiler, so correctness is maintained by a distributed act of remembering. Under the union, the compiler holds the domain rule and reports every site that needs to change, so correctness survives people leaving.

Applying Lesson 1's question to the flag version: the rule is "a shipped order has a tracking number", and yes, anyone can violate it by writing new code elsewhere, and nothing stops them. Applying it to the union: the rule is the same, and no, they cannot, because the value does not exist. Same behaviour today, different structure, and the difference is entirely about code that has not been written yet.

Key line A flag plus optional fields permits every combination of the two, and the domain allows a handful. Split into one case per state, each carrying only its own fields, and the illegal combinations stop being values that can be built. Keep transition rules in one function, not in every consumer.
The common trap The near-miss is keeping the flag encoding and adding a runtime guard or a validation function that rejects the bad combinations. That is strictly better than nothing and it is still convention: the illegal value remains constructible, so the guard has to be called everywhere, forever, by everyone. The distinction is whether the wrong thing is rejected or unrepresentable. A second trap in the other direction: assuming the union also handles transitions. It does not, and a union with transition logic copied into six consumers has traded one shape problem for another.

Recall — answer out loud before peeking:

① What is the argument that turns "I dislike this type" into something a colleague can check?

show answer

Count what the type permits against what the domain allows. A status: string with an independent optional field permits unboundedly many values, of which four are legal states, with the optional field required in one and meaningless in the rest. Each permitted-but-illegal combination is a bug someone must be prevented from writing by hand.

② A discriminated union is in place. What still has to be designed, and where does it go?

show answer

Legal transitions. The union removes illegal states, not illegal state changes. Transition knowledge is real domain knowledge and belongs in one transition function that is the only way the state changes, not copied into every consumer that touches the object.

③ Adding a fifth state to the flag version compiles and passes tests. Why is that the problem rather than the point?

show answer

Because the consumers that need to decide about the new state are silent. With an exhaustive switch over a union, adding a case fails compilation at every site that must choose, which converts "find the thirty places" into a worklist handed to you before merge. Under the flag it is found in production.
