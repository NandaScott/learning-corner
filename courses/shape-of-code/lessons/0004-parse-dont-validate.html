Parse, don't validate

A validator learns something true about its input and then throws that knowledge away, which is why the same check reappears in every function downstream. A parser learns the same thing and returns a value that carries the proof.

The concept

Lesson 3 shaped data that is already inside the system. This lesson is about the boundary where untrusted input becomes trusted data, which is the boundaries axis from Lesson 2 applied to information rather than to authority.

Alexis King's formulation is the canonical one, and the whole argument sits in a pair of function signatures.1 A validator takes the input and returns nothing: it either raises or it does not. A parser takes the input and returns a different type, one that can only hold valid data. King's summary of what parsing is: "a function that consumes less-structured input and produces more-structured output."

Step 3 is the whole move. Steps 4 and 5 are what it buys.

Step 1 — The signature tell: a check that returns nothing

King's advice is to "treat functions that return m () with suspicion", which in a Python or TypeScript codebase reads as: be suspicious of a check whose return type is None, void, or bool.1 Such a function establishes a fact and then discards it. The caller knows the fact only for as long as it stays on that line, and every function it calls afterwards knows nothing.

def validate_non_empty(items: list[str]) -> None:      # proves something, returns nothing
    if not items:
        raise ValueError("empty")

def parse_non_empty(items: list[str]) -> NonEmpty:     # proves something, returns the proof
    if not items:
        raise ValueError("empty")
    return NonEmpty(head=items[0], rest=items[1:])

Same check, same raise. The difference is entirely in the return type, and that is the whole lesson.

Whether the check raises or returns a boolean is not the distinction. Both discard the knowledge. The distinction is whether anything downstream can tell, from a type, that the check happened.

Step 2 — Name what the check proved

Before writing a type, say the fact in words. "This list is not empty." "This string is a well-formed email address." "This path points at a file that exists." "This user ID belongs to the current tenant." A check that cannot be summarised as a single fact is usually several checks, which is useful to discover here rather than later.

The naming step is also where fake proofs get caught. "This input has been validated" is not a fact about the data; it is a fact about the code's history, and it cannot be encoded in a type because it is not a property of the value.

Step 3 — Return a type that carries the proof

The type does not need to be clever. It needs to be a distinct type that only the parser can produce, so that possessing one is evidence.

@dataclass(frozen=True)
class TenantScopedUserId:
    value: int

def parse_user_id(raw: object, tenant: Tenant) -> TenantScopedUserId:
    ...                                   # all the checking happens once, here
    return TenantScopedUserId(user_id)

def send_invoice(user_id: TenantScopedUserId) -> None:
    ...        # cannot be called with an arbitrary int; nothing to re-check

A function taking TenantScopedUserId states its precondition in its signature instead of trusting its callers.

Frozen matters. If the value can be mutated after construction, the proof expires without anything saying so, and the type is documentation rather than a guarantee. King makes the point directly in his closing advice: avoid denormalized, mutable representations of data.1

Step 4 — Push the parse to the edge, but no further

Parse as early as the data arrives, so the region of the program handling untrusted values is as small as possible. King's version: "push the burden of proof upward as far as possible, but no further."1

The second half is the part that gets dropped and matters. Pushing a proof further up than the data warrants forces every caller to supply evidence it may not have, and the usual result is a function that reconstructs the parsed type from nothing to satisfy a signature, which is worse than not having asked. The right edge is the point where the raw input actually enters, not the outermost function you can reach.

The failure mode this prevents has a name from the security literature, which King quotes: shotgun parsing, "a programming antipattern whereby parsing and input-validating code is mixed with and spread across processing code."1 The consequence is that processing begins before validation finishes, so the program can act on input it later rejects.

Step 5 — The stack this actually runs on: where DRF stops helping

A DRF serializer is a parser in every respect but the one that counts. The documentation describes deserialization in two stages: parse a stream into Python native datatypes, then "restore those native datatypes into a dictionary of validated data", and .validated_data holds the result.2

A dictionary. The serializer does the full parse, proves every field, and then hands back an untyped mapping, so the proof stops at the view boundary. A service function taking data: dict cannot tell a validated payload from any other dict, and its author reasonably re-checks the fields it depends on. That is shotgun parsing reintroduced one layer down, by the framework's own return type.

proof discarded at the view            proof carried past the view
──────────────────────────            ──────────────────────────
s = OrderSerializer(data=request.data) s = OrderSerializer(data=request.data)
s.is_valid(raise_exception=True)       s.is_valid(raise_exception=True)
place_order(s.validated_data)          cmd = PlaceOrder(**s.validated_data)
                                       place_order(cmd)

def place_order(data: dict):           def place_order(cmd: PlaceOrder):
    # any dict at all; the author          # only constructible from a
    # re-checks what it needs             # parsed payload; nothing to
                                          # re-check

One extra line at the boundary. It is the line that keeps the parse from being wasted.

The fix is small: construct a frozen dataclass, one per command or query, from validated_data, and let everything inward take that type. The serializer keeps doing the checking, which it is good at. The dataclass carries the result, which the dict cannot.

Why it matters

Re-validation looks like diligence and behaves like a shape problem. Every function that re-checks its input is a function whose signature was not honest about what it required, and the checks drift: one call site tightens a rule, another does not, and the difference is invisible because both are individually correct. The tell from Lesson 1 is exactly what shows up, a new edge case handled by another check in another place.

Parsing also relocates the error. Under validation, a bad value can travel deep into the system and fail somewhere with no useful context, possibly after partial work. Under parsing it fails at the boundary, where the raw input is still in scope and a specific message is possible. Same rejection, and the difference in debuggability is not small.

Key line A validator returns nothing, so the fact it established survives one line. A parser returns a type that carries the proof, so every function downstream states its precondition in its signature instead of re-checking. Parse at the edge, once, and let the type travel.
The common trap The near-miss is "we validate once, at the entry point." That fixes where the check runs and not what comes out of it: if the entry point still passes a plain dict or a bare string inward, nothing downstream can distinguish checked data from unchecked, so the re-checks come back and the discipline decays. Parsing is defined by the return type differing, not by the check being early. On this stack that is precisely the DRF gap, since .validated_data is a dict, so "the serializer validated it" is exactly the near-miss with a framework behind it.

Recall — answer out loud before peeking:

① What single feature of a function's signature tells you it validates rather than parses?

show answer

The return type. Returning None, void, or bool means the fact it proved is discarded at the end of the call. A parser returns a distinct type that only it can construct, so holding that type is evidence the check happened. Raising instead of returning false changes nothing about this.

② "Push the burden of proof upward as far as possible, but no further." What does the second half prevent?

show answer

Demanding proof from callers that have no way to supply it. Pushed too far, a function requires a parsed type from a caller that never saw the raw input, and the usual result is fabricating the type to satisfy the signature, which destroys the guarantee. The right edge is where the raw input actually enters the program.

③ A DRF serializer validated the payload. Why is passing validated_data inward still the wrong shape, and what is the one-line fix?

show answer

.validated_data is a plain dict, so the proof does not cross the view boundary and a service function cannot tell a validated payload from any other mapping, which invites re-checking. Build a frozen dataclass from it at the boundary and let inner layers take that type.
