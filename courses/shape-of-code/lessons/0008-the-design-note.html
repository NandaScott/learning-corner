The design note

Everything in this course happens before the first line of code or not at all. Ten minutes, plain English, no code: entities, invariants, lifecycle, boundaries, options, choice. Then one question at the end that decides whether the design is finished.

The concept

The seven preceding lessons are analysis tools. This one is the practice that puts them in front of the keyboard, which is the only place they pay. A design note is a short written artefact for any non-trivial ticket, written before code, in prose, deliberately without code.

Prose is part of the mechanism rather than a formatting preference. Sentences make vagueness visible in a way a class diagram does not: a rule you cannot state as a sentence is a rule you have not decided yet, and it will get decided implicitly by whatever gets typed first.

The order is not arbitrary: each section constrains the next, and the last question audits all of them.

Step 1 — Entities, as concepts rather than tables

List the real, distinct things in the problem. The parenthetical in the template does the work: not tables, concepts. Starting from tables imports whatever merges the schema already made, which is the merged-entity fault from Lesson 2 arriving pre-installed.

The check from Lesson 3 applies here: if two of your listed things are distinguished only by a flag, they are one entity in the code and two in the domain, and the rest of the note will generate fake rules about which fields are required when.

Step 2 — Invariants, as always-true sentences

Write what can never be violated, at any point. Each one as a sentence with no "when" and no "before", per Lesson 6's step 1. This section is short and it is the one that most often turns out to be empty on first pass and non-empty on second, which is worth taking as a signal rather than as a relief.

Step 3 — Lifecycle, if there is one

Which states can this thing be in, which transitions between them are legal, and which data is only valid or relevant in certain states. That third question is the one that produces a discriminated union directly: any field that is meaningful in some states and not others belongs to the states where it is meaningful.

"If applicable" is real. Plenty of tickets have no lifecycle, and inventing one produces a state machine over something that was a value. The tell that there is no lifecycle: nothing in the ticket describes a transition, only a computation.

Step 4 — Boundaries, and the word "only"

What is the only thing allowed to change each piece of state, and where does one concept's responsibility end and the next begin. Writing "only" forces the question from Lesson 2: nominating an owner is easy, and the design content is whether anything enforces the nomination.

This section is where the enforcement mechanism gets chosen, so it is where the door list from Lesson 6 gets written down. If an invariant from step 2 has no owner named here, it is currently enforced by convention, and the note has just told you that.

Step 5 — Options and the choice

At least two approaches, each with its tradeoffs, then the chosen one and why. Two matters: a note with one option is a justification rather than a design, and the second option is what makes the tradeoffs of the first visible.

This is also where Lesson 7's two axes belong. If the options differ in how visible an enforcement is rather than in whether it holds, say so in the tradeoff line. Recording that the correctness question was settled and the visibility question was a deliberate choice is what stops the argument being re-litigated later as though it were about correctness.

Step 6 — The last question, which is the gate

What would make the wrong thing impossible, not just unlikely, here?

This is the most important line in the template. If it cannot be answered, the design is not finished, even when it is completely clear how to start typing. Those two feelings are easy to confuse, because knowing how to start is what "ready" normally feels like.

Answering it requires everything above: which wrong thing (from entities and invariants), which mechanism (from boundaries), and impossible rather than unlikely (the distinction from Lesson 1). An honest answer of "nothing available makes it impossible, so we are enforcing it by convention and accepting that" is a legitimate answer. What is not legitimate is not noticing.

Practice: four exercises

The note is a habit, and habits need reps that are not the real thing. Four, in increasing cost:

1. Retro-fit a past ticket. Pick something already shipped and write the note after the fact, describing the code as it actually is. The gaps between what the note says and what the code does are the conceptual mismatches, measured rather than guessed. This is the highest-information exercise here because the answer is checkable.

2. The "what's impossible" audit. Pick any function touched this week. Ask what wrong input or combination should be impossible, then determine whether it actually is impossible or merely untested. Five minutes, and it is Lesson 5's call-space enumeration applied without ceremony.

3. Ask a reviewer the model question. In the next review: "before you looked at my code, what shape did you expect this to have?" That surfaces someone else's pre-keyboard model directly, which is the one thing no book supplies, because it is normally discarded the moment the code is read.

4. Spot the flag. Find a boolean or string-enum flag in a codebase you work in that changes which fields are valid or required. Almost always Lesson 3 or Lesson 5 in disguise. Sketch the discriminated-union version on paper, not in code, since the point is the reflex rather than the refactor.

Why it matters

Every lesson in this course describes a fix that is cheap before code and expensive after. Splitting an entity is a paragraph in a note and a migration in production. Adding a chokepoint is a design decision on day one and an audit of every existing call site on day two hundred. The note is the mechanism that moves the decision to the cheap side, and ten minutes is the whole cost.

The compounding effect is the vocabulary. Written notes make shape arguable, and arguable is what shape needs, because these are judgment calls with real tradeoffs rather than rules to apply. A team that can say "that is an invariant, not a lifecycle rule" or "we agree on correctness and disagree on visibility" resolves in minutes what otherwise circles, and the notes are how the phrases get into circulation.

Key line Shape isn't about how the code is written. It's about whether the code makes the domain's rules hard to break, by making the wrong thing structurally impossible instead of just discouraged. Ten minutes of prose before typing, and one question at the end: what would make the wrong thing impossible here, not just unlikely?
The common trap The near-miss is writing the note and stopping at "chosen approach and why", which feels finished because a decision got made. The last question is the gate, and skipping it is how a note becomes a record of a preference. The other trap is treating clarity about how to start typing as evidence the design is done. Those are different states that feel identical, and the last question is the only thing that reliably tells them apart.

"What would make the wrong thing impossible, not just unlikely, here?" Not being able to answer means the design is not finished, even when it is entirely clear how to start typing. ③ Which exercise gives checkable feedback rather than an opinion, and why?

show answer

Retro-fitting the note to something already shipped. The code exists, so the gaps between what the note says the design should be and what the code actually does are measurable rather than hypothetical. Each gap is a conceptual mismatch that was made without being noticed.
