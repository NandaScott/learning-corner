The Shape of Code · Arc 3 · Lesson 5

Kill the flag that changes what's required

An optional parameter that is mandatory in one branch and meaningless in the other is the same shape problem as an optional field on a flagged record. The fix is the same too: split, so each signature accepts exactly what it needs.

The concept

Lesson 3 split a data type into one case per state. This lesson applies the identical move to a parameter list. Same disease, different surface, and the function version is easier to miss because a parameter list does not look like a data model.

Here is the case, from the original design conversation. A single function validates two kinds of document. One kind has a single file; the other has two.

function validateDocument(type: 'pdf' | 'email', htmlPath: string, txtPath?: string) {
  if (type === 'pdf') {
    // validate htmlPath only
  } else {
    // validate htmlPath and txtPath
  }
}

Nothing stops validateDocument('email', htmlPath) from compiling, and it silently under-validates.

The third parameter is required when type is 'email' and irrelevant when it is 'pdf'. Because the type system sees an independent optional string, the wrong combination is a legal call. It compiles, it runs, it validates half of what it should, and it reports success.

Step 4 is where this gets argued about, and step 5 is where the win compounds.

Step 1 — Spot the coupled parameter

The tell is a parameter whose necessity depends on another parameter's value. Optional in the signature, mandatory in one branch of the body. Fowler names the general category and gives the same remedy: "A flag argument is a kind of function argument that tells the function to carry out a different operation depending on its value," and "rather than use a flag argument, I prefer to define separate methods."1

Not every boolean parameter is this problem. A parameter that tunes behaviour without changing which other parameters are meaningful is a configuration value. The specific fault here is a flag that changes what the rest of the signature means, which is the point at which one function is standing in for two.

Step 2 — Enumerate the call space

The same arithmetic as Lesson 3's step 2, and it makes the case in one line. Two values of type, times present-or-absent for txtPath, gives four calls that compile. Three of them are meaningful. The fourth, email without a text path, is the under-validating one, and it is the call a hurried author is most likely to write, because the parameter is optional and optional reads as "safe to omit."

Worth noting which way the failure points. This does not raise. It validates fewer things and returns success, so the bug is a document that passed validation it never actually received. Silent under-enforcement is the worst failure mode a validator can have, because the whole point of the call was to be told.

Step 3 — Split into one function per branch

function validatePdfDocument(htmlPath: string) { /* ... */ }
function validateEmailDocument(htmlPath: string, txtPath: string) { /* ... */ }

"Email without a text path" is no longer discouraged. It is not callable.

Both parameters are now required where they are required, and absent where they are irrelevant. The four-call space collapses to two calls, both meaningful. The if is gone, so is the optional marker, and so is the possibility of the silent case. The names improved as a side effect, which is pleasant and is not the point.

Step 4 — Shape is not DRY: share the mechanism, delete the branch

This is the step that draws the objection, and the objection deserves a straight answer. In the original case the underlying validation mechanism was shared between both kinds of document, and it stayed shared. Both new functions call the same internals.

Shape work is not about reducing duplication. The two functions are not a copy-paste of each other; they are two public entry points over one shared implementation. What was deleted is the branch that let a caller supply the wrong combination, which is a different thing from deleting shared code.

one entry point, branch inside          two entry points, one mechanism
──────────────────────────              ──────────────────────────
validateDocument(type, a, b?)           validatePdfDocument(a)
  if type == pdf:  check(a)               → checkOne(a)
  else:            check(a, b)          validateEmailDocument(a, b)
                                          → checkOne(a); checkTwo(b)
4 calls compile, 3 are valid
                                        2 calls compile, 2 are valid
                                        shared internals: unchanged

The duplication argument is answered by where the sharing lives: below the entry points, not at them.

Ousterhout's framing is useful for the objection in the other direction, that two functions is a wider interface than one. It is a wider interface only by count. The single function's interface included an undocumented rule about which parameter combinations are legal, which is interface complexity that no signature declared. Two honest signatures are less to know than one signature plus a rule.2

Step 5 — Check whether the caller still needs the flag

The fix often propagates usefully upward. If callers were passing a literal 'pdf' or 'email', they already knew which kind they had, and the flag existed only to carry that knowledge across the call. Splitting the function deletes the carrying, and the caller's own branch may disappear with it.

If a caller genuinely does not know which kind it has, that is real information and it needs modelling. It usually means the caller is holding a value that should itself be a discriminated union, and the dispatch belongs at the one place that narrows it, not inside a validator that guesses from a string.

Why it matters

Applying Lesson 1's question to the original signature: the rule is "an email document is validated against both of its files", and yes, new code elsewhere can violate it by omitting an optional argument, with nothing objecting. The under-validated call passes review because it looks like every other call, and it passes tests because the tests were written by someone who knew to pass the third argument.

The general lesson is that a parameter list is a data model. Every optional parameter multiplies the call space, and every optional parameter whose necessity depends on another parameter puts illegal calls into that space. The techniques from Lesson 3 apply unchanged, and the reason to treat it as its own lesson is that nobody reviews a parameter list the way they review a type.

Key line A parameter that is required in one branch and irrelevant in the other makes the wrong combination a legal call. Split into one function per branch, each taking exactly what it needs, and keep sharing the mechanism underneath. The target is the branch, not the duplication.
The common trap The near-miss is keeping one function and adding a guard: throw when the type is email and the text path is missing. That converts a silent under-validation into a loud runtime failure, which is a genuine improvement, and it leaves the illegal call compiling. The wrong combination is still writable, so it still reaches production to fail there. The second trap is rejecting the split on duplication grounds. Shape work is not DRY work: the mechanism stays shared below two honest entry points, and what gets deleted is the branch that permitted the bad combination.

② A colleague objects that two functions duplicate logic. What is the answer?

show answer

The mechanism stays shared: both entry points call the same internals. Nothing was duplicated. What was deleted is the branch that let a caller supply an illegal combination. Shape work targets what the signature permits, not how many lines repeat.

③ Why is the original signature's failure mode worse than an exception would be?

show answer

Omitting the optional argument does not raise. It validates fewer things and returns success, so a document passes validation it never received. Silent under-enforcement defeats the purpose of calling a validator, and it looks identical to a correct call at every review.
