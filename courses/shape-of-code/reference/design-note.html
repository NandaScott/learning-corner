The Shape of Code · Reference

Design note template

The compressed payoff of the eight lessons. Ten minutes, plain English, no code yet, before writing anything on a non-trivial ticket. Print it. The table at the bottom is the smell list for when the note is already written and something still feels wrong.

The template

### Design note: [ticket/feature name]

**Entities involved:**
- What are the real, distinct things here? (Not tables — concepts.)

**Invariants (must always be true):**
- What rules can never be violated, at any point?

**Lifecycle (if applicable):**
- What states can this thing be in?
- What are the legal transitions between them?
- What data is only valid/relevant in certain states?

**Boundaries:**
- What's the only thing allowed to change each piece of state?
- Where does one concept's responsibility end and the next begin?

**Approach considered:**
1. [Option A] — tradeoffs:
2. [Option B] — tradeoffs:

**Chosen approach and why:**

**What would make the wrong thing impossible (not just unlikely) here?**

Copy this verbatim into the ticket or a scratch file. The last line is the gate.

What each section is asking

SectionWhat it is really askingFails when
Entities Do the code's things match the domain's things? Start from concepts, because starting from tables imports whatever merges the schema already made. Two listed things are distinguished only by a flag. That is one entity in the code and two in the domain. L2, L3
Invariants What must be true in every state, at every moment, including in code written next year by someone who never heard the rule. The sentence contains a "when", a "before", or a verb aimed at a developer. That is an instruction, so it is already a convention. L6
Lifecycle Which states, which legal transitions, and which data is valid in only some states. That last question hands you a discriminated union directly. You invent a state machine over something that was a value. The tell for no lifecycle: the ticket describes a computation, not a transition. L3
Boundaries What is the only thing allowed to change each piece of state, and what enforces that. Write the door list here. An invariant from the section above has no owner named here. It is currently enforced by convention, and the note just said so. L2, L6
Options At least two approaches with tradeoffs. The second is what makes the first one's tradeoffs visible. One option, which makes the note a justification rather than a design. Also: a tradeoff about visibility written as though it were about correctness. L7
The last question What makes the wrong thing impossible rather than unlikely. Requires every section above: which wrong thing, by which mechanism, and impossible or merely discouraged. It cannot be answered. The design is unfinished, however clear it is how to start typing. "Nothing makes it impossible, so we accept a convention" is a legitimate answer; not noticing is not. L1, L8

Shape smells: tell, diagnosis, move

For code that already exists, or a note that is written and still feels wrong. Each row is a tell you can spot in under a minute.

TellDiagnosis → move
A field's meaning depends on another field's value. A record with a kind or status plus optional fields. Two entities merged behind a flag. Count what the type permits against what the domain allows, then split into one case per state, each carrying only its own fields. Keep transition rules in one function. L3
A parameter is optional in the signature and mandatory in one branch of the body. A flag that changes what the rest of the signature means. Split into one function per branch, each taking exactly its own inputs. Keep the mechanism shared underneath; the target is the branch. L5
A check returns None, void, or bool, and the same check reappears downstream. Validation discarding its own proof. Name the fact it proved, return a frozen type that carries it, and parse where the raw input actually enters. Then delete the downstream re-checks. L4
A service function takes dict and re-checks fields a serializer already validated. The DRF dict gap: .validated_data is a plain mapping, so the proof stopped at the view. Build a frozen dataclass from it at the boundary and let inner layers take that type. L4
Documentation or a review comment says "always remember to X first." An invariant stored in people's heads. State it as an always-true sentence, enumerate the entry points, wrap each one, then audit for the door you forgot. L6
The correct behaviour lives in one shared helper that everyone is supposed to call. Convention with better ergonomics. Enforcement is beside the path, not on it. Move it to the chokepoint: middleware for HTTP, an app-wide task base for workers. L6
Several unrelated functions can each mutate the same piece of state. Diffuse authority, so "how did this become wrong" has no single answer. Narrow the aperture to one owner through which all changes pass, which is also the only place a rule check can live. L2
Every new edge case arrives as a surprise and is fixed by another branch elsewhere. The patch test failing. The structure does not distinguish cases the domain distinguishes. Find the missing distinction and put it in the type or the signature, so the next fix falls out. L1
Adding a new state or kind compiles, passes tests, and touches nothing. No exhaustiveness. The consumers that must decide are silent until production. Switch over a union so the compiler hands you the worklist before merge. L3
A rule is enforced structurally, and a reviewer objects that they cannot see it. A visibility objection, not a correctness one. Name the split out loud, then buy visibility with a loud name, an invariant test, and docs at the chokepoint. Never a redundant call-site check. L7
A rule is enforced twice, once at the chokepoint and once "for clarity" at each call site. Signal inversion. The call-site check becomes the norm, so safe paths look wrong and bypassed paths look safe. Keep enforcement in exactly one place and buy visibility elsewhere. L7
A test asserts that the middleware calls the enforcement, not that the rule holds. Testing the mechanism. Rewrite it to enter through each door and assert the invariant, so it fails when a new unprotected door appears. L6

Four practice reps

#ExerciseWhy
1Retro-fit the note to something already shipped, describing the code as it actually is.The gaps between note and code are the conceptual mismatches, measured rather than guessed. The only rep here with a checkable answer.
2Pick a function touched this week. What wrong input or combination should be impossible, and is it, or is it merely untested?Five minutes, no ceremony. It is the call-space enumeration applied on the spot.
3Ask a reviewer: "before you looked at my code, what shape did you expect this to have?"Someone else's pre-keyboard model, which is normally discarded the moment the code is read. No book supplies this.
4Find a flag in a codebase you work in that changes which fields are valid or required. Sketch the union version on paper.Paper, not code. The point is the reflex, not the refactor.
The one-line summary Shape isn't about how the code is written. It's about whether the code makes the domain's rules hard to break, by making the wrong thing structurally impossible instead of just discouraged.
Using this. Bring a filled-in note, especially one where the last question has no good answer. That is where the interesting tradeoffs live, and it is the fastest way to sharpen the habit.
