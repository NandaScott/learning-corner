The Shape of Code · Reference

Glossary

The shared vocabulary for this course. Every lesson uses these terms exactly as defined here. The first table is the set of names other engineers will recognise in a design discussion, which is the point of learning them.

Names for this, so you can say it out loud

Five phrases cover the territory. Say "making illegal states unrepresentable" in a design discussion and most senior engineers will know exactly what you mean, which makes it the highest-value one to have ready.

TermCoined by / associated withWhat it emphasizes
Making illegal states unrepresentableYaron MinskyThe general principle, and the most commonly recognised phrase for it. (Lesson 3)
Parse, don't validateAlexis KingParse once into a type that can only hold valid data, instead of re-validating a loosely typed thing everywhere. (Lesson 4)
Type-driven designGeneral usageThe umbrella discipline of leaning on types to enforce domain rules. Useful as a heading, less useful as an argument, since it names the family rather than a move.
Correct by constructionFormal methods traditionInvalidity is structurally impossible rather than checked after the fact. The lineage behind Lesson 6's chokepoints.
Deep modules / information hidingJohn OusterhoutA module's interface should hide the complexity rather than expose the mess. The reason some invisibility is a feature. (Lessons 5, 7)

Course terms

TermDefinition
Functionally correctThe code produces the right output for the inputs it was given. It passes its tests and does what the ticket asked. A claim about behaviour on the inputs someone thought to write down. (Lesson 1)
Conceptually correctThe code's structure matches the real structure of the problem, so wrong states, wrong combinations, and rule violations are hard or impossible to create by accident. A claim about what future code is permitted to write. (Lesson 1)
The one question"What rule is this code trying to guarantee, and could someone violate that rule by writing new code elsewhere, without the compiler or the structure stopping them?" Yes means a shape problem. Note that it forces you to name the rule first. (Lesson 1)
Shape problem vs style problemStyle is how the code reads. Shape is what the code permits. Renaming and extracting improve how a wrong shape reads while leaving every wrong thing it permits equally writable. (Lesson 1)
The patch testThe tell for a wrong shape: every new edge case is a surprise, and the fix bolts on another if, flag, or special case in another place instead of falling out of the existing structure. (Lesson 1)
Change amplificationOusterhout's first symptom of complexity: a seemingly simple change requires modifications in many different places. What a wrong shape produces steadily rather than all at once. (Lesson 1)
Unknown unknownsOusterhout's worst symptom: there is something you need to know and no way to find out what it is, or whether there is an issue, until a bug appears after your change. (Lesson 1)
The three axesEntities, boundaries and authority, invariants. The three places a shape problem lands. Naming which one converts a taste claim into a locatable one. Worked in that order. (Lesson 2)
Entities axisDo the things in the code correspond to the real, distinct things in the domain, or is one bloated object standing in for two or three, distinguished only by a flag? Tell: a field whose meaning depends on another field's value. (Lesson 2)
Boundaries / authority axisIs the thing allowed to change a piece of state actually the only thing that can? The word "only" is the design content. Tell: several unrelated functions can each mutate the same state. (Lesson 2)
InvariantA rule that must hold always, not merely during a transition. "A tenant must never see another tenant's data." Stated as an always-true sentence with no "when" and no verb aimed at a developer. (Lessons 2, 6)
Lifecycle ruleA rule constraining a change: an order may go from paid to shipped but not from cancelled to shipped. Checked at a moment, so the code performing the change is an obvious home. Contrast with an invariant, which has none. (Lesson 2)
Fake invariantA rule that exists only because two entities were merged ("if kind is email then the text path is required"). Splitting the entity deletes it rather than enforcing it. Building enforcement for one makes the merge permanent. (Lesson 2)
AggregateDomain-driven design's term for a cluster of objects with a single root through which all changes pass, so the root can be the one place the rules are checked. The boundaries axis with a name. (Lesson 2)
Flag-plus-optionals encodingThe wrong shape on the entities axis: a status or kind field alongside optional fields that are meaningful for only some of its values. Permits the product of the two, of which the domain allows a handful. (Lesson 3)
Counting what the type permitsThe argument that turns a taste claim into arithmetic: enumerate the values the type allows against the states the domain allows. Each permitted-but-illegal combination is a bug someone must be prevented from writing by hand. (Lessons 3, 5)
Discriminated unionPer the TypeScript handbook, a union where every member shares a common property with literal types, letting the checker narrow out members. Each case carries only its own fields, so illegal combinations are not values. (Lesson 3)
NarrowingThe checker deducing a union's specific case from a test on the discriminant, so a case's fields are reachable only inside the matching branch. Reading them elsewhere is a compile error rather than undefined. (Lesson 3)
ExhaustivenessThe property that adding a case to a union fails compilation at every site that switches over it, converting "find the thirty places that care" into a worklist delivered before merge. (Lesson 3)
Transition functionThe single place that knows the legal order of states. A union removes illegal states, not illegal state changes, so this knowledge is real and must be concentrated rather than smeared across consumers. (Lesson 3)
Rejected vs unrepresentableThe distinction the entities axis turns on. A runtime guard rejects the illegal value, which means it stays constructible and the guard must be called everywhere forever. Unrepresentable means the value cannot be built. (Lesson 3)
ValidatingChecking input and returning nothing (None, void, bool). The fact it established survives one line, so every function downstream knows nothing and re-checks. (Lesson 4)
ParsingKing's definition: a function that consumes less-structured input and produces more-structured output. Returns a distinct type only it can construct, so holding that type is evidence the check happened. (Lesson 4)
Carrying the proofThe parsed type as evidence. A function taking TenantScopedUserId states its precondition in its signature instead of trusting callers. Frozen matters: a mutable value's proof expires silently. (Lesson 4)
Push the burden of proof upward, but no furtherParse where the raw input actually enters. Pushed further, callers that never saw the raw input must fabricate the type to satisfy a signature, which destroys the guarantee. (Lesson 4)
Shotgun parsingFrom the LangSec literature via King: parsing and input-validating code mixed with and spread across processing code, so processing begins before validation finishes and the program can act on input it later rejects. (Lesson 4)
The DRF dict gap.validated_data is a plain dict, so a serializer performs a full parse and then discards the proof at the view boundary. The fix is a frozen dataclass built from it at that boundary, with inner layers taking that type. (Lesson 4)
Flag argumentFowler: an argument that tells the function to carry out a different operation depending on its value. The shape fault specifically is a flag that changes what the rest of the signature means. (Lesson 5)
Coupled parameterA parameter whose necessity depends on another parameter's value: optional in the signature, mandatory in one branch of the body. Makes the wrong combination a legal call. (Lesson 5)
Silent under-enforcementThe failure mode of the coupled-parameter validator: omitting the argument does not raise, it validates fewer things and reports success. The worst outcome available to a validator, since being told was the whole point of the call. (Lesson 5)
Shape is not DRYSplitting one entry point into two does not duplicate anything if the mechanism stays shared underneath. The target is the branch that permitted the illegal combination, not the repeated lines. (Lesson 5)
Interface complexityOusterhout's measure: what a caller must know. A single signature plus an undocumented rule about legal parameter combinations is more to know than two honest signatures, even though it is fewer entry points. (Lessons 5, 7)
Search pathPostgres resolves an unqualified table name by walking a list of schemas, first match wins. Pointing it at a tenant's schema scopes every unqualified query, which is why forgetting to set it yields a correct query against the wrong tenant. (Lesson 6)
Entry point (door)A way execution enters the system: HTTP request, background task, management command, shell session, scheduled job. Finite, knowable, and rarely changing, which is what makes it auditable. (Lesson 6)
ChokepointEnforcement placed on the only path in, so application code cannot run without it: middleware for HTTP, an app-wide task base class for workers. On the path, not beside it. (Lesson 6)
Convention-based enforcementAsking an unbounded set of present and future call sites to remember a step. No audit over that set can complete, and its reliability decays with turnover, deadlines, and code volume. (Lesson 6)
Structural enforcementEnforcement at each door, so the rule holds for code whose author never heard of it. Indifferent to turnover and deadline pressure, because nobody had to know. (Lesson 6)
Beside the path, not on itThe test that catches a helper masquerading as structure. A correct shared function everyone is supposed to call is convention with better ergonomics: the guarantee still depends on remembering. (Lesson 6)
Bypass auditChecking each door for a way application code can run without passing the wrapper. Usual finds: a task not inheriting the base, a management command, a raw connection or second database alias, a middleware ordered too low. (Lesson 6)
Invariant testA test that asserts the rule rather than the mechanism: enter through each door, run something that would violate the invariant if enforcement were missing, assert it does not. Fails when a new door appears unprotected. (Lessons 6, 7)
The two axesCorrectness ("can this be violated by later code?", binary) and visibility ("can a reader tell that it cannot?", a gradient). No amount of the second changes the first. Settle correctness, then spend on visibility. (Lesson 7)
Naming the splitThe move that unsticks a stalled design argument: state which axis each side is on. "We agree the invariant must be structurally enforced. We are disagreeing about how visible the enforcement should be." (Lesson 7)
Buying visibilityLoud names (TenantScopedTask), an invariant test, documentation at the chokepoint, and where the tradeoff is worth it, an explicit decorator at the definition. Never a redundant check at the call site. (Lesson 7)
Signal inversionWhat belt-and-braces produces: once a redundant call-site reset becomes the norm, safe paths that omit it look wrong and bypassed paths that include it look safe. Visibility bought with the correctness property it was meant to display. (Lesson 7)
Design noteA ten-minute prose document written before code on any non-trivial ticket: entities, invariants, lifecycle if applicable, boundaries, options with tradeoffs, chosen approach, then the last question. Prose because a rule you cannot state as a sentence has not been decided. (Lesson 8)
The last question"What would make the wrong thing impossible, not just unlikely, here?" The gate. Unanswerable means the design is unfinished, even when it is entirely clear how to start typing. Those two states feel identical. (Lesson 8)
Retro-fit exerciseWriting the design note after the fact for code already shipped. The gaps between note and code are the conceptual mismatches, measured rather than guessed. The only exercise here with a checkable answer. (Lesson 8)
Using this. The first table is for talking to other engineers; the second is for thinking. If a term here is doing less work than its definition claims, say so and it gets cut or sharpened.
