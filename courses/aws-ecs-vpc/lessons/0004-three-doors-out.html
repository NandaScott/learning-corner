The three doors out

An internet gateway, a NAT gateway, and a VPC endpoint look like three unrelated services. They are one idea seen three ways. Each answers the same question differently: who is allowed to start the conversation, and does the traffic leave the AWS network at all.

The concept

A private network with no exits is not useful. Applications call payment APIs, pull container images, write to object storage, and receive requests from customers. Each of those crosses the VPC boundary, and AWS gives three ways across. They are all route targets, in the sense of Lesson 3, so adding one is always the same move: create the door, then point a route at it.

The difference between them is direction and path.

One question, three answers. Memorise the question, not the list.

Step 1 — Internet gateway: two-way, and the only one that accepts inbound

An internet gateway is attached to a VPC and "enables your instances to connect to the internet through the Amazon EC2 network edge."1 It is the door a public subnet's default route points at, and it is the only one of the three through which something outside can open a connection to something inside.

Being able to accept inbound does not mean everything inside becomes reachable. The resource still needs a public address, and the filtering layer still applies. What the gateway provides is the possibility.

Step 2 — NAT gateway: outbound only, by construction

The docs state the purpose in one sentence: "You can use a NAT gateway so that instances in a private subnet can connect to services outside your VPC but external services can't initiate a connection with those instances."2 And the constraint that makes it a design tool: "Connections must always be initiated from within the VPC containing the NAT gateway."2

The placement surprises people. A public NAT gateway "is created in a public subnet and must associate an Elastic IP address with the NAT gateway at creation", and traffic is routed from it to the internet gateway.2 So the device that serves private subnets does not live in one. The private subnets route 0.0.0.0/0 to the NAT gateway, and the NAT gateway, sitting in a public subnet, routes onward to the internet gateway.

The translation is what removes the inbound path: the NAT gateway maps the source private address of the instance to its own address, and translates the answer back on the way in.2 Nothing outside ever learns an address that reaches the instance directly.

Step 3 — VPC endpoint: do not leave the AWS network at all

Much of what an application calls is an AWS service: object storage, a secrets store, a container registry, a queue. Those services have public endpoints, so reaching them from a private subnet through a NAT gateway works. A VPC endpoint asks why the traffic should go out at all.

With AWS PrivateLink, clients in your VPC "connect to services and resources in other VPCs using private IP addresses, as if those services and resources were hosted directly in your VPC."3 Concretely, an interface endpoint puts an endpoint network interface in your subnet, with a private address, and "traffic between a VPC endpoint and an endpoint service or resource stays within the AWS network, without traversing the public internet."3

There is a second, older kind. A gateway endpoint sends traffic to Amazon S3 or DynamoDB and works through the route table rather than an interface, and the docs note that gateway endpoints "do not use AWS PrivateLink, unlike the other types of VPC endpoints."3 Two shapes, same intent: keep the call on the AWS network so no internet-facing door is needed for it.

Step 4 — Read the three as a single decision

Given any dependency, ask two questions in order. Does anything outside need to open a connection to us? If yes, an internet gateway is involved, and almost always with a load balancer in front rather than direct exposure. If no, is the dependency an AWS service that offers an endpoint? If yes, use the endpoint and keep the traffic internal. Otherwise a NAT gateway carries the outbound call.

Most real workloads use all three at once, for different flows, in the same VPC. That is normal and it is worth saying out loud in an interview, because it shows the three are not alternatives.

Why it matters

"Put it in a private subnet" is the standard security recommendation, and on its own it breaks things: an application in a private subnet with no doors cannot pull its image, call an API, or write a log. The doors are what make a private placement workable, and picking the right one is the difference between an architecture that is closed by default and one that is closed by accident.

The cost story follows the same lines. A VPC costs nothing, and a NAT gateway is one of the components AWS charges for, by the hour and by data processed.4 Which is why replacing NAT traffic to AWS services with endpoints is one of the first things a cost review looks at, and why an answer that reaches for endpoints unprompted reads as experienced.

Key line Three doors, one question: who may start the conversation. An internet gateway allows either side. A NAT gateway allows only the inside, because connections must be initiated from within the VPC. A VPC endpoint keeps the call on the AWS network, so nothing needs to face the internet for it.
The common trap The near-miss is calling a NAT gateway a firewall. It is an address translation device, and the inbound protection is a side effect of how translation works rather than a policy you configure. Nothing about it inspects or filters traffic, and it does not restrict what the inside may call out to. The related slip is putting the NAT gateway in the private subnet it serves. A public NAT gateway sits in a public subnet with an Elastic IP; the private subnets route to it.

Recall — answer out loud before peeking:

① Give the one question that separates the three doors, and answer it for each.

show answer

Who may initiate the connection. Internet gateway: either side. NAT gateway: only something inside the VPC, since connections must always be initiated from within the VPC. VPC endpoint: only the inside, and the traffic never leaves the AWS network.

② Which subnet does a public NAT gateway live in, and why is that not a contradiction?

show answer

A public subnet, with an Elastic IP address. It needs its own route to the internet gateway to do its job. Private subnets route their outbound traffic to it, so the private resources stay private while the device that relays for them does not.

③ A service in a private subnet reads from Amazon S3 through a NAT gateway. What is the alternative, and what changes?

show answer

A VPC endpoint for S3, which is a gateway endpoint reached through the route table. The traffic stays on the AWS network instead of going out through the NAT gateway and back, so no internet path is used for it.
