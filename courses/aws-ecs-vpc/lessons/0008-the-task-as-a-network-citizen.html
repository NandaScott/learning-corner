The task as a network citizen

Here the two halves meet. In awsvpc networking mode a task is not a process hiding behind a host's address. It gets its own network interface, its own private IP, and its own security group, which means everything learned about the VPC applies to it directly.

The concept

The docs state the goal in the first line: "The task networking features that are provided by the awsvpc network mode give Amazon ECS tasks the same networking properties as Amazon EC2 instances."1 Same properties means the VPC does not have a special category for containers. A task appears in the network the way anything else does, with an address drawn from a subnet.

The mechanism is one sentence of the same page: "Each Amazon ECS task that uses the awsvpc network mode receives its own elastic network interface (ENI)", and "Each task ENI is assigned a private IPv4 address by default."1 One task, one interface, one address.

The interface is created for the task and destroyed with it. Addresses are as temporary as the tasks are.

Step 1 — You hand ECS the network decisions from Arc 1

Running a task or creating a service takes a network configuration "that includes one or more subnets to place your tasks in and one or more security groups to attach to an ENI."1 Those are exactly the two objects from Lessons 2 through 5, and they carry exactly the meanings they had there.

Placement follows from the subnets: "The tasks are placed on compatible Amazon EC2 instances in the same Availability Zones as those subnets."1 Listing subnets in three zones is how a service becomes multi-zone. There is no separate availability setting. There are quotas on the inputs, currently 16 subnets and 5 security groups per network configuration.1

Step 2 — The security group now describes one task, not one machine

Because the group attaches to the task's own interface, two different services on the same infrastructure can have entirely different rules. The group-references-group idea from Lesson 5 becomes the natural way to express a tier: the database group allows the application group, and every task of that service inherits the permission by being launched with the group.

This is the concrete reason awsvpc is the default in modern ECS. Filtering per workload, rather than per host, is what makes a shared cluster safe to reason about.

Step 3 — Containers in one task share the interface

A task can hold several containers, and they do not each get an address. They share the task's network stack, so "all containers in a task are addressable by the IP addresses of the ENI, and they can communicate with each other over the localhost interface."1

That is the sidecar pattern's plumbing. An application container and a log forwarder in the same task reach each other on localhost, with no service discovery and no exposure to the rest of the VPC. Across tasks, localhost means nothing; those are separate interfaces and separate addresses.

Step 4 — Load balancing targets the address, not the host

A load balancer keeps a target group, the list of backends it forwards requests to, and registers or removes members as they come and go. With awsvpc there is a constraint: "When you create any target groups for these services, you must choose ip as the target type. Do not use instance. This is because tasks that use the awsvpc network mode are associated with an ENI, not with an Amazon EC2 Linux instance."1

The constraint is a consequence, not a rule to memorise separately. Once the task owns an address, the address is the thing worth registering. Lesson 9 puts the load balancer in place around this.

Step 5 — A private address means the doors from Lesson 4 apply

A task with only a private address reaches the internet the way anything else in a private subnet does, and it usually needs to, because pulling its image is itself an outbound call. For Fargate the docs enumerate the options exactly: "For a task on Fargate to pull a container image, the task must have a route to the internet", satisfied by assigning a public IP address to the task ENI in a public subnet, by a NAT gateway attached to a private subnet, or by configuring an Amazon ECR interface VPC endpoint so that "the image pull occurs over the task's private IPv4 address."2

One asymmetry is worth knowing because it contradicts the pattern. When tasks run on EC2 instances you manage, "your task ENIs aren't given public IP addresses", so internet access there means a private subnet with a NAT gateway; a public subnet does not help.1 The public IP option is specific to Fargate.

Why it matters

This lesson is the reason the VPC half came first. Every ECS networking question resolves into a VPC question about an ENI: which subnet gives it an address, which security group is attached, which route table serves that subnet, which door it uses to leave. Nothing new appears at the container layer.

It also changes what "the same machine" means. Two tasks on one EC2 instance are two interfaces with two addresses and possibly two different security groups, and they cannot reach each other on localhost. Container-level intuitions from a single Docker host do not transfer, and that gap is a favourite interview probe.

Key line In awsvpc mode the task is a first-class citizen of the VPC: its own elastic network interface, its own private IP from a subnet you chose, its own security groups. Containers inside one task share that interface and talk over localhost. Target groups must use the ip target type, because the target is an interface rather than an instance.
The common trap The near-miss is the single-Docker-host model: containers share the host's address and are reached on mapped ports, so a security group covers everything on the box. That describes a different network mode, and under awsvpc it is wrong in every part. Each task has its own interface and address, security groups apply per task, and two tasks on one instance cannot reach each other over localhost. The follow-up that catches people is the target type: registering instance targets for tasks that are addressed by interface.

Recall — answer out loud before peeking:

① What does a task get in awsvpc mode, and what two inputs does ECS need to give it?

show answer

Its own elastic network interface with a private IPv4 address. The inputs are one or more subnets to place the task in and one or more security groups to attach to the interface.

② Why must target groups for these services use the ip target type?

show answer

Because the task is associated with an elastic network interface rather than with an EC2 instance, so the address is what gets registered. Instance targets would name a host that is not the unit being balanced.

③ A Fargate task in a private subnet fails to start, reporting that it cannot pull its image. Name two fixes consistent with this lesson.

show answer

Give the subnet a route to a NAT gateway, or configure an Amazon ECR interface VPC endpoint so the pull happens over the task's private address. Moving it to a public subnet works only with a public IP assigned to the task ENI.
