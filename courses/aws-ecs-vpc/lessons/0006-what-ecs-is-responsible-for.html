What ECS is responsible for

Amazon ECS is a control loop with four nouns around it. Learn the loop and the nouns stop being vocabulary: a cluster holds capacity, a task definition describes a unit of work, a task is one running copy, and a service is the promise that a number of copies keeps being true.

The concept

AWS describes ECS as "a fully managed container orchestration service that helps you easily deploy, manage, and scale containerized applications."1 Orchestration is the part worth unpacking. A container image on its own answers "what should run." Orchestration answers everything else: where it runs, how many copies, what happens when one dies, what happens when the machine under it dies, and how traffic finds the copies that are alive.

The docs split ECS into three layers: capacity, "the infrastructure where your containers run"; controller, which deploys and manages the applications; and provisioning, the tools you use to talk to the scheduler.1 This lesson is the controller. The next one is capacity.

The loop is the product. Everything else is an input to it.

Step 1 — A task definition is a blueprint, not a running thing

"A task definition is a blueprint for your application. It is a text file in JSON format that describes the parameters and one or more containers that form your application."2 It names the images to run, how much CPU and memory to give them, the networking mode, the logging configuration, the command to run, and the IAM role the application uses.2

Nothing runs when you write one. It is a registered document, versioned as numbered revisions, and deploying a change means registering a new revision and pointing something at it. Multiple containers can appear in one task definition, which is how a sidecar such as a log forwarder travels with the application.

Step 2 — A task is one running instantiation of it

"A task is the instantiation of a task definition within a cluster."2 One task is one copy of that blueprint, running now, with its own resources. If the blueprint lists three containers, the task is all three together, placed as a unit and living and dying as a unit.

Tasks can be run directly, which suits a batch job: start, do work, exit. The docs use exactly that framing, describing a task as "an application such as a batch job that performs work, and then stops."1

Step 3 — A service keeps a count of tasks true

A long-running application should not stop when a task stops. That is what a service adds: "You can use an Amazon ECS service to run and maintain a specified number of instances of a task definition simultaneously in an Amazon ECS cluster. If one of your tasks fails or stops, the Amazon ECS service scheduler launches another instance of your task definition to replace it."3

That is the control loop, stated in the docs' own words. You declare a desired count; the scheduler compares it with what is actually running and acts on the difference. It also acts on health rather than only on crashes: the scheduler "replaces tasks determined to be unhealthy after a container health check or a load balancer target group health check fails."3 Replacement is ordered deliberately, starting the replacement before stopping the unhealthy task where capacity settings allow it.3

Two more behaviours are worth naming because they show up as interview follow-ups. A service can sit behind a load balancer, which "distributes traffic across the tasks that are associated with the service."3 And service auto scaling "is the ability to increase or decrease the desired number of tasks in your Amazon ECS service automatically", implemented through Application Auto Scaling.3 Scaling changes the number the loop is aiming at; the loop itself does not change.

Step 4 — A cluster is the boundary the loop runs inside

"An Amazon ECS cluster is a logical grouping of tasks or services that provides the infrastructure capacity for your containerized applications."4 Two things follow. It is a grouping, so it is a boundary for organisation and for access control rather than a machine. And "clusters are AWS Region specific", so it does not span Regions.4

A cluster also carries the network that its work runs in. The docs list among its components "the network (VPC and subnet) where your tasks and services run."4 That line is where the two halves of this course start to touch.

Why it matters

Almost every ECS question is answerable by asking which of the four nouns it is about. "How do I change the image?" is a task definition question. "Why did it come back after I killed it?" is a service question. "Why is it in the wrong Availability Zone?" is a cluster and network question. "Why did this one exit and nothing replaced it?" means a standalone task rather than a service.

The loop framing also explains the shape of the whole system. Nothing in ECS is imperative for long. You do not start copies; you state how many should exist. Deployments, scaling, and failure recovery are all the same mechanism viewed at different moments, which is why they share one set of settings.

Key line ECS is a control loop over four nouns. The task definition is the blueprint, a task is one running copy, a service holds a desired count of copies and replaces the ones that fail or go unhealthy, and the cluster is the Region-scoped grouping that provides the capacity.
The common trap The near-miss is describing a cluster as a pool of machines. It is a logical grouping that provides capacity, and where that capacity comes from is a separate choice, which is the next lesson. Saying "a cluster is a set of EC2 instances" commits you to one answer and makes the serverless case sound like an exception rather than a normal configuration. The related slip is using "task" and "task definition" interchangeably; the distinction between a blueprint and an instance is the one an interviewer is checking.

Recall — answer out loud before peeking:

① Define task definition, task, service, and cluster in one sentence each.

show answer

Task definition: a JSON blueprint describing one or more containers and their parameters. Task: one running instantiation of that blueprint within a cluster. Service: a controller that runs and maintains a desired number of tasks, replacing any that fail or become unhealthy. Cluster: a Region-scoped logical grouping of tasks and services that provides the infrastructure capacity.

② You stop a task by hand and another appears seconds later. What happened, and what would have been different if nothing came back?

show answer

The task belonged to a service, so the scheduler saw actual fall below desired and launched a replacement. If nothing came back it was a standalone task, which has no controller keeping a count.

③ Besides a crash, what else causes the service scheduler to replace a task?

show answer

A failed health check, either a container health check or a load balancer target group health check. Where capacity allows, the scheduler starts the replacement first and then stops the unhealthy task.

Primary source — read this one Amazon ECS Developer Guide, "Amazon ECS services". It states the control loop in one paragraph and then spends the rest of the page on the cases that make it subtle: unhealthy task replacement, the interaction with maximum percent, and the throttle that slows repeated failed launches.
