Who owns the box

The scheduler from Lesson 6 needs somewhere to put tasks. That somewhere is the capacity layer, and choosing it is one question asked in several ways: how much of the machine do you want to be responsible for?

The concept

ECS separates the controller from the capacity, which is why the same service definition can run on very different infrastructure. The docs list the capacity options plainly: EC2 instances in the AWS cloud, where "you choose the instance type, the number of instances, and manage the capacity"; serverless, where "Fargate is a serverless, pay-as-you-go compute engine"; ECS Managed Instances, where AWS "handles provisioning, patching, scaling, and maintenance of the underlying infrastructure"; and on-premises servers registered through ECS Anywhere.1

Read them as points on one axis rather than four products.

Step 1 — Fargate removes the fleet from the picture

"AWS Fargate is a technology that you can use with Amazon ECS to run containers without having to manage servers or clusters of Amazon EC2 instances. With AWS Fargate, you no longer have to provision, configure, or scale clusters of virtual machines to run containers. This removes the need to choose server types, decide when to scale your clusters, or optimize cluster packing."2

What you declare instead is the shape of the task: "you package your application in containers, specify the CPU and memory requirements, define networking and IAM policies, and launch the application."2 Isolation is per task, and the docs are specific about it: "Each Fargate task has its own isolation boundary and does not share the underlying kernel, CPU resources, memory resources, or elastic network interface with another task."2

Because there is no host you own, there is also no host you patch. Fargate exposes platform versions instead, "a combination of the kernel and container runtime versions", and a new task "always runs on the latest revision of a platform version, ensuring that tasks are always started on secure and patched infrastructure."2 Patching becomes a property of starting a new task.

Step 2 — EC2 capacity keeps the fleet, and the control that comes with it

With EC2 capacity you register instances to the cluster and the scheduler places tasks onto them. You pick the instance types, so you can reach things Fargate does not offer, and you decide how full the machines run. The docs frame the choice around needing "specific instance types or configurations", existing EC2 infrastructure, "custom AMIs or specialized software", or "maximum control over the underlying infrastructure."3

The cost model differs in kind, not only in rate. Instances are billed while they exist, whether or not tasks fill them, so packing and scaling the fleet is your problem and your opportunity. Fargate bills per task. That is the real content of most "which is cheaper" debates.

Step 3 — ECS Managed Instances is the middle, and it is the current default advice

"Amazon ECS Managed Instances is a compute option for Amazon ECS that enables you to run containerized workloads on a range of Amazon EC2 instance types while offloading infrastructure management to AWS."1 You get EC2 instance characteristics such as GPU acceleration or specific CPU architectures, and AWS handles provisioning, patching, scaling, and lifecycle management.3

The docs currently call it "the recommended choice for most new workloads."3 Worth knowing by name: it is recent enough that many people's mental model of ECS still has only two options in it.

Step 4 — Launch type or capacity provider, and clusters can mix

Two ways to say where a task should go. A launch type "causes Amazon ECS to launch our tasks directly on either Fargate or on the EC2 instances registered to your clusters."4 A capacity provider strategy distributes tasks "in one or across multiple capacity providers", with weights, and a cluster can have a default strategy.3

The flexible part is that these are per-workload, not per-cluster: "A cluster can contain a mix of tasks that are hosted on Amazon ECS Managed Instances, AWS Fargate, Amazon EC2 instances, or external instances."3 Fargate Spot is the common reason to use a strategy rather than a launch type, since it "runs tasks on spare compute capacity" at a discount and interrupts them "with a two-minute warning" when AWS needs it back.2 A strategy can put a baseline on regular Fargate and the surge on Spot.

Why it matters

This is the ECS question that actually gets asked, and the weak version of the answer is a preference. The strong version names the axis. Fargate trades control and per-unit price for the disappearance of an entire operational surface: no AMIs, no fleet scaling, no bin packing, no patch windows. EC2 capacity keeps that surface because something about the workload needs it, and a reason worth naming is a reason like GPUs, a specialised AMI, or existing committed capacity.

It also explains why the capacity choice barely touches the rest of the design. The service and its desired count do not change. The next lesson shows that the networking does not change much either, which is the part that surprises people.

Key line Fargate against EC2 is one question: who owns the machine. Fargate means AWS owns it, you declare CPU and memory per task, and patching is a property of launching a new task. EC2 capacity means you own the fleet, its types, its packing, and its idle time. Managed Instances sits between them and is what the docs now recommend for most new workloads.
The common trap The near-miss is treating this as a cluster-wide, one-time decision. A cluster can hold tasks on Fargate, on EC2 instances, on Managed Instances, and on external instances at the same time, and a capacity provider strategy can split a single service across providers with weights. The most common real design is exactly that split: steady capacity on one provider, burst on Fargate Spot, which is interruptible with a two-minute warning.

Recall — answer out loud before peeking:

① State the axis the capacity options sit on, and place Fargate and EC2 on it.

show answer

How much of the machine you own. Fargate: AWS owns it, no instances to provision, configure or scale, and each task has its own isolation boundary. EC2: you choose instance types and numbers and manage the capacity yourself.

② There is no host to patch under Fargate. So how do tasks get security updates?

show answer

Through platform versions, which pair a kernel with a container runtime. AWS publishes new revisions, and a new task always starts on the latest revision, so replacing tasks is what applies the update.

③ A workload needs GPU instances for one component and has a bursty stateless web tier. Does that force two clusters?

show answer

No. One cluster can mix capacity types. The GPU component uses EC2 or Managed Instances capacity; the web tier uses Fargate, optionally with a capacity provider strategy that sends burst tasks to Fargate Spot.
