Failure-handling cheat sheet

One page for designing what happens to a failed JetStream message. Defaults are from nats-server source at v2.16.0-dev (latest stable v2.15.0) and nats.js v3.4.0. Terms follow the glossary.

The DLQ pattern

  1. Consumer: ack_policy: explicit, finite max_deliver, optional backoff.
  2. Handler: ack on success, nak(delay) on transient errors, term(reason) on permanent ones, working() for long jobs. Idempotent on a natural ID.
  3. Capture stream bound to $JS.EVENT.ADVISORY.CONSUMER.MAX_DELIVERIES.<stream>.* and …MSG_TERMINATED.<stream>.*, created with the source stream. Advisories are published once, never stored, and skipped with no interest.
  4. DLQ worker: read stream + stream_seq, call jsm.streams.getMessage(stream, { seq }) (leader read; returns null if gone). Avoid Direct Get here: not read-after-write coherent.
  5. Copy payload and headers to dlq.<stream>.<consumer> with advisory type, deliveries, reason. Publish with msgID = advisory id; ack the advisory last.
  6. WorkQueue source: jsm.streams.deleteMessage(stream, seq) after the copy.
  7. Replay: republish from the DLQ stream to the original subject after the fix. Watch the duplicate window if the original Nats-Msg-Id is reused.

Advisory payloads

AdvisorytypeFields
MAX_DELIVERIESio.nats.jetstream.advisory.v1.max_deliverid, timestamp, stream, consumer, stream_seq, deliveries
MSG_TERMINATEDio.nats.jetstream.advisory.v1.terminatedas above plus consumer_seq, reason
MSG_NAKEDio.nats.jetstream.advisory.v1.nakas above plus consumer_seq

No advisory carries the message body or headers. jsm.advisories() in nats.js is a core subscription and has no nak kind: monitoring only, not a DLQ source.
