NATS and JetStream for failure handling · Reference

Glossary

Canonical vocabulary for this course. Every lesson uses these terms as defined here, following the NATS documentation. The last column of each row names the lesson that introduces the term. For defaults and outcome tables, see the failure-handling cheat sheet.

Core NATS

TermDefinition
Core NATSThe base publish-subscribe layer of NATS, with no persistence. Delivers each message at most once to subscribers interested at publish time. (Lesson 1)
SubjectA case-sensitive, dot-separated string the server uses to match publishers to subscribers. Never declared; the server tracks it only while something subscribes. (Lesson 1)
TokenOne dot-separated part of a subject. Wildcards match whole tokens. (Lesson 1)
* wildcardSubscriber-only. Matches exactly one token, not zero and not two. (Lesson 1)
> wildcardSubscriber-only. Matches one or more tokens; must be the last token. (Lesson 1)
Reserved subjectsSubjects starting with $, used by the system. $JS. holds the JetStream API and advisories. (Lesson 1)
At-most-onceThe core NATS guarantee. A subscriber that is connected and interested at publish time gets one copy; one that is absent, slow or disconnected gets zero. No retry. (Lesson 1)
Fire-and-forgetCore publish behaviour: the call hands the message to the server and returns, with no report of who received it. (Lesson 1)
InterestThe set of current subscriptions matching a subject. A message published with no interest is discarded silently. (Lesson 1)
JetStreamThe NATS persistence layer, built into the server. Adds storage, redelivery and replay on top of core NATS. (Lessons 1, 3)

Core NATS: queue groups and request-reply

TermDefinition
Queue groupA set of subscribers on the same subject sharing a group name. The server treats it as one logical subscriber and delivers each message to exactly one member. Nothing is configured on the server, and nothing is stored: a member that dies after delivery loses the message. (Lesson 2)
Request-replyPublish and subscribe used twice: the request carries a reply subject, and the responder publishes its answer there. At most once in both directions, so every request has a timeout. (Lesson 2)
InboxThe private reply subject for a request, under the reserved _INBOX. prefix. A client subscribes once to a wildcard inbox and gives each request a fresh last token. (Lesson 2)
No respondersAn immediate reply with status 503 and no payload, sent when a request's subject has no subscribers. In nats.js v3 a RequestError whose cause is NoRespondersError. Distinct from a timeout. (Lesson 2)

JetStream: streams and consumers

TermDefinition
StreamA JetStream store on the server that keeps every message published on its subjects. A subject may be bound by only one stream. (Lesson 3)
Stream sequenceThe number a stream assigns to each stored message. Starts at 1, only increases, never reused. The message's permanent address in the stream. (Lesson 3)
PubAckThe server's reply to a JetStream publish: stream name, stream sequence, and a duplicate flag. Confirms storage, not delivery to any consumer. (Lesson 3)
StorageFile (default) or memory. Memory storage does not survive a server restart. Fixed at creation. (Lesson 3)
ReplicasHow many servers hold a copy of a stream. Default 1, maximum 5. (Lesson 3)
LimitsMaxAge, MaxMsgs, MaxBytes (and per-subject and size caps). Unlimited by default; whichever is reached first triggers a discard. Apply under every retention policy. (Lesson 3)
Discard policyWhat happens at a limit. DiscardOld (default) deletes the oldest messages; DiscardNew rejects the new publish. (Lesson 3)
Retention policyWhat makes a message ready to leave a stream besides limits. One per stream, not editable after creation. Limits, Interest, or WorkQueue. (Lesson 3)
Limits retentionThe default. Messages leave only by limits; reading and acking change nothing. (Lesson 3)
Interest retentionA message is removed once every consumer whose filter covers it has acked it, or immediately if no consumer is interested when it arrives. (Lesson 3)
WorkQueue retentionA message is removed by the first ack. For job queues where each message is work for one worker. (Lesson 3)
Nats-Msg-Id / duplicate windowA publish header carrying a stable ID. Within the stream's duplicate window (default 2 minutes) a repeated ID is stored once and its PubAck reports duplicate: true. (Lesson 3)
Per-message TTLThe Nats-TTL header (server 2.11+) on a stream with AllowMsgTTL, which can be enabled but never disabled. A deadline on the stored copy. (Lesson 3)
ConsumerA server-side cursor on a stream. Tracks how far its clients have progressed and hands out the next message. Reading through a consumer moves its position only; it does not remove the message from the stream. (Lesson 4)
Durable consumerA consumer created with a durable name. The server keeps its position under that name across disconnects and restarts. The right choice for any service that must not miss work. (Lesson 4)
Ephemeral consumerA consumer with no durable name. No persisted state or fault tolerance; removed automatically after a period of inactivity. (Lesson 4)
Inactive thresholdConsumer setting controlling automatic cleanup after inactivity. Does not make a consumer durable; applies to durables too since server 2.9. (Lesson 4)
Pull consumerA consumer where the client asks for messages when ready. The default and recommended kind. In nats.js: next, fetch, or consume. (Lesson 4)
Push consumerThe older model, where the server sends messages to a deliver subject on its own. Not used in this course. (Lesson 4)
Consumer sequenceA per-consumer counter bumped on every delivery, redeliveries included. Counts handovers, not distinct messages; contrast stream sequence. (Lesson 4)
Deliver policyWhere a consumer starts: all (default), last, last_per_subject, new, or a start sequence or time. Not editable after creation. (Lesson 4)
Filter subjectA subject pattern on a consumer. The consumer receives only stored messages whose subject matches; the rest of the stream is skipped. (Lesson 4)

Acks and giving up

TermDefinition
At-least-onceThe JetStream guarantee with explicit acks: a message stays available and is redelivered until a reader confirms it. Handlers may see a message more than once, so they must be idempotent. (Lesson 5)
Ack policyConsumer setting for whether and how deliveries are answered. explicit: each message answered (the basis for redelivery). none: done on delivery, no redelivery. all: one ack retires every earlier message. Not editable after creation. (Lesson 5)
Pending listThe consumer's record of delivered messages that have not yet received a final answer. (Lesson 5)
AckWaitHow long the server waits for an answer before treating a delivery as failed and redelivering it. Default 30 seconds. (Lesson 5)
ackFinal answer: the work succeeded. Removes the message from the pending list; never delivered again to this consumer. nats.js m.ack(). (Lesson 5)
nakFinal answer for this delivery: the work failed, redeliver. Plain nak redelivers at once; m.nak(millis) delays it (server 2.7.1+). Returns the message to the consumer, not the same worker. (Lesson 5)
termFinal answer: this can never succeed. Clears the pending entry like an ack and is never redelivered to this consumer. Moves the message nowhere. Optional reason string (server 2.11+). nats.js m.term(reason). (Lesson 5)
in-progressNot a final answer: resets the AckWait timer for a long job. nats.js m.working(). (Lesson 5)
Delivery countHow many times this consumer has handed out a message. nats.js m.info.deliveryCount; m.redelivered is true above one. (Lesson 5)
MaxAckPendingCap on delivered-but-unanswered messages for a consumer, shared across all its workers. Delivery stops when reached. Default 1000. (Lesson 5)
MaxDeliverConsumer setting capping how many times a message is delivered, the first delivery included; nak and AckWait redeliveries both count. Default -1, unlimited. Reaching it stops delivery to that consumer without acking or deleting the message. (Lesson 6)
BackOffConsumer list of delays for redeliveries caused by an AckWait timeout. Replaces AckWait: the first entry becomes the ack deadline for the first delivery; the last entry repeats. Does not slow a nak. Server 2.7.1+. (Lesson 6)
Poison messageA message that fails every time it is processed, typically a malformed payload. With unlimited MaxDeliver it is redelivered forever and holds a MaxAckPending slot. Handled with term or a finite MaxDeliver. (Lesson 6)
Consumer pauseServer 2.11 feature that stops a consumer's delivery until a deadline, keeping its position and redelivery counts. An alternative to burning delivery attempts during an outage. (Lesson 6)

Advisories and the DLQ pattern

TermDefinition
AdvisoryA transient JSON message JetStream publishes once, on a subject under $JS.EVENT.ADVISORY., when something notable happens to a stream or consumer. Travels over core NATS: not stored unless a stream captures it, and not published at all when nothing is subscribed. (Lesson 7)
Max-deliveries advisoryAdvisory of type io.nats.jetstream.advisory.v1.max_deliver on $JS.EVENT.ADVISORY.CONSUMER.MAX_DELIVERIES.<stream>.<consumer>. Sent once when a message reaches MaxDeliver; only if MaxDeliver is greater than zero. Fields: type, id, timestamp, stream, consumer, stream_seq, deliveries. (Lesson 7)
Terminated advisoryAdvisory of type io.nats.jetstream.advisory.v1.terminated on …CONSUMER.MSG_TERMINATED.<stream>.<consumer>, sent when a handler terms a message. Adds consumer_seq and the optional reason text. (Lesson 7)
Nak advisoryAdvisory of type io.nats.jetstream.advisory.v1.nak on …CONSUMER.MSG_NAKED.<stream>.<consumer>, sent on every nak. (Lesson 7)
Capture streamA stream whose subjects are advisory subjects, so each advisory is stored as a normal message. Also counts as interest, so the server publishes the advisory in the first place. (Lesson 7)
Dead-letter queue (DLQ)A durable place where messages a consumer gave up on end up, with enough context to inspect and replay them. JetStream has none built in; on NATS it is a stream the design creates and fills. (Lesson 8)
Advisory-capture streamA stream bound to advisory subjects (for a DLQ, MAX_DELIVERIES and MSG_TERMINATED for one source stream). It counts as interest and keeps each advisory until a worker acks it, so give-up events survive worker downtime. (Lesson 8)
DLQ workerA consumer on the capture stream that fetches each failed message by stream_seq and copies payload and context headers into the DLQ stream. Itself an ordinary JetStream consumer: naks on transient failure, acks last. (Lesson 8)
Copy at captureRepublishing the original payload into the DLQ stream when the advisory is processed, so the dead letter no longer depends on the source stream's retention or limits. (Lesson 8)
Stream message getjsm.streams.getMessage(stream, { seq }): reads one stored message by sequence from the stream leader. Returns null in nats.js v3 when the message is gone. (Lesson 8)
Direct GetA by-sequence or by-subject read any replica can answer (allow_direct, server 2.9.0). Not read-after-write coherent, so not the first choice for DLQ lookups. (Lesson 8)
ReplayRepublishing dead letters to their original subject after the defect is fixed. A reused Nats-Msg-Id inside the duplicate window is refused. (Lesson 8)
Error classThe handler's classification of a failure, which decides its response: success (ack), permanent (term with reason), known transient (nak with delay), slow but healthy (working), unknown (no response; AckWait and BackOff take over). (Lesson 9)
Retry windowRoughly the sum of the delays the max_deliver budget reaches. An outage longer than the window sends in-flight messages to the DLQ. (Lesson 9)
Idempotent handlerA handler that produces the same result when it processes a message twice, keyed on a natural ID. Required because JetStream delivery to consumers is at least once. (Lesson 9)
