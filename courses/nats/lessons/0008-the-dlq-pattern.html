NATS and JetStream for failure handling · Arc 3 · Lesson 8

The DLQ pattern on NATS

JetStream has no dead-letter queue setting. What it has is the set of parts one is built from: a bounded delivery count, a terminate response, advisories that name the failed message by stream sequence, and streams to hold whatever needs keeping. This lesson assembles them into a dead-letter queue and names the places where the assembly can leak.

The concept

The docs are blunt: "JetStream has no built-in dead-letter queue."1 The Synadia blog says the same and goes further: "There is no dead_letter: true field on a consumer. What NATS has instead is the set of primitives you assemble one from, and the DLQ you build is an ordinary JetStream stream."2 No release up to nats-server 2.15 adds one. The only mentions of DLQ in the server source are comments calling these advisories "a candidate for DLQ handling."3

A dead-letter queue here means a durable place where messages that a consumer gave up on end up, with enough context to inspect them and replay them. On NATS that place is a stream the design creates, and something the design runs has to put messages into it.

Five parts. Only the advisory is produced by the server; every box after it is something the design owns.

Step 1 — Make the failure produce a signal

The pattern starts on the consumer, with the settings from Lessons 5 and 6. The consumer needs an explicit ack policy and a finite max_deliver, because the max-deliveries advisory never fires under the default of -1 (unlimited).3 The handler acks on success, naks with a delay on a transient failure, and terms a message it knows can never succeed. Each give-up path then produces one advisory from Lesson 7: MAX_DELIVERIES when the budget runs out, MSG_TERMINATED when the handler terms.

Both carry stream, consumer and stream_seq. Neither carries the message body or its headers.4 The advisory is a pointer to the failed message, not a copy of it.

Step 2 — Capture the advisories in a stream

Advisories are transient. "An advisory is published exactly once, the moment its event fires, and it is not stored in any stream."5 The server also skips publishing an advisory when nothing in the account is subscribed to its subject.6 A DLQ worker that subscribes with core NATS loses every event that fires while it is restarting.

The documented fix is a stream bound to the advisory subjects, which is always listening and counts as interest.5 The docs bind all of $JS.EVENT.ADVISORY.>; a DLQ only needs the two give-up subjects for its own source stream. Composed from verified nats.js v3 APIs (not run):7

import { nanos } from "@nats-io/transport-node";
import { AckPolicy, RetentionPolicy, StorageType } from "@nats-io/jetstream";

await jsm.streams.add({
  name: "ORDERS_DLQ_EVENTS",
  subjects: [
    "$JS.EVENT.ADVISORY.CONSUMER.MAX_DELIVERIES.ORDERS.*",
    "$JS.EVENT.ADVISORY.CONSUMER.MSG_TERMINATED.ORDERS.*",
  ],
  storage: StorageType.File,
  retention: RetentionPolicy.Workqueue,   // each advisory handled once
  max_age: nanos(7 * 24 * 60 * 60 * 1000),
});
await jsm.consumers.add("ORDERS_DLQ_EVENTS", {
  durable_name: "dlq-worker",
  ack_policy: AckPolicy.Explicit,
});

The capture stream must exist before the first failure. An advisory that fires while it is missing is lost for good, and nothing records the loss.

Step 3 — Fetch the original by stream sequence

The DLQ worker consumes the capture stream, reads stream and stream_seq from each advisory, and asks the source stream for that message. In nats.js, jsm.streams.getMessage(stream, { seq }) sends the request to the stream leader, so it always sees the latest state.8 Direct Get (jsm.direct.getMessage) can be answered by any replica, and the docs warn it "is not read-after-write coherent."8 For a DLQ lookup, prefer the leader read.

In v3, getMessage returns null when the message no longer exists.7 The worker has to handle that case. The failure-mode table below shows it happens in normal operation, not only after mistakes.

Step 4 — Copy the payload into a DLQ stream at capture time

The Synadia version of the pattern does not leave the failed message where it is. It republishes the original payload and headers to a subject such as dlq.<stream>.<consumer>, captured by its own DLQ stream.2 The blog states the reason: "on any retention policy that removes messages once they are terminally handled, capture the payload while it still exists."2 Once copied, the dead letter no longer depends on what the source stream does next. The DLQ stream itself is one call: await jsm.streams.add({ name: "DLQ", subjects: ["dlq.>"] }), the nats.js form of the blog's Go example.2

Composed worker (not run), adapted from the research notes:7

import { headers } from "@nats-io/transport-node";

type GiveUpAdvisory = {
  id: string; type: string; stream: string; consumer: string;
  stream_seq: number; deliveries: number; reason?: string;
};

const events = await js.consumers.get("ORDERS_DLQ_EVENTS", "dlq-worker");
for await (const m of await events.consume()) {
  const adv = m.json<GiveUpAdvisory>();
  try {
    const original = await jsm.streams.getMessage(adv.stream, { seq: adv.stream_seq });
    const h = headers();
    h.set("Dlq-Advisory-Type", adv.type);
    h.set("Dlq-Stream-Seq", String(adv.stream_seq));
    h.set("Dlq-Deliveries", String(adv.deliveries));
    if (adv.reason) h.set("Dlq-Reason", adv.reason);   // term reason only
    if (original === null) h.set("Dlq-Original-Missing", "true");
    else h.set("Dlq-Original-Subject", original.subject);
    await js.publish(`dlq.${adv.stream}.${adv.consumer}`,
      original?.data ?? "", { headers: h, msgID: adv.id });
    m.ack();
  } catch {
    m.nak(5_000);   // source stream unreachable: retry this advisory later
  }
}

The worker is an ordinary JetStream consumer, so it follows the same rules as any handler: nak on a transient failure, ack only after the DLQ publish returns its PubAck. Using the advisory's id as the Nats-Msg-Id is a composition, not a documented step. It makes a retry after a crash between publish and ack a duplicate the DLQ stream refuses, inside the 2-minute duplicate window from Lesson 3.

Step 5 — Clean up and replay

On a WorkQueue stream, a message that reached MaxDeliver "will remain in the stream and must be manually deleted via the JetStream API."9 After copying it, the worker can remove it with jsm.streams.deleteMessage(stream, seq).7 On a Limits stream nothing needs deleting; the original ages out with the stream's limits.

Replay is a publish. Once the defect is fixed, a tool reads the DLQ stream and republishes each payload to its Dlq-Original-Subject. The blog frames this as the benefit of the design: the DLQ "is itself a replayable stream."2 If the original publisher set a Nats-Msg-Id, a replay with the same ID inside the duplicate window is refused as a duplicate. That follows from Lesson 3's dedupe rule; it is an inference, not a documented warning.

One row needs a caveat. On an Interest stream, a message that hit MaxDeliver never gets an ack from that consumer, so it should stay until limits remove it. That is an inference from the Interest definition in Lesson 3, not a documented statement.

An alternative — the handler publishes the dead letter itself

A handler that detects a permanent failure already holds the full message and the error. It could publish a copy to dlq.> and then term. This is a composition of Lesson 5's primitives, not a documented NATS pattern, and its trade-offs follow from the mechanics. It keeps the payload even on a WorkQueue stream and can attach the real error. It cannot cover the MaxDeliver path, because when the budget runs out on a timeout, no handler is running to see the last failure. The publish and the term are also two separate calls, so a crash between them can leave a dead letter for a message that is redelivered. Designs that use it still need advisory capture for the timeout path.

Why it matters

The design doc's question, "what happens to a message that fails," has a precise answer on NATS once these parts are in place: the consumer stops delivering it, the server emits one advisory naming its stream sequence, a stream catches that advisory, and a worker copies the payload somewhere durable and replayable. Each arrow in that chain is a design decision with its own failure mode. Retention policy decides whether the original survives a term. Limits decide how long the worker can be down. The capture stream decides whether the signal survives at all.

For the Synadia Cloud evaluation, the absence of a DLQ setting is not a missing feature to work around. It is the normal NATS shape. What needs confirming with Synadia is narrower: that the account can bind advisory subjects to a stream, which server version is running, and what the plan allows in streams and consumers.

Key line A NATS dead-letter queue is three things the design builds: a stream that captures the give-up advisories, a worker that fetches each failed message by stream sequence, and a DLQ stream it copies the payload into while the payload still exists.
The common trap The near-miss is "capture the advisories and the DLQ is done." The advisory holds a stream sequence, not the message. On a WorkQueue or Interest stream a term removes the original as an ack would, and on any stream the limits can age it out, so a DLQ that stores only advisories can point at messages that no longer exist. The second slip is subscribing to advisories with core NATS or jsm.advisories(): both miss every event that fires while the subscriber is down.

Recall: answer before peeking.

① A DLQ worker reads a MSG_TERMINATED advisory for a WorkQueue stream and calls getMessage with its stream_seq. It gets null. Why, and what design change would have kept the payload?

show answer

A term is processed like an ack, and on a WorkQueue stream the first ack removes the message. The fix is to keep the payload before or at the term: have the handler record it, or use Limits retention so the original stays until limits remove it.

② Why does the pattern need a capture stream instead of a DLQ worker that subscribes to the advisory subjects directly?

show answer

Advisories are published once and never stored, and the server skips publishing when nothing is interested. A core subscription misses every advisory that fires while the worker is down. A stream bound to the subjects is always listening and keeps each advisory until the worker acks it.

③ Why use jsm.streams.getMessage rather than Direct Get for the lookup?

show answer

getMessage asks the stream leader, which always sees the latest state. Direct Get can be answered by any replica and is not read-after-write coherent, so it can lag behind.
