NATS and JetStream for failure handling · Arc 2 · Lesson 5

Acks and redelivery

A consumer hands a message to a worker and then waits for an answer. The worker can say done, failed, give up, or still working. If no answer comes in time, the server assumes the worker died and hands the message out again. This loop is what turns a stored message into at-least-once processing, and every failure-handling choice in a NATS design is made inside it.

The concept

The docs describe the loop as "one of the pieces that give JetStream its at-least-once delivery: a message stays available and is redelivered until a reader confirms it, so it's handled at least once even when things fail."1 The durable stream from Lesson 3 keeps the message. The consumer from Lesson 4 keeps track of which deliveries are still unanswered. An ack is the answer.

Whether answers are expected at all is set by the consumer's ack policy. Everything in this lesson assumes explicit, the policy for "work that must not be lost."2

Three final answers, one keep-alive, and a timeout that behaves like a nak the worker never sent.

Step 1 — Choose the ack policy

The ack policy has three values that matter for work consumers.2

explicit   each message is answered on its own; the basis for redelivery
none       done the moment it is delivered: no pending list,
           no AckWait, no redelivery
all        one ack answers every earlier message too

none gives up everything in this lesson; it is at-most-once again, with storage. all is cheaper but is a trap for parallel work: acking message 10 "also retires a message 7 that failed and was waiting to come back," which is silent data loss.2 The ack policy cannot be changed after the consumer is created.3

Step 2 — The pending list and AckWait

When the server delivers a message, it "keeps a copy on the pending list and starts a timer. If the answer never comes, the server assumes the worker stopped and delivers the message again."2 The timer is AckWait, and "it defaults to 30 seconds."2 A delivery that is not acked, nak'd, or kept alive before AckWait runs out is treated "as a silent failure" and redelivered.2

That timeout is what protects against a crashed worker, a killed pod, or a handler stuck on a network call. No code in the worker has to run for the message to come back.

Step 3 — The four answers

"A client answers a delivered message in exactly one of four ways."2

ack           the work succeeded; off the pending list, never delivered again
nak           the work failed; redeliver, at once or after a delay
term          this can never succeed; off the pending list, never delivered again
in-progress   still working; resets the AckWait timer, not a final answer

"ack, nak, and term are final. Each one closes out a delivery. in-progress extends the timer instead."2

nak is for transient failures: a dependency is briefly down, a row is locked, a rate limit was hit.2 A plain nak redelivers immediately, so "the message retries over and over with no pause"; the fix is a nak with a delay.2 Delayed nak needs server 2.7.1 or later.4 A nak "returns the message to the consumer, not to the worker that nak'd it," so the retry can land on a different replica.2

term is for permanent failures, such as a payload that will never parse. The server drops it from the pending list as it does for an ack, "but the work was never done."2 Term runs through the same path as an ack, so under the default Limits retention the message stays in the stream and other consumers still see it.2 A term can carry a reason string, which needs server 2.11 or later.5

in-progress resets AckWait "so a long job doesn't trip redelivery."2

In nats.js these are methods on the delivered message: ack(), nak(millis?), term(reason?), and working().5 A handler that maps outcomes to answers (composed from those signatures, not run against a server):

const c = await js.consumers.get("ORDERS", "shipping");
for await (const m of await c.consume()) {
  const order = parse(m.data);
  if (!order) { m.term("unparseable payload"); continue; }   // permanent

  const keepAlive = setInterval(() => m.working(), 10_000);    // long job
  try {
    await ship(order);
    m.ack();                                                   // success
  } catch {
    m.nak(5_000);                                              // transient: retry in 5s
  } finally {
    clearInterval(keepAlive);
  }
}

Step 4 — Recognise a redelivery

Each delivered message carries its delivery count. In nats.js, m.info.deliveryCount is the number of times this consumer has handed the message out, and m.redelivered is true when that count is above one.5 This is the per-message view of the consumer sequence from Lesson 4, which counts every handover.

Two consequences follow from at-least-once. A handler can see the same message more than once, for example when it finished the work but the ack was lost, or when the work outran AckWait. Handlers therefore need to be idempotent. And a redelivered message "arrives after later messages unless MaxAckPending is 1": redelivery does not hold the line for the failed message.2

Step 5 — MaxAckPending caps work in flight

MaxAckPending limits how many delivered-but-unanswered messages a consumer may have. The default is 1000 for explicit-ack consumers.6 The limit applies across every worker on the consumer, and delivery stops when it is reached.3

That makes it flow control. Set too low, it limits throughput; the docs note that a worker pool "shares this single limit across every worker, so it matters even more there."7 It also means that messages waiting on slow answers or long nak delays occupy slots that new work cannot use.

Nothing configured so far limits how many times a failing message is redelivered. That limit, and the spacing between attempts, is the subject of Lesson 6.

Why it matters

This loop is the vocabulary a failure-handling design is written in. Each failure a handler can detect maps to an answer: transient failures to a delayed nak, permanent failures to term, slow work to in-progress. Failures the handler cannot detect, such as a crash, a hang, or a lost connection, are covered by AckWait without any code running. A design that names, for each kind of failure, which of these paths it takes is already most of the way to a DLQ design.

It also shows why NATS has no DLQ object to switch on. The server's part is limited to keeping a pending list and a timer per consumer. Deciding that a message is poison, and what should happen to it, is the worker's answer. AckWait also has to be chosen against real processing time: "If a job often takes longer than AckWait and the worker never sends in-progress, the server decides the worker stopped and redelivers a message that's still being handled, so two workers run the same order."2

Key line Every delivery waits on an answer: ack for done, nak for try again, term for never, in-progress for not yet. No answer before AckWait counts as failure, and the message goes back to the consumer. That loop is what JetStream's at-least-once means.
The common trap The near-miss is "term sends the message to a dead-letter queue." Term only clears the pending entry and stops this consumer from delivering the message again; nothing is moved anywhere. The second slip is treating a nak as a gentle retry. A plain nak redelivers at once, so a handler that naks on every error against a down dependency spins through attempts with no pause. Transient failures need a nak with a delay.

Recall: answer before peeking.

① A worker pulls a message, then its pod is killed before it answers. No code runs. What happens to the message, and when?

show answer

It stays on the consumer's pending list until AckWait runs out (30 seconds by default). The server then treats the missing answer as a failure and redelivers it to the consumer, so any worker on that consumer can receive it.

② A payment provider returns a 503 for a few minutes. Which answer should the handler give, and why not the alternatives?

show answer

A nak with a delay. The failure is transient, so the message should come back, but after a pause. A plain nak retries at once and fails again; term would drop it for good although it could succeed later; ack would mark unfinished work as done.

③ Why is ack_policy: all risky on a consumer with several workers?

show answer

One ack retires every earlier message too. With parallel workers, an ack for message 10 can retire message 7 that failed and was waiting for redelivery, so message 7 is lost without any error.
