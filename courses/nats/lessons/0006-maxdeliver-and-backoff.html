Giving up: MaxDeliver and BackOff

Lesson 5 showed how a consumer brings a message back: a nak, or an AckWait that runs out. By default nothing ever stops that loop. Three settings decide how often a message comes back, how long the server waits between attempts, and when it gives up. This lesson covers those settings and what giving up actually does to the message.

The concept

The docs name the limit directly: "MaxDeliver is the limit on attempts."1 Its default is -1, which means unlimited.1 A consumer created with defaults retries a failing message forever. BackOff and the nak delay from Lesson 5 decide the spacing between attempts. Term, also from Lesson 5, lets the handler give up before the server does.

Giving up is not the same as deleting. When a message reaches MaxDeliver, the consumer stops delivering it, and the message itself is left where it was. Most of the design consequences in this arc follow from that difference.

Two ways a message stops coming back: the handler terms it, or the count reaches MaxDeliver. Only the first one acks.

Step 1 — Delivery n reaches a worker

MaxDeliver counts every delivery of a message to the consumer, the first one included. Redeliveries caused by a nak count, and so do redeliveries caused by an AckWait timeout.2 A consumer set to max_deliver: 5 hands a message to a worker at most five times in total.

With the default of -1, a broken payload never stops. The docs describe the cost even with a finite limit: without term, "a broken payload is nak'd over and over until MaxDeliver gives up, using the full set of attempts and holding up the messages behind it."1 With no limit, that holding up has no end.

Step 2 — The outcome decides what comes next

The four responses from Lesson 5 map onto the diagram. An ack ends the story. A term ends it too, from the handler's side. A nak, or silence until AckWait runs out, sends the message round again. Each of those last two paths has its own wait.

This is also where MaxAckPending from Lesson 5 comes in. It caps how many delivered but unacked messages a consumer may have, and delivery stops when the cap is reached.2 A message cycling through redelivery has not been acked, so it occupies one of those slots for as long as it cycles. A few poison messages with unlimited MaxDeliver keep their slots for good. That last point follows from the MaxAckPending definition; the docs phrase it as the message "holding up the messages behind it".

Step 3 — The wait before the next attempt

Timeouts use BackOff. BackOff is a list of delays on the consumer. "Setting a backoff replaces AckWait: the first entry in the list becomes the wait before the first redelivery, so it's also the ack deadline for the first delivery."1 The server code does the same thing literally: config.AckWait = config.BackOff[0].3 "If the list has fewer entries than MaxDeliver allows, the server reuses the last entry for the remaining attempts."1 A list longer than MaxDeliver is rejected, unless MaxDeliver is -1.3 BackOff needs server 2.7.1 or later.2

backoff: [1s, 5s, 30s]   max_deliver: 5

delivery 1   ack deadline 1s    (backoff[0] replaces AckWait)
delivery 2   after 1s timeout,  ack deadline 5s
delivery 3   after 5s timeout,  ack deadline 30s
delivery 4   after 30s timeout, ack deadline 30s  (last entry reused)
delivery 5   after 30s timeout, ack deadline 30s
             no answer: consumer stops delivering it

Naks do not use BackOff. The docs are explicit: "A bare nak redelivers right away, and a configured backoff doesn't slow it." Instead, "to delay a nak, the client attaches the delay to the nak itself."1 In nats.js that is m.nak(5_000), the delayed nak from Lesson 5. A handler that catches an error and sends a bare nak burns through MaxDeliver in milliseconds, whatever the BackOff list says.

Step 4 — The count against MaxDeliver

When the count reaches the limit, the consumer stops delivering the message. It does not ack it. Under Limits retention, "the message itself stays in the stream … other consumers still see it, and it ages out with the stream's limits like any other message."1 On a WorkQueue stream, where only an ack removes a message (Lesson 3), the old developer docs state the result: messages that reached MaxDeliver "will remain in the stream and must be manually deleted via the JetStream API."4 On an Interest stream the same reasoning says the message is kept until the stream's limits remove it, because the consumer never acks it. That last case is inferred from the Interest definition, not stated in the docs.

The consumer's normal output says nothing about any of this. "MaxDeliver drops a message with no dead-letter. The message stays in the stream, but the shipping consumer's normal output says nothing, so the drop is easy to miss."1

Step 5 — Term against MaxDeliver: two different endings

Term is the handler deciding the failure is permanent. The server processes it like an ack, so it suppresses redelivery at once.5 That has a retention consequence: "On a WorkQueue or Interest stream, where a handled message is removed, a term removes it just as an ack would."1 Reaching MaxDeliver never acks, so the message stays.

A consumer that uses all of these looks like this. The field names come from the nats.js ConsumerConfig type, and durations are in nanoseconds, hence nanos(). This snippet is composed from verified signatures and has not been run.6

import { nanos } from "@nats-io/transport-node";
import { AckPolicy } from "@nats-io/jetstream";

await jsm.consumers.add("ORDERS", {
  durable_name: "shipping",
  ack_policy: AckPolicy.Explicit,
  max_deliver: 5,
  backoff: [nanos(1_000), nanos(5_000), nanos(30_000)], // replaces ack_wait
});

// in the handler:
//   invalid payload   -> m.term("invalid payload")   permanent, acts as an ack
//   downstream error  -> m.nak(5_000)                transient, delayed retry
//   success           -> m.ack()

Why it matters

Every consumer in the design needs a finite MaxDeliver. The default retries forever and quietly takes MaxAckPending slots from healthy messages. Picking the number is a design decision: it is the number of attempts after which a message is judged unprocessable.

The other decisions follow from the table. Use term for failures the handler can recognise as permanent, such as a payload that fails validation, and choose the stream's retention knowing that term removes the message from a WorkQueue stream. Use a delayed nak for transient errors the handler catches, and BackOff for the case where the handler crashes or hangs and never answers. Size the first BackOff entry above normal processing time, because it becomes the ack deadline. For a long downstream outage, burning attempts is the wrong tool: server 2.11 added consumer pause, which stops delivery until a deadline and keeps redelivery counts.7 Which server version Synadia Cloud runs is not stated publicly, so check before relying on it.

The gap is visible now. A message that reaches MaxDeliver stops being delivered and nothing in the consumer's output reports it. A design that must handle failed messages needs a signal for that moment.

Key line MaxDeliver defaults to unlimited, and reaching it stops delivery without deleting anything. BackOff spaces out timeouts only; a nak needs its own delay. Term acts as an ack, so on a WorkQueue stream it removes the message, while hitting MaxDeliver leaves it in place.
The common trap The near-miss is "BackOff controls the delay between retries." It controls the delay between retries caused by an AckWait timeout. A handler that catches an exception and calls a bare nak() gets immediate redelivery regardless of the BackOff list, and uses up MaxDeliver in a tight loop. The second slip is assuming a message that reached MaxDeliver is gone. It is still in the stream, and on a WorkQueue stream it stays there until something deletes it.

Recall: answer before peeking.

① A consumer has ack_wait 30s and backoff: [2s, 10s]. What is the ack deadline for the first delivery, and why?

show answer

2 seconds. Setting a backoff replaces AckWait, and the first entry becomes the ack deadline for the first delivery. A job that normally takes 5 seconds would be redelivered while still running.

② A handler catches every error and calls m.nak() with no argument. The consumer has max_deliver: 10 and a BackOff list of minutes. How long until the consumer gives up on a broken message?

show answer

Close to no time. A bare nak redelivers right away and BackOff does not slow it, since BackOff only spaces out AckWait timeouts. The ten attempts are spent in a tight loop. A delayed nak, such as m.nak(5_000), fixes it.

③ On a WorkQueue stream, one message is termed and another reaches MaxDeliver. Which of the two is still in the stream afterwards?

show answer

The one that reached MaxDeliver. Term is processed like an ack, and on a WorkQueue stream an ack removes the message. Reaching MaxDeliver never acks, so that message stays until it is deleted through the API or removed by the stream's limits.
