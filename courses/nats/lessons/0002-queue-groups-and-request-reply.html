Queue groups and request-reply

Lesson 1 delivered every message to every interested subscriber. A microservice system needs two more shapes: spread work across replicas of one service, and ask a question that gets one answer. Core NATS builds both from the same publish and subscribe, with no queue on the server. That last part decides what happens when something fails.

The concept

A queue group turns several subscribers into one logical subscriber, so each message goes to exactly one replica. Request-reply uses publish and subscribe twice, once out and once back, so a caller can wait for an answer. Neither adds storage. Both inherit the at-most-once guarantee from Lesson 1, but request-reply gives the caller something a plain publish never does: a signal when nothing answered.

Steps 1 and 2 are load spreading. Steps 3 and 4 are a round trip. None of them stores a message.

Step 1 — A queue group picks one member per message

The docs define it directly: "A queue group is a set of subscribers on the same subject that share a name. The server treats the whole group as one logical subscriber: for each message, it picks exactly one member of the group and delivers to that member alone."1 Running three replicas of a service with the same group name spreads the load across them.

No setup is involved: "There's nothing to configure on the server. … The server learns a group exists the moment its first member subscribes."1 In nats.js the group is one option on the subscription:2

const sub = nc.subscribe("orders.created", { queue: "packers" });
for await (const m of sub) {
  console.log(`packer handling: ${m.string()}`);
}

Step 2 — Plain subscribers still get every message

A queue group and a plain subscriber can share a subject. Plain subscribers always get every message, while the group gets one copy shared among its members. "The server runs the two distributions independently."1 One subject can therefore feed an analytics service that counts every order and a packing pool that handles each order once.

Step 3 — A request carries its own reply subject

"Request-reply isn't a new protocol; it's the pub/sub you already know, used twice."3 The client creates a private reply subject called an inbox, under the reserved _INBOX. prefix, and sends it with the request. The responder publishes its answer to that inbox. The client subscribes once to a wildcard such as _INBOX.<connection>.* and gives each request a fresh last token, so "thousands of concurrent requests cost one subscription, not thousands."3

Responders are ordinary subscribers, so a service usually answers requests from a queue group. Each request then reaches one replica.

Step 4 — The caller learns about two different failures

The reply is a core message too, so it can be lost. Every request has a timeout, and in nats.js the default is one second.2 If no subscriber exists at all, the client does not wait out the timeout. The server replies at once with a status 503 and no payload, and the client raises a separate error. The docs put the difference plainly: "A missing service surfaces immediately as NoRespondersError; a slow one as TimeoutError."3

In nats.js v3 a timeout rejects with TimeoutError. A no-responders reply rejects with a RequestError whose cause is NoRespondersError, which isNoResponders() checks.4 Composed from those types, not run against a server:

import { connect, errors } from "@nats-io/transport-node";

try {
  const m = await nc.request("orders.inventory.check", order, { timeout: 2000 });
  console.log(m.string());
} catch (err) {
  if (err instanceof errors.RequestError && err.isNoResponders()) {
    // nobody subscribed: the service is down or not deployed
  } else if (err instanceof errors.TimeoutError) {
    // someone may have received it: slow, crashed mid-work, or reply lost
  }
}

Why it matters

A queue group is load balancing, not a work queue. The docs name the limit: core NATS is at-most-once, "so if the server picks a packer and it dies after delivery, that message is gone," and "the server won't retry it with another member." They also give the remedy: "Work that must survive a worker crash belongs in a durable work queue in JetStream."1 Running many replicas does not change this. Nothing holds the message for a second attempt.

Request-reply changes who owns failure. The caller is waiting, so the caller decides: retry, report an error upstream, or fall back. No-responders means the request reached nobody, so a retry cannot cause the work to happen twice. A timeout is ambiguous. The responder may have done the work and the reply was lost, so a retry after a timeout must be safe to repeat. For a design, the question per flow becomes: does the sender need an answer now, so failure surfaces to it (request-reply)? Or does the sender move on, so something other than the sender must keep the message (JetStream, from the next lesson on)?

Key line A queue group spreads messages across replicas but keeps none of them, so a replica that dies mid-message loses it. Request-reply keeps nothing either, but it hands failure back to the caller, with no-responders and timeout as two different signals.
The common trap The near-miss is treating a timeout like no-responders and retrying freely. No-responders is a 503 the server sends because no subscription existed, so the request reached nobody. A timeout only says no reply arrived in time. The responder may have handled the request and crashed before replying, or the reply may have been lost, so a blind retry can do the work twice. The second slip is calling a queue group a queue. Nothing waits in it. If no member is subscribed, the message is discarded, exactly as in Lesson 1.

Recall: answer before peeking.

① Three replicas of a service share the queue group billing. One crashes right after receiving a message. What happens to that message?

show answer

It is gone. Core NATS delivered it at most once to the one member it picked, and nothing stores it for another member. Surviving a worker crash requires JetStream.

② On orders.created there is a queue group packers with three members and one plain subscriber analytics. One message is published. How many copies are delivered, and to whom?

show answer

Two. One goes to a single member of packers, and one goes to analytics. The server runs the group distribution and the plain distribution independently.

③ A request fails. Why does it matter whether the error is no-responders or a timeout before retrying?

show answer

No-responders is an immediate 503 meaning no subscriber existed, so the request reached nobody and a retry is safe. A timeout means no reply arrived in time; the responder may have done the work, so a retry must be safe to repeat.
