NATS and JetStream for failure handling · Arc 1 · Lesson 1

Subjects and at-most-once delivery

Core NATS does one thing: it hands a message published to a subject to every client subscribed to that subject at that moment. It keeps nothing. Every later lesson about retries, advisories and dead letters exists because of that one fact, so it comes first.

The concept

The docs state the whole model in a sentence: "Core NATS has one fundamental operation: a client publishes a message to a subject, and every client subscribed to that subject right now gets a copy."1 There is no queue object to create and no topic to declare. A subject is a string, and the server matches publishers to subscribers by that string.

The important words are "right now". The server does not hold a message for a subscriber that is not there. Persistence, redelivery and replay belong to JetStream, which later lessons build on top of this layer.

Step 1 — The publisher names one literal subject

A subject is a dot-separated string such as orders.us.created. The dots split it into tokens, and the server matches token by token.2 Subjects are case-sensitive and contain no whitespace. A publisher always names one full subject: "Wildcards are a subscriber-only tool."2

Subjects are never declared. The server keeps an entry only while something subscribes, so a design can use very fine-grained subjects (one per order, per tenant, per region) at little cost.2 Subjects that start with $ are reserved for the system. $JS., the JetStream API and advisory namespace, is the one this course comes back to.

Step 2 — Subscribers match with wildcards

A subscriber can name a literal subject or a pattern. Two wildcards exist:2

orders.*.created    *  matches exactly one token
                       matches  orders.us.created
                       misses   orders.created          (zero tokens)
                       misses   orders.us.west.created  (two tokens)

orders.>            >  matches one or more tokens, last position only
                       matches  orders.us.created, orders.us.west.created
                       misses   orders                  (needs at least one)

Token order is therefore a design decision. Put the dimensions you will filter on in positions a wildcard can reach. orders.<region>.<event> lets one service take orders.*.created and another take orders.eu.>. JetStream streams and consumers also select messages by subject pattern, so this hierarchy carries through the rest of the design.

Step 3 — The server delivers to whoever is interested now

Publishing is fire-and-forget: "the call hands the message to the server and returns."1 The publisher learns nothing about how many subscribers received the message, or whether any did. The guarantee is named directly: "Core NATS delivers each message at-most-once. … A subscriber that's absent, slow, or disconnected at that instant gets it zero times."1

The no-subscriber case needs to be named, because it is the quiet one. A message published where nothing is subscribed "was published into an empty interest graph and discarded."1 No error is raised. The publisher cannot tell the difference.

Step 4 — What a message is, in nats.js

In nats.js v3 the core API lives in the modular @nats-io/* packages. On Node, @nats-io/transport-node exports connect().3 Adapted from the core README (the README imports the Deno transport; the rest is identical):4

import { connect } from "@nats-io/transport-node";

const nc = await connect({ servers: "demo.nats.io:4222" });

const sub = nc.subscribe("orders.*.created");
(async () => {
  for await (const m of sub) {
    console.log(m.subject, m.string());
  }
})();

nc.publish("orders.us.created", "order 42");  // returns at once, no ack

await nc.drain();

Note what is absent. There is no ack, no retry setting and no "failed" state. A core subscription has nothing to give up on, because the server never promised a second attempt.

Why it matters

The design doc asks how the system handles messages that fail. On core NATS that question has no answer at the messaging layer. A message that never reaches a handler, because the handler crashed, was slow or was not deployed yet, is gone, and nothing records that it existed. Nothing exists to dead-letter, because nothing was kept.

That is not a flaw. The docs name the workloads where at-most-once is correct: "telemetry you sample, cache invalidations, a live dashboard feed."1 Some flows in a microservice system fit that list. Many, such as orders, payments and state changes another service depends on, do not. The first design decision per flow is which layer it belongs on, and every failure-handling feature this course covers (acks, redelivery limits, advisories, the DLQ pattern) exists only on the JetStream side of that line.

Key line Core NATS delivers to whoever is listening right now, at most once, and keeps nothing. If a message must survive a crash or a missing consumer, it belongs on JetStream, because there is nothing in core NATS to retry or dead-letter.
The common trap The near-miss is "core NATS is unreliable, so messages get lost in transit." The transport is not the issue. The guarantee is defined by interest at publish time: a subscriber that is connected and keeping up receives the message. What core NATS does not do is store a message for a subscriber that is absent, slow or disconnected, and it gives the publisher no signal either way. The second slip is assuming a publish to a subject with no subscribers raises an error. It is discarded silently.

Recall: answer before peeking.

① A service restarts for ten seconds. During that window, three messages are published on a subject only it subscribes to, using core NATS. What happens to them, and what does the publisher see?

show answer

They are discarded. Delivery is at-most-once and decided by interest at publish time, so an absent subscriber gets zero copies. The publisher sees nothing, because publish is fire-and-forget and reports no delivery result.

② Which of these does orders.*.created match: orders.created, orders.eu.created, orders.eu.de.created? What would match all three region shapes with one or more tokens after orders?

show answer

Only orders.eu.created, because * matches exactly one token. orders.> matches the other two as well, but it also matches every other event under orders, not only created.

③ Why can a publisher not use a wildcard?

show answer

Wildcards are subscriber-only. A publish names one literal subject, and the server matches that subject against the subscription patterns.
