Streams and retention

Lessons 1 and 2 ended on the same gap: core NATS keeps nothing, so nothing can be retried. A JetStream stream closes that gap. It stores messages on the server before anyone reads them, numbers each one, and removes them only when a rule says so. Which rule removes a message is the decision this lesson is about.

The concept

The docs define it in two sentences: "Plain core NATS drops any of these messages the moment no service is listening. A stream saves them instead. A stream is a store that runs on the server and keeps every message on the subjects you choose."1 Publishers do not change much. They still publish to a subject. If a stream's subject list matches, the server stores the message and confirms it.

Storing is half the design. The other half is when a stored message leaves. Two separate mechanisms decide that: limits, which remove messages when the stream is too old or too large, and the retention policy, which can remove a message once readers are finished with it.

One way in, two ways out. Limits and retention are independent, and both always apply.

Step 1 — A stream captures subjects

A stream has a name and a list of subjects, and the list may use wildcards. The docs' example stream ORDERS captures orders.>, so orders.created and orders.shipped are stored, and so would a new orders.refunded subject be, with no change to the stream.1 This is where the subject hierarchy from Lesson 1 pays off. A subject may be bound by only one stream.6

Two settings are fixed at creation. Storage is file (the default) or memory, and memory storage does not survive a server restart.67 Replicas sets how many servers hold a copy, defaulting to 1 with a maximum of 5.6 In nats.js v3 the stream is created through the JetStream manager:17

import { jetstreamManager, RetentionPolicy } from "@nats-io/jetstream";

const jsm = await jetstreamManager(nc);
await jsm.streams.add({
  name: "ORDERS",
  subjects: ["orders.>"],
  retention: RetentionPolicy.Limits,   // the default, stated for clarity
});

Step 2 — A publish is confirmed with a sequence number

A plain publish returns nothing. A JetStream publish waits for a PubAck, which "contains the name of the stream that stored the message and the sequence number the stream gave it. Sequence numbers start at 1 and only increase. The server gives each new message the next number and never reuses one."2

import { jetstream } from "@nats-io/jetstream";

const js = jetstream(nc);
const pa = await js.publish("orders.created", data, { msgID: "ord_8w2k-created" });
console.log(pa.stream, pa.seq, pa.duplicate);

The PubAck has a precise meaning. It confirms the message is stored. "It does not confirm that any consumer has received it."2 The stream sequence is the message's permanent address inside the stream, which matters whenever something later needs to find one specific message.

Step 3 — Retries are made safe with a message ID

If a publish fails or its PubAck never arrives, the publisher should retry, and the docs say to "make the retry safe with the Nats-Msg-Id header."2 The msgID option above sets it. Inside the stream's duplicate window, two minutes by default, the server stores a repeated ID once and returns a PubAck with duplicate: true.12 The ID should be one the producer can recompute, "such as an order ID, a request ID, or a hash of the payload."2 A retry after the window has passed is stored again.6

Step 4 — Limits remove messages when the stream is too old or too big

MaxAge, MaxMsgs and MaxBytes cap the stream, and "whichever one is reached first triggers a discard."3 All are unlimited by default.1 The discard policy chooses the victim: "the server discards the new message or the oldest stored one."3 DiscardOld, the default, deletes the oldest messages to make room. DiscardNew rejects the publish that would exceed the limit, so the publisher sees an error instead of silent loss of old data.6

Step 5 — Retention removes messages when readers are done

Streams are read through consumers, named readers that confirm each message they have handled with an ack. The next two lessons cover both in depth; retention needs only that much. "A stream has exactly one retention policy," and there are three:4

Limits     (default)  removed only by limits. Reading and acking change nothing.
Interest              removed once every consumer whose filter covers it has acked.
                      No interested consumer when it arrives: removed right away.
WorkQueue             removed by the first ack. Each message is handled once, then gone.

The docs pair each with a kind of work: an audit log or event history uses Limits, a fan-out where every consumer must process each message uses Interest, and a job queue where each message is work for one worker uses WorkQueue.4 Limits still apply under all three, as "the backstop that keeps it bounded when consumers fall behind."4 Retention cannot be changed later. The docs advise to "create a new stream with the right policy rather than editing the running one."4

Since version 2.11 a stream with AllowMsgTTL also accepts a per-message Nats-TTL header, a third way for a stored message to expire. That setting can be enabled and never disabled.5

Why it matters

A stream is what makes failure handling possible at all. A message that a reader fails to handle is still in the stream, under a known sequence number, so it can be delivered again. That is the property Lessons 1 and 2 lacked.

Retention decides how long that second chance lasts, and it is fixed at creation. On a Limits stream a handled message stays until age or size removes it, so it can still be read back by sequence for inspection or replay. On a WorkQueue stream the first ack deletes it, and on an Interest stream the last interested ack does. Those two keep the stream small, but nothing remains to look at afterwards unless the design copies it somewhere first. Two other choices remove messages nobody has handled yet: a MaxAge shorter than the longest outage a reader might have, or DiscardOld with a MaxMsgs cap that a backlog can reach. Both should be chosen with failure in mind, not only disk size.

Key line A stream stores every message on its subjects and gives each one a sequence number that is never reused. Limits remove messages when the stream is too old or too big. Retention removes them when readers are done. Pick retention from the kind of work, because it cannot be changed later.
The common trap The near-miss is "a PubAck means the message was delivered." It means the message was stored in a stream at a given sequence. No consumer may have read it yet, and on a stream with a short MaxAge none may ever read it. The second slip is assuming WorkQueue or Interest retention replaces limits. Retention adds a second way out; limits still apply, and a WorkQueue stream with DiscardOld and a message cap can drop work before any reader saw it.

Recall: answer before peeking.

① A publisher retries after a network blip and both attempts reach the server within a minute. What prevents a duplicate, and what does the second PubAck report?

show answer

A Nats-Msg-Id header (the msgID option) with a stable ID. Inside the duplicate window, two minutes by default, the server stores it once, and the second PubAck reports duplicate: true with the same sequence.

② On which retention policy does a message stay in the stream after it has been read and acked, and what removes it eventually?

show answer

Limits. Acks have no effect on what a Limits stream keeps; the message leaves when MaxAge, MaxMsgs or MaxBytes is reached, per the discard policy.

③ A team creates a Limits stream for a job queue and later wants WorkQueue behaviour. What are the options?

show answer

Retention cannot be edited after creation. Create a new stream with WorkQueue retention and move the work to it.
