Consumers — a cursor on the stream

A stream stores messages. It does not decide who reads them or how far each reader has got. That is the job of a consumer: an object on the server that holds one reader's position in one stream. Every failure-handling setting in the rest of this course lives on the consumer, so the shape of this object comes first.

The concept

The docs define it in one line: "A consumer is a server-side cursor on a stream."1 A client connects to the consumer to receive messages, and "the consumer tracks how far that client has progressed and hands out the next one."1

Two properties follow. The consumer is not part of the application: "it's an object on the server, sitting next to the stream."1 And a stream can feed many consumers at once, "each reading at its own pace and each with its own position."1 Reading a message through one consumer does not remove it from the stream or hide it from another consumer. Removal is a retention decision on the stream, covered in Lesson 3.

Step 1 — The consumer holds the position, not the client

Because the position lives on the server, "the client can disconnect and reconnect without losing its place or tracking any sequence numbers itself."1 A worker process can crash, restart, or be replaced by a new deployment, and it resumes where the consumer left off.

The consumer also keeps a counter of its own. Each consumer has a consumer sequence: a counter the server bumps on every delivery, redeliveries included, "so it counts deliveries, not distinct messages."1 The stream sequence from Lesson 3 identifies a message; the consumer sequence counts handovers. The difference matters once redelivery enters the picture in Lesson 5.

Step 2 — Durable or ephemeral

A consumer is durable when it is created with a durable name; otherwise it is ephemeral.2 A durable consumer's state is kept by the server under that name, so a reader "resumes where it left off after a disconnect or a server restart instead of starting over."1 An ephemeral consumer has no persisted state or fault tolerance and is removed automatically after a period of inactivity.2

Setting inactive_threshold controls only that automatic cleanup. It does not make a consumer durable, and since server 2.9 it applies to durable consumers as well.2 For a service that processes work, the choice is a durable consumer, because the position and the record of what is in flight must survive a restart.

Step 3 — Pull: the worker asks

"Pull means the client asks the server for messages when it's ready, rather than having the server push them on its own. Pull is the default for new consumers; an older push model exists."1 The older docs give the recommendation directly: pull consumers for new projects, "in particular when scalability, detailed flow control or error handling are a concern."2

In nats.js v3 a durable is created with the JetStream manager and read through js.consumers.get(), which returns a pull consumer. The client offers three ways to pull: one message (next), a bounded batch (fetch), or a continuous loop where the library issues pulls in the background (consume).34 Adapted from the JetStream README:3

import { AckPolicy, DeliverPolicy, jetstream, jetstreamManager } from "@nats-io/jetstream";

const jsm = await jetstreamManager(nc);
await jsm.consumers.add("ORDERS", {
  durable_name: "shipping",
  ack_policy: AckPolicy.Explicit,      // Lesson 5
  deliver_policy: DeliverPolicy.All,
  filter_subject: "orders.created",
});

const js = jetstream(nc);
const c = await js.consumers.get("ORDERS", "shipping");

const messages = await c.consume();    // continuous pull loop
for await (const m of messages) {
  console.log(m.seq, m.subject);       // m.seq is the stream sequence
  m.ack();
}

The ack line closes each delivery. What it means, and what the alternatives are, is the whole of Lesson 5.

Step 4 — Where it starts and what it sees

Two settings shape what a consumer hands out. The deliver policy picks the starting point: all (the default, from the first stored message), last, last_per_subject, new (only messages stored after creation), or a start sequence or start time.2 It cannot be changed after creation.2

A filter subject narrows what the consumer sees. "A filter is a subject pattern attached to a consumer. The consumer receives only the messages whose subject matches the filter; the rest of the stream is skipped."5 It uses the same * and > wildcards as core subscriptions in Lesson 1, which is why the subject hierarchy chosen early carries through to here.

Step 5 — Fan out with consumers, share work within one

Two different jobs look alike and need different shapes. To give each service its own copy of every message, create one consumer per service: billing and shipping each read the full stream at their own pace. To spread one service's work across replicas, point every replica at the same consumer. "Point several processes at the same shipping consumer and they share the load: the server hands each stored order to exactly one worker."6

The docs put the distinction in one sentence: "The workers share a position, not the messages."6 This resembles a queue group from Lesson 2, with a difference that decides failure behaviour. A queue group spreads live deliveries among whoever is subscribed, and nothing is kept. A shared consumer spreads stored messages from one cursor, so a message survives the worker that was handling it.

Why it matters

A consumer is where JetStream keeps the facts that failure handling depends on: which messages a service has been handed, which it has finished, and how many handovers each has had. The stream only holds the messages. So the failure policy for a service is a property of that service's consumer, and two services reading the same stream can have different retry rules without affecting each other.

It also fixes three early design choices. Each service that must not miss work gets its own durable consumer, not an ephemeral one, because the in-flight record has to outlive a restart. Scaling a service means adding workers to its consumer, not adding consumers, since a second consumer would hand every message out a second time. And the filter subject plus deliver policy decide, at creation, exactly which slice of the stream that service is responsible for.

Key line A consumer is a server-side cursor on a stream. One consumer per service fans out; many workers on one consumer share the work. The position lives on the server, so the worker can die and the work does not.
The common trap The near-miss is "consuming a message takes it off the stream." Reading through a consumer moves that consumer's position and nothing else; whether the message is ever removed is the stream's retention policy. The second slip is scaling a service by giving each replica its own consumer. Each consumer reads the whole stream, so every replica would process every message. Replicas of one service belong on one shared consumer.

Recall: answer before peeking.

① A shipping service runs three replicas and must process each order once. Billing must also see every order. How many consumers, and which workers attach to which?

show answer

Two durable consumers on the stream: one for billing, one for shipping. All three shipping replicas attach to the shipping consumer, which hands each stored message to exactly one of them. Billing reads from its own consumer at its own pace.

② A worker on an ephemeral consumer is down for an hour over a weekend. What is the risk, compared with a durable consumer?

show answer

An ephemeral consumer has no persisted state and is removed after a period of inactivity, so its position can be gone when the worker returns. A durable consumer keeps its position under its name across disconnects and server restarts.

③ How does a shared consumer differ from a queue group from Lesson 2, given that both hand each message to one member?

show answer

A queue group divides live core deliveries and keeps nothing, so a message is lost if no member is there to take it. A shared consumer divides stored messages from one server-side position, so the message stays in the stream and the position survives any one worker.
