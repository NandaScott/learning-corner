Advisories

Lesson 6 ended on a silent drop: a message reaches MaxDeliver and the consumer's output says nothing. JetStream does report that moment, and the report is called an advisory. It is a plain NATS message on a reserved subject, and it follows the same at-most-once rule as Lesson 1. A design that relies on advisories has to make sure something is always there to receive them.

The concept

The docs define it in two sentences: "An advisory is a transient JSON message that JetStream publishes once, the moment something noteworthy happens to a stream or a consumer. It's a normal NATS message on a well-known subject."1 Those subjects live under $JS.EVENT.ADVISORY., inside the $ namespace that Lesson 1 described as reserved for the system.

The word that matters for failure handling is "transient". An advisory is not kept anywhere unless something keeps it.

Step 1 — An event fires in the server

Many events produce an advisory: streams and consumers created or deleted, leader elections, storage running out, and others.2 Three are about individual messages on a consumer, and those are the ones a failure-handling design reads:23

AdvisoryFires whenSubject
Max deliveriesA message reaches MaxDeliver without a final ack$JS.EVENT.ADVISORY.CONSUMER.MAX_DELIVERIES.<stream>.<consumer>
TerminatedThe handler sends term$JS.EVENT.ADVISORY.CONSUMER.MSG_TERMINATED.<stream>.<consumer>
NakThe handler sends any nak$JS.EVENT.ADVISORY.CONSUMER.MSG_NAKED.<stream>.<consumer>

The max-deliveries advisory depends on Lesson 6. The server only sends it when MaxDeliver is greater than zero, so a consumer left at the default of -1 never produces one.4 The server code also sends it only once per message. Reading the code, it fires when the server would otherwise make the next delivery, which is after the last attempt's ack deadline runs out or after its nak, not at the moment of the last delivery.4 That timing comes from the source, not from a documented statement.

Step 2 — The server checks for interest

Before it publishes, the server checks whether anything is subscribed to that subject. If nothing is, it skips the publish. The comment in the source reads: "If there is no one listening for this advisory then save ourselves the effort."5 This is the empty interest graph from Lesson 1, applied to the server's own messages. With no subscriber, the event leaves no trace at all.

Step 3 — The advisory is published once

The payload is JSON with a type string naming its schema. The max-deliveries schema from the reference docs:3

{
  "type": "io.nats.jetstream.advisory.v1.max_deliver",
  "id": "…",                 // unique correlation ID for this event
  "timestamp": "…",          // RFC3339
  "stream": "ORDERS",
  "consumer": "shipping",
  "stream_seq": 987,         // the failed message's sequence in the stream
  "deliveries": 5
}

The terminated advisory (io.nats.jetstream.advisory.v1.terminated) carries the same fields plus consumer_seq and an optional reason, the free text passed to term(). The nak advisory (io.nats.jetstream.advisory.v1.nak) carries the same fields as terminated, without a reason.6 The reference page lists consumer_seq as a string; the server struct is an unsigned integer and sends a JSON number, so trust the server.6

None of these payloads includes the message body or its headers. An advisory says which message failed, by stream name and stream sequence (Lesson 3), and how many attempts were made. It does not say what the message was.

Step 4 — Who receives it

The docs state the consequence plainly: "An advisory is published exactly once, the moment its event fires, and it is not stored in any stream. If you're not subscribed at that instant, you never learn the event happened."1

A core subscription receives advisories only while it is connected. The docs show the TypeScript form, using a literal subject:7

const sub = nc.subscribe(
  "$JS.EVENT.ADVISORY.CONSUMER.MAX_DELIVERIES.ORDERS.shipping",
);
for await (const m of sub) {
  console.log(`max deliveries reached: ${m.string()}`);
}

nats.js also has a helper, jsm.advisories(), that yields { kind, data } objects. It is built on a core subscription to $JS.EVENT.ADVISORY.>, so it has the same weakness, and its list of kinds includes max_deliver and terminated but not nak.8 It is a monitoring tool.

The documented fix is a stream whose subjects are the advisory subjects, so the server stores each advisory as it would any other message. A stream listening on the subject also counts as interest, so the server publishes in the first place.5 The docs give the CLI form:1

nats stream add ADVISORIES --subjects '$JS.EVENT.ADVISORY.>' \
  --storage file --retention limits --max-age 168h --defaults

A narrower capture uses the wildcards from Lesson 1. In nats.js, composed from verified APIs and not run:9

import { nanos } from "@nats-io/transport-node";
import { StorageType } from "@nats-io/jetstream";

await jsm.streams.add({
  name: "ORDERS_FAILURES",
  subjects: [
    "$JS.EVENT.ADVISORY.CONSUMER.MAX_DELIVERIES.ORDERS.*",
    "$JS.EVENT.ADVISORY.CONSUMER.MSG_TERMINATED.ORDERS.*",
  ],
  storage: StorageType.File,
  max_age: nanos(7 * 24 * 60 * 60 * 1000), // 7 days
});

The * in the last token matches any consumer on the ORDERS stream. The capture stream needs room: a full stream with the discard-new policy from Lesson 3 rejects new messages, and an advisory rejected there is lost like any other.10

Why it matters

On Synadia Cloud, as on any NATS server, the advisory is the only record that a message was given up on. For the max-deliveries case it is the only signal at all, since the consumer reports nothing. So every failure-handling design built on JetStream starts with three decisions: a finite MaxDeliver so the advisory exists, a capture stream so it survives, and that stream created before the consumers it watches so no event falls into a gap.

Two limits shape what can be built on top. An advisory carries a pointer, the stream sequence, not the message, so anything that needs the payload has to look it up in the source stream. And advisories are published in the account that owns the stream. That scoping is read from the server code; whether Synadia Cloud lets an application account capture its own $JS.EVENT.ADVISORY subjects is not covered in public docs and is worth confirming with Synadia early.5

Key line An advisory is a core NATS message the server publishes once, and only if something is listening. To rely on it, bind a stream to the advisory subjects. Even then it holds a stream sequence, not the message.
The common trap The near-miss is "JetStream advisories are durable because they come from JetStream." They come from JetStream and travel over core NATS, with no storage unless a stream captures them. A service subscribing to advisories that restarts at the wrong moment misses the event for good, and the server does not publish at all when nothing is subscribed. The second slip is expecting a max-deliveries advisory from a consumer left at the default MaxDeliver of -1. It never fires.

Recall: answer before peeking.

① A team subscribes to max-deliveries advisories with jsm.advisories() in a monitoring service. That service is redeploying when a message hits MaxDeliver. What record of the event exists afterwards?

show answer

None. The helper is a core subscription, and advisories are published once and not stored. With no listener at that instant, the server may skip publishing entirely. Only a stream bound to the advisory subject would have kept it.

② What does a max-deliveries advisory payload tell you, and what does it not?

show answer

It names the stream, the consumer, the message's stream sequence and the number of deliveries, plus an event ID and timestamp. It does not include the message body or headers.

③ A consumer has max_deliver unset. A capture stream exists on $JS.EVENT.ADVISORY.CONSUMER.MAX_DELIVERIES.ORDERS.*. A poison message fails repeatedly. What lands in the capture stream?

show answer

Nothing. MaxDeliver defaults to -1, unlimited, so the message is redelivered forever and the server never sends a max-deliveries advisory. If the handler naks, nak advisories fire, but this stream does not capture that subject.
