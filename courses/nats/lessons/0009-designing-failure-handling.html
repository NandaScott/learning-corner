Designing failure handling for one service

Every earlier lesson covered one mechanism. This one uses all of them to design failure handling for a single service, an order-fulfilment worker, from the publish to the dead letter. Each step is a decision, and each decision is stated with the mechanic that justifies it.

The concept

The service is a fulfilment worker in a microservice system. An orders service publishes an event when an order is created. The fulfilment worker reserves stock and calls a shipping provider. Other services, such as billing, also read order events. The shipping provider sometimes times out, sometimes returns a server error for a few minutes, and occasionally goes down for hours. Some orders arrive malformed and can never be fulfilled.

The design question is the one from the design doc: what happens to an order event that fails? The answer below is one defensible design, not the only one. The decision table at the end shows where a different service would choose differently.

Six decisions, in dependency order. Each one constrains the next.

Step 1 — Pick the layer

Core NATS delivers at most once and keeps nothing (Lesson 1). An order event lost during a fulfilment deploy is an order nobody ships, so this flow belongs on JetStream. A request-reply call (Lesson 2) would tell the orders service that fulfilment failed, but it would make order creation wait on the shipping provider, and a no-responders error during a deploy would push the retry problem back onto the publisher. Persisting the event and letting the worker retry keeps the two services decoupled.

Step 2 — Shape the source stream

Three choices from Lesson 3:

  • Retention: Limits. Billing also reads order events, so WorkQueue is out: it removes a message on the first ack and rejects overlapping consumers.1 Limits retention has a second benefit for failure handling. A term counts as an ack, and "on a WorkQueue or Interest stream, where a handled message is removed, a term removes it just as an ack would."2 Under Limits the original stays, so the DLQ lookup by stream sequence (Lesson 8) still finds it. Retention cannot be changed after creation, so this choice is made once.3
  • Limits: max_age of 7 days. Long enough to outlast any realistic DLQ-worker outage and any replay window the team needs, and bounded so the stream does not grow forever.
  • Dedupe: Nats-Msg-Id set to the order ID. A publisher that retries after a lost PubAck stores the event once, inside the 2-minute default duplicate window.4

Step 3 — Configure the consumer

One durable pull consumer, fulfilment, shared by every worker replica (Lesson 4). Its settings come from Lessons 5 and 6:

  • ack_policy: explicit. Required for redelivery at all.5
  • max_deliver: 5. The default of -1 retries a poison message forever and never emits a max-deliveries advisory.5 A finite budget is the precondition for the DLQ.
  • backoff: [30s, 2m, 10m, 30m]. When BackOff is set it replaces AckWait, and its first entry becomes the ack deadline.6 So the first entry must exceed normal processing time, or slow but healthy work is redelivered. BackOff spaces only the redeliveries that follow an AckWait timeout, not naks.2 With max_deliver larger than the list, the last entry repeats.5
  • max_ack_pending: 200. The default is 1000, and delivery stops when the limit is reached across all replicas.6 A limit near the shipping provider's safe concurrency stops a backlog from flooding it. Too low starves batches.

The Synadia blog gives the sizing rule in one line: "Size MaxDeliver against the backoff schedule so the retries you want all get a chance to run."7 The total retry window is roughly the sum of the delays the budget reaches. An outage longer than that window sends messages to the DLQ, which is acceptable here because replay is cheap.

Step 4 — Decide the handler's response per error class

The handler, not the consumer config, knows why a message failed. Lesson 5's four responses map onto error classes:

Error classExampleResponseEffect
SuccessShipment bookedack()Removed from the pending list.
PermanentMalformed payload, unknown SKUterm(reason)Never redelivered; MSG_TERMINATED advisory with the reason.

Two consequences follow. First, a nak's delay comes from the handler, so the handler should grow it with m.info.deliveryCount to mirror the BackOff schedule.8 Second, delivery is at least once. A redelivered message may already have been processed, for example when the provider booked the shipment but the ack was lost. The handler must be idempotent, keyed on the order ID. The Synadia blog makes the same point: effectively-once results come from "idempotent consumers on top of at-least-once delivery."7

Step 5 — Capture the give-ups and copy them out

Exactly as Lesson 8 built it. A capture stream binds MAX_DELIVERIES and MSG_TERMINATED for ORDERS, created in the same deploy as the source stream so no advisory fires into an empty interest graph.9 A DLQ worker fetches each original with jsm.streams.getMessage and copies it into dlq.ORDERS.fulfilment with the advisory type, deliveries and term reason as headers. Because the source stream uses Limits retention, the original is still there after a term; copying it anyway makes the dead letter independent of the 7-day limit.

Step 6 — Replay and monitor

Replay is a republish from the DLQ stream to the original subject once the defect is fixed (Lesson 8). Because the handler is idempotent, replaying an order that was in fact shipped is harmless.

Monitoring watches levels and signals. jsm.consumers.info("ORDERS", "fulfilment") reports num_pending, num_ack_pending and num_redelivered.10 A rising redelivery count with a flat pending count points at a struggling downstream. A non-empty DLQ stream is the alert that a message gave up.

For an outage measured in hours, burning the retry budget sends every in-flight order to the DLQ. Server 2.11 added consumer pause, which stops delivery until a deadline and keeps the cursor and redelivery counts.11 Pausing fulfilment during a known provider outage is an operational alternative to replaying a large DLQ afterwards. It depends on the server version Synadia Cloud runs, which is not public and needs confirming.

The whole design in code

Composed from verified nats.js v3 signatures; not run against a server.810 Durations on the wire are nanoseconds, hence nanos(ms).

import { connect, nanos } from "@nats-io/transport-node";
import {
  AckPolicy, DeliverPolicy, RetentionPolicy, StorageType,
  jetstream, jetstreamManager,
} from "@nats-io/jetstream";

const nc = await connect({ servers: process.env.NATS_URL });
const jsm = await jetstreamManager(nc);
const js = jetstream(nc);
const DAY = 24 * 60 * 60 * 1000;
// Order, isValid, fulfil, PermanentError and region are application code.

// Step 2: source stream. Limits retention keeps originals after a term.
await jsm.streams.add({
  name: "ORDERS",
  subjects: ["orders.>"],
  retention: RetentionPolicy.Limits,
  storage: StorageType.File,
  num_replicas: 3,
  max_age: nanos(7 * DAY),
});

// Step 5: capture give-up advisories, same deploy as the source stream.
await jsm.streams.add({
  name: "ORDERS_DLQ_EVENTS",
  subjects: [
    "$JS.EVENT.ADVISORY.CONSUMER.MAX_DELIVERIES.ORDERS.*",
    "$JS.EVENT.ADVISORY.CONSUMER.MSG_TERMINATED.ORDERS.*",
  ],
  retention: RetentionPolicy.Workqueue,
  max_age: nanos(7 * DAY),
});
await jsm.streams.add({ name: "DLQ", subjects: ["dlq.>"] });

// Step 3: the work consumer.
await jsm.consumers.add("ORDERS", {
  durable_name: "fulfilment",
  filter_subject: "orders.*.created",
  deliver_policy: DeliverPolicy.All,
  ack_policy: AckPolicy.Explicit,
  max_deliver: 5,
  backoff: [nanos(30_000), nanos(120_000), nanos(600_000), nanos(1_800_000)],
  max_ack_pending: 200,
});

// Publisher side (orders service): dedupe on the order ID.
await js.publish(`orders.${region}.created`, JSON.stringify(order), {
  msgID: order.id,
});

// Step 4: the handler.
const NAK_DELAYS = [5_000, 30_000, 120_000, 600_000];
const c = await js.consumers.get("ORDERS", "fulfilment");
for await (const m of await c.consume({ max_messages: 10 })) {
  const order = m.json<Order>();
  if (!isValid(order)) {
    m.term("invalid payload");               // permanent
    continue;
  }
  const keepAlive = setInterval(() => m.working(), 10_000);
  try {
    await fulfil(order);                     // idempotent on order.id
    m.ack();
  } catch (err) {
    if (err instanceof PermanentError) {
      m.term(err.message);
    } else {
      const n = m.info.deliveryCount;        // 1 on first delivery
      m.nak(NAK_DELAYS[Math.min(n - 1, NAK_DELAYS.length - 1)]);
    }
  } finally {
    clearInterval(keepAlive);
  }
}
// Step 5 continued: the DLQ worker is the Lesson 8 worker, unchanged.

Why it matters

Each mechanism in the course answers one part of "what happens to a message that fails." JetStream decides whether the message exists to be retried. Retention decides whether the original survives being given up on. The consumer's budget and spacing decide how long the system keeps trying and how hard it hits a struggling downstream. The handler's choice of response decides which failures are retried and which are given up on at once. Advisories are the only signal that a give-up happened, and a capture stream is the only way that signal survives. The DLQ worker turns the signal back into a message someone can act on.

Read in reverse, the chain explains why NATS has no DLQ setting. A dead-letter queue depends on choices only the design can make: which failures are permanent, how long to retry, which retention policy, which payloads to keep. NATS provides each mechanism separately and leaves the policy to the system that knows its own failure modes. On Synadia Cloud the design work is the same. What remains to confirm is the account-level detail: server version, advisory capture, and plan limits.

Key line Failure handling on NATS is a chain the design builds: JetStream so the message exists, a finite MaxDeliver so giving up is possible, handler responses that separate transient from permanent, a capture stream so the give-up signal survives, and a DLQ worker that copies the payload while it still exists.
The common trap The near-miss is treating BackOff as the retry policy for every failure. BackOff spaces only redeliveries after an AckWait timeout, so a handler that catches errors and sends a bare nak gets immediate redelivery and burns its max_deliver budget in seconds. The handler has to supply its own delay on a nak. The second slip is setting BackOff's first entry below normal processing time; it replaces AckWait, so healthy slow work is redelivered while still running.

Recall: answer before peeking.

① The shipping provider returns 503 for ten minutes. The handler catches the error and calls m.nak() with no delay. The consumer has max_deliver: 5 and a BackOff of 30s, 2m, 10m, 30m. What happens to an order that arrives at the start of the outage?

show answer

It is redelivered immediately on each nak, because BackOff does not apply to naks. Five deliveries happen within seconds, the budget runs out, and a max-deliveries advisory fires. The order lands in the DLQ even though the provider recovers ten minutes later. A delayed nak that grows with the delivery count fixes it.

② Why does this design choose Limits retention for ORDERS even though only the fulfilment consumer does work on it?

show answer

Other services such as billing also read the events, which rules out WorkQueue. Limits also keeps the original after a term, which counts as an ack and would remove the message on a WorkQueue or Interest stream, so the DLQ lookup by stream sequence still finds it.

③ A worker books a shipment, then crashes before acking. What happens next, and which design choice keeps it from shipping twice?

show answer

AckWait expires and the message is redelivered after the BackOff delay. Delivery is at least once, so the handler must be idempotent on the order ID; the second attempt sees the order is already booked and acks.
